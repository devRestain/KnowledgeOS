# KnowledgeOS C12 adoption handoff

## Preparation boundary

The selected domain criterion is a Blueprint-typed synthetic note retrieved through the existing provider-free lexical path, normalized into a deterministic Pending proposal, then reviewed without changing source or review-time bytes. Approval records an owner decision and pending apply intent. Canonical apply is a separate explicit stage and is tested only against disposable notes.

The implementation is a graphless KnowledgeOS Capsule preparation. `PROJECT_STATE.md` binds the final commands and acceptance evidence. AgentFabric `CORE_C12_OPERATION_ADOPTION` remains the next planned objective. A local fixture result does not establish real corpus, Host adoption, provider, service, deployment or device acceptance.

The subsequent user-authorized KnowledgeHub alignment treats the unused existing Vault as implementation output. [KNOWLEDGEHUB_ALIGNMENT.md](KNOWLEDGEHUB_ALIGNMENT.md) declares the 65-file projection, exact retired-fixture recovery, profile boundaries and read-only real-Vault checks. This supersedes the preparation-only Vault preservation restriction for those filesystem artifacts while retaining real State/Runtime and operational cutover boundaries. Maintained generators define the resulting copies. Real generated-seed retrieval and isolated-copy proposal/review evidence remain distinct from real corpus acceptance and an operating writer. The intentionally inactive Git/broker pair yields a legacy profile diagnostic of DEGRADED with no configuration errors; native plugin execution remains unrun.

## Writer cutover and rollback procedure

1. Select the exact host, trusted principals, five roots, corpus, pending/canonical namespaces, legacy-data disposition and rollback targets. Record separate acceptance for Host binding, domain results and operational recovery.
2. Under that authorization, identify and stop the exact CLI/MCP/worker/scheduler/provider writers. Fence the old generation and record quiescence evidence; process existence or an inactive config alone does not prove quiescence.
3. Freeze an owner-controlled backup/checkpoint of the old private records and Vault Git revision plus dirty bytes. Preserve unresolved outcomes and frozen source/proposal/policy/schema pins. Do not stash, reset, clean or implicitly commit user changes.
4. Prepare distinct new State and Runtime roots. Apply an explicitly reviewed conversion/import tool or retain old records inert. Create a v3 owner journal only after deciding which records can be admitted; obtain fresh human decisions for legacy proposals.
5. Bind one owner writer generation and exact host ResourceBinding/HostBinding. Run `operation check`, then status and observation-only recovery against the selected roots. Admit the real domain workflow only after static binding and State checks pass.
6. Verify retrieve/propose/read-only review on the selected real corpus before authorizing any canonical apply. Revalidate all target bytes and pins immediately before explicit apply. Reconcile unknown effects from actual artifacts; do not automatically replay them.
7. For rollback, stop/fence the new writer first. Restore the exact old executable/config binding and the retained checkpoint only within the selected rollback scope. Observe whether any new effect reached the Vault before choosing an exact inverse; do not overwrite current notes or reactivate old approvals automatically.
