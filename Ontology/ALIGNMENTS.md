# KnowledgeOS Alignment Authoring

This authoring space declares no adopted cross-domain ontology alignment. It supplies a place for an actual mismatch to be proposed and reviewed. Existing Blueprint inverse aliases remain local relation rules and are not reclassified as cross-domain mappings.

## Identify an actual mismatch

Begin with a concrete permitted exchange or interpretation problem. Keep participating Operations' source definitions independent. Do not align concepts merely because their labels match or because a search model assigns high similarity.

## Author a bounded proposal

The following information is for review documentation rather than a new wire schema or executable alignment record.

| Information | Authoring requirement |
|---|---|
| Proposal identity and publisher | Name the stable proposal and the Operation responsible for publishing it. |
| Participants and adoption | Identify each meaning owner and the explicit adoption evidence required from each participant. |
| Purpose and scope | Describe the concrete mismatch and bounded permitted use. |
| Source and target | Reference exact source definitions and the versions and content digests used when reviewing the mapping. |
| Direction and strength | Distinguish descriptive association, hierarchy, claimed equivalence, or a value transform without treating them as interchangeable. |
| Loss and transforms | Declare information lost and any conversion needed, with example inputs and expected outputs. |
| Reverse use and composition | Review reverse direction and chaining separately; neither follows from forward adoption. |
| Policy and evidence | Reference participants' current export/admission policies, test observations, and owner review evidence. |
| Historical interpretation | Preserve original pins and record new lineage if a meaning changes. |

The preparation flow is actual mismatch, bounded proposal, participant review, transform verification, exact interpretation pins, and recipient adoption. A proposal does not update Gateway admission or make a domain package available to the current reference validator. HermesTrace does not become the automatic owner of all domain alignments, and sharing meanings does not widen the three-foundation InterOps requester set.

Keep enduring review and adoption records in the declared owner State and domain evidence in its existing Vault. Record implementation and performed-check progress only in the Operation root PROJECT_STATE. Implement runtime package loading and mapping only in a later selected slice with representative domain acceptance.
