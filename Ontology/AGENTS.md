# KnowledgeOS Ontology Authoring

## Definition and contents

- Treat this directory as KnowledgeOS-owned vocabulary and alignment authoring material.
- Use TERMS for stable domain vocabulary, RELATIONS for directed relation proposals, and ALIGNMENTS for purpose-bounded mapping proposals.
- Read the Operation root PROJECT_STATE before substantive changes and record evidence there.

## Preserve authoritative inputs

- Apply the existing Blueprint Markdown then blueprint YAML then Whitepaper precedence.
- Reference `../blueprint/blueprint.yaml` selectors `note_types`, `property_registry`, and `relation_registry` for existing definitions.
- Treat `../ops/policies/properties.yaml` and `../ops/policies/relations.yaml` as generated policy copies rather than separate ontology sources.
- Use `knowledgeos.domain` for new domain vocabulary while retaining existing Blueprint identifiers.
- Keep existing registries authoritative until a separately selected owner change updates their contracts.

## Author and use meanings

- Distinguish a proposed definition from an adopted executable contract or published domain package.
- Record participants, purpose, direction, exact source pins, loss, transforms, and review evidence for any future alignment.
- Require each participant's explicit adoption before treating a cross-domain mapping as operative.
- Keep canonical note evidence in the existing Vault and persistent review or adoption records in owner-controlled State.
- Preserve the current Core namespace, recipient admission, and Experience assertion scope when consulting shared definitions.
- Keep this directory free of a second machine-state source and store unrelated probes in workspace Tmp.
