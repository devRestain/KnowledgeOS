# KnowledgeOS Team methods

The authoritative offline definitions are [`ops/config/team-catalog.json`](../ops/config/team-catalog.json), [`ops/config/work-methods.json`](../ops/config/work-methods.json), the owner action policy and the single MCP capability manifest. They describe seven Teams. Each Team has one dedicated Manager. A bounded task may instead use a standalone Officer with no Manager. A reusable teammate definition confers no authority until this Operation admits an exact local executor and Profile binding.

| Team | Manager | Main method output |
| --- | --- | --- |
| Knowledge Curation | `CurationManager` | Source-bound normalization or draft proposal |
| Corpus Stewardship | `StewardshipManager` | Daily cited empty-field candidate for an owner-only provisional effect |
| Evidence Research | `ResearchManager` | Cited answer artifact |
| Relation and Ontology | `OntologyManager` | Relation or alignment proposal |
| Project Review | `ReviewManager` | Cited project review proposal |
| Knowledge Exchange | `ExchangeManager` | Gateway-admitted adaptation proposal |
| Vault Maintenance | `MaintenanceManager` | Diagnosis or recovery plan proposal |

Director admission pins the objective, method, source scope, criteria, budget, executor, Profile and any user-selected Graph. A Manager proposes immutable Graph segments only inside those bounds. The owner rechecks them for each MCP call. Producing an artifact or Pending proposal does not approve or apply it. An independent EvalOfficer assesses the exact artifact revision against admitted criteria. A failed assessment can continue inside the admitted scope and budget; a changed objective requires revised admission.

The definitions do not activate installed Team Profiles. Concrete bounded Officer, Curation Team, committed-result recovery, criterion-linked successor and quiescent control bindings are indexed in `TEAM_BINDINGS.md` and `RUNTIME.md`; use `PROJECT_STATE.md` for exact native evidence. The opt-in control route retains commands during Worker outages, applies CANCEL or one PAUSE/RESUME pair, and permits only the existing successor after resume without resetting independent gap evidence or admitted budgets. Production Team composition, external exchange and a real Obsidian GUI round trip remain separate. These paths do not establish arbitrary topology, repeated pause/resume, CUTOVER, in-flight control, combined continuation/recovery, history rollover, or Service and disk recovery.
