    C4 강화 (Enhance)

    1. 한눈에 보기#

    강화는 지금까지 Vault에 쌓인 생각을 이용해 지금 하고 있는 생각을 더 단단하게 만드는 기능입니다. 노트 하나나 질문 하나를 받아, Vault에서 읽은 근거만으로 "내가 이미 쓴 것 / 연결과 긴장 / 빈틈과 반론 / 다음 걸음"을 정리한 인용 달린 보고서를 만듭니다. 보고서는 내가 쓴 내용과 추론을 분명히 나눠서 보여 줍니다.

    강화는 Thinking Team이 맡습니다. Team은 ThinkingManager가 구성하고, retriever·connector·challenger·synthesizer 네 teammate와 독립 평가자(EvalOfficer)가 함께 일합니다. 용어는 용어를 참고하세요.

    항목 내용
    트리거Thin Client "강화"(현재 노트에서 모드 선택), 또는 Director가 강화로 해석한 자유 요청
    담당Thinking Team: ThinkingManager, retriever(코드), connector·challenger·synthesizer(모델), EvalOfficer
    결과물01_AI_Review/Reports/에 새로 만들어지는 보고서 노트 (Work 완료 뒤 TeamReview도 남음)
    사용자 결정 여부요청 자체가 사용자의 결정입니다. 보고서는 만들어진 뒤 사용자의 문서이며, 적용·거절 단계는 없습니다. 원본 노트는 바꾸지 않습니다

    세 가지 모드가 있습니다(원문은 5절에 그대로 실려 있습니다).

    모드 입력 보고서 구성
    develop (발전)아이디어·지식·질문 노트내 말로 다시 쓴 핵심(인용), 이미 써 둔 관련 내용, 연결과 긴장, 빈틈과 열린 질문, 가능한 다음 걸음
    ask (묻기)질문답, 뒷받침하는 노트, 충돌하는 노트, Vault가 다루지 않는 것
    review (돌아보기)프로젝트 노트와 해석 기간(날짜)움직인 것, 멈춘 것, 열린 결정, 다음 행동

    2. 왜 이 명세가 필요한가#

    USER_FEATURE_SPEC의 '지키는 약속' 중 이 기능이 직접 지키는 것은 다음입니다.

    • 7. 근거를 밝힙니다. 결과는 이미 쓴 노트를 정확히 인용하고 근거·추론·근거 없음을 구분합니다. 그래서 모든 주장에 cited/inference/not found 라벨이 붙고, 모든 인용이 이 Work에서 실제로 읽은 바이트로 이어져야 합니다 (ENH-1, ENH-2).
    • 1. Vault는 사용자의 것입니다. 강화는 원본 노트를 직접 바꾸지 않습니다(ENH-1). 보고서는 한 번 만들어진 뒤에는 내 문서이고, 다시 쓰이거나 덮어써지지 않습니다. 또 이전 보고서는 어떤 역할의 검색에도 나오지 않아(ENH-5) 모델이 자기 요약을 다시 근거로 삼는 일이 없습니다.
    • 개인정보 (ai_policy). 보고서는 읽은 모든 입력 중 가장 엄격한 정책을 물려받습니다(ENH-4). 자세한 값은 용어를 보세요.

    이 약속이 없다면 모델이 그럴듯하지만 근거 없는 말을 섞어 쓰거나, 쓰는 도중 내가 고친 노트와 다른 버전을 인용하거나, 이전 보고서를 다시 근거로 삼아 생각이 맴돌 수 있습니다. 기본 원칙은 운용 원칙에도 정리되어 있습니다.

    3. 어떻게 쓰는가#

    Obsidian Thin Client / 사이드바#

    1. 강화하고 싶은 노트를 엽니다. (사이드바 탭에는 마지막으로 활성이던 노트 이름이 표시되고, 탭으로 초점을 옮겨도 대상은 유지됩니다.)
    2. 사이드바에서 강화를 선택한 뒤 아래 기능 창에서 발전 / 묻기 / 돌아보기 중 하나를 고릅니다. 발전은 발전 요청을 눌러 실행합니다. 기능·모드 선택만으로는 작업을 제출하지 않습니다. 명령 팔레트·문맥 메뉴에서는 해당 명령을 바로 실행합니다.
    3. 사이드바의 묻기는 질문, 돌아보기는 기간(날짜)을 같은 영역에 입력해 제출합니다. 명령 팔레트·문맥 메뉴는 기존 입력창을 사용합니다. 노트가 없어도 묻기·자유 요청은 쓸 수 있습니다 (C11).
    4. 요청에는 노트 경로와 마지막으로 본 내용의 해시만 가고, 본문은 가지 않습니다 (SUR-1).
    5. 사이드바의 완료 상태·결과 링크 또는 명령 실행의 완료 알림을 확인한 뒤 01_AI_Review/Reports/의 보고서 노트를 엽니다. 필요하면 자유롭게 고치고 옮기고 지울 수 있고, type을 바꾸면 내 지식으로 편입됩니다. 편입 전에는 근거로 쓰이지 않습니다 (Blueprint §5.6).

    자유 요청#

    "이 아이디어를 더 발전시켜 줘"처럼 쓰면 모델 Director가 허용된 강화 명령으로 해석합니다. 해석할 수 없으면 Work가 만들어지지 않고 이유가 알려집니다 (SUR-3). Director는 기준·예산·경로를 정할 수 없습니다.

    관리 콘솔#

    작업 이력에서 해당 Work의 Graph, 역할별 호출과 모델, 평가, 남은 작업, TeamReview를 볼 수 있습니다. 진행 중인 Work는 콘솔에서 취소할 수 있습니다 (SUR-4).

    자동 경로와 CLI#

    • 자동 실행은 없습니다. 예약 작업(C7)은 C1·C2·C3·C5만 시작하므로 강화는 내가 요청할 때만 돕니다.
    • README의 CLI 목록(standardize, index, job run standardize|embed|curate|digest 등)에는 강화 명령이 없습니다. 강화는 Obsidian 쪽에서 요청합니다.

    사용 예#

    아이디어 노트 40_Knowledge/Ideas/…와 관련 노트 세 개가 있다고 합시다. 아이디어 노트에서 사이드바의 강화 → 발전을 선택하고 발전 요청을 누릅니다.

    잠시 뒤 01_AI_Review/Reports/에 보고서가 생깁니다. 핵심은 내 문장으로 인용되고, 관련 노트의 인용은 [[경로|제목]] (L3-5, 1a2b3c4d)처럼 노트 링크 뒤에 줄 범위와 짧은 해시가 붙습니다. 각 주장에는 "인용 / 추론 / 찾지 못함" 라벨이 붙습니다. 아이디어 노트는 한 바이트도 바뀌지 않습니다 (ENH-1).

    요청한 뒤 아이디어 노트를 고쳤다면 보고서는 요청 시점의 스냅샷을 인용하고, 그 사이 입력이 바뀌었음을 보고서에 밝힙니다 (ENH-3).

    4. 동작 흐름#

    강화는 Team 대상 Work이므로 공통 Work 흐름을 따릅니다. 강화에 해당하는 부분은 Manager가 retriever/connector/challenger/synthesizer 중에서 순서를 정하고, synthesizer가 항상 마지막 생산자라는 점입니다.

    참고

    평가에서 "긴장이 근거로 뒷받침되지 않는다"는 판정이 나오면 ThinkingManager가 connector와 synthesizer만 넣은 후속 구간을 한 번 구성하고, 최종 보고서는 그 후속 구간에서 나옵니다 (ENH-6). 예산(기본: Team 2구간, 생산자 호출 6회)을 넘기면 Work는 미충족으로 끝나고 보고서는 쓰이지 않습니다.

    5. 원본 명세#

    원본: docs/CAPABILITIES.md · C4 Enhance

    C4 Enhance#

    The Thinking Team uses the accumulated Vault to strengthen the user's thinking about one note or question. The output is a cited report that separates what the user already wrote from inference.

    • Trigger: Thin Client "강화" on the current note in a chosen mode, or a free-text request routed by the Director.
    • Modes:
    Mode Input Report sections
    developAn idea, knowledge or question noteCore restated in the user's own words (cited); related things already written; connections and tensions; gaps and open questions; possible next steps
    askA questionAnswer; supporting notes; conflicting notes; what the Vault does not cover
    reviewA project note and an interpretation window (dates)What moved; what stalled; open decisions; next actions
    • Team pool:
      • retriever (static): evidence candidates through C3, within the Work's policy. User-requested Work may read remote_ok and ask notes.
      • connector (model): related prior thinking, connections and tensions.
      • challenger (model): gaps, counterpoints and open questions.
      • synthesizer (model): the report.
    • Manager: ThinkingManager composes the Graph. The synthesizer is always the last producer.
    • Report: rendered by the Owner from the synthesizer submission.
      • Its language follows the source note.
      • Citations render as wikilinks with line locators and short content hashes.
      • Every claim is labeled cited, inference or not found.
      • Its inputs and inherited policy cover the focal note and every note read in the Work, not only the notes ultimately cited.
      • It states when any version of an input read in the Work differs from the current note.
    • Review window: in review mode, notes linked to the project or in its folder are selected when their creation or modification time falls in the window. It is not a task-completion filter.
    • Criteria:
      • Static: every citation handle was read in this Work; every claim is labeled; the mode's sections are present.
      • Semantic: the report addresses the focal note or question, and its stated tensions are supported by the cited notes.
    • Refuses: a deny or missing input, or a focal input for which no admitted model route satisfies its policy. A question with no readable notes completes at admission as "not covered" with no Work and no report.

    Acceptance:

    • ENH-1 Given an idea note and three related notes, when develop runs, then a report exists in 01_AI_Review/Reports/ whose every citation resolves to bytes read in this Work, and the idea note is unchanged.
    • ENH-2 Given the synthesizer submits an unlabeled, uncited claim, then the submission fails validation once, and if it fails again the Work ends unmet with no report written.
    • ENH-3 Given the user edits the idea note while the Work runs, then the report cites the snapshot and states that the input changed.
    • ENH-4 Given input notes with ai_policy: ask and remote_ok, then the report's ai_policy is ask.
    • ENH-5 Given an earlier report in 01_AI_Review/Reports/, then no role's search returns it.
    • ENH-6 Given the EvalOfficer finds the tensions unsupported, then the ThinkingManager composes one successor with connector and synthesizer addressing only that gap, and the final report comes from that successor.
    • ENH-7 Given a completed Work, then a TeamReview exists that rates each producing teammate and changes no role, catalog entry or assessment.

    7. 현재 상태와 남은 일#

    • 명세 구현: 모든 인수 예시(ENH-1~7)는 추적표에 구현 심볼과 테스트 노드가 연결되어 있습니다. 현재 전체 인수 ID 61개와 추적표 61행·171개 pytest 노드의 연결은 E_SIDEBAR_INLINE_TRACE에 기록되어 있습니다(현재 상태). 이 추적 결과 자체가 전체 테스트 재실행이나 실환경 검증을 뜻하지는 않습니다.
    • 실환경 근거: E_REAL_ROLE_SMOKE가 Obsidian에서 organize·enhance·자유 요청을 라벨 붙은 KOS smoke 노트 세 개에 실행해, director·managers·eval은 gpt-6.1-sol, teammate는 gpt-6.1-terra Hermes 세션으로 완료되고 제안 하나와 보고서 하나가 만들어졌음을 기록합니다. 이것은 합성 노트 기준 한 번의 확인입니다.
    • 별도 실환경 기록이 없는 것: PROJECT_STATE는 실제 Vault에서 ask·review 모드나 EvalOfficer 후속 구간(ENH-6)을 따로 관찰한 기록을 담고 있지 않습니다. 이 위키에서 확인할 수 있는 근거는 계약 테스트이며, 기록 부재가 실행하지 않았다는 증거는 아닙니다.
    • 열린 일: 현재 PROJECT_STATE의 인계(handoff)는 열린 정리 제안 검토, 시간별 규격화 관찰, related_min_score·related_min_probability·min_confidence 조정이며, 강화에만 해당하는 열린 항목은 기록되어 있지 않습니다. retriever가 쓰는 관련 후보는 System One 이웃 거르기를 거칩니다(C3, SRC-9). Blueprint §9의 열린 질문(기본 ai_policy가 ask로 충분한지 등)은 강화에도 간접적으로 걸려 있습니다.

    전체 진행과 후속 과제는 로드맵과 현재 상태에서 봅니다.

    8. 관련 기능#

    • C3 검색: retriever가 C3를 통해 근거 후보를 모읍니다. 보고서는 역할 검색에서 제외됩니다(ENH-5).
    • C1 정리: 같은 Team 구조(Manager+teammate)를 쓰는 다른 Team이며, 제안을 만듭니다. 강화는 보고서를 만듭니다.
    • C6 검토: 제안의 적용·거절은 C6의 일입니다. 강화 보고서는 제안이 아니어서 적용 단계가 없습니다.
    • C9 학습: TeamReview와 보고서 편집·삭제가 synthesizer 등의 피드백이 됩니다(ENH-7).
    • C11 호출 화면: 사이드바와 명령으로 강화를 요청하고, 콘솔에서 Work와 TeamReview를 봅니다.
    • C7 예약 작업: 예약 작업은 C1·C2·C3·C5만 시작하며 강화는 시작하지 않습니다.
