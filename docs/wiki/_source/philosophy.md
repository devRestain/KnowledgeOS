# 이 위키가 설명해야 하는 것

이 위키는 **설계 의도를 알고 있는 사용자가, 코드를 읽지 않고도 에이전트가 실제로 무엇을 만들었는지 이해하기 위한 문서**입니다. 명세를 쉬운 말로 반복하는 것만으로는 부족합니다. 명세가 정하지 않아 구현 과정에서 선택된 처리 순서, 역할의 입력과 출력, 실행 방식, 결과가 저장되는 위치까지 설명해야 합니다.

예를 들어 “정리는 Manager가 Graph를 만들고 평가를 거친다”에서 설명을 끝내지 않습니다. `kos-curation-manager`가 어떤 정보를 보고 팀원 순서를 고르는지, `classifier`와 `linker`가 서로 무엇을 넘기는지, 평가가 끝나야 왜 제안 파일이 생기는지까지 따라갈 수 있어야 합니다.

## 기능 페이지가 답해야 할 질문

1. **무엇을 넣고 무엇을 얻는가?** 사용자의 실제 조작과 노트 예시로 시작합니다. “정리”라면 선택한 노트와 만들어지는 제안, “강화”라면 질문과 보고서가 먼저 나와야 합니다.
2. **그 사이에 정확히 무엇이 일어나는가?** 내부 단계마다 무엇을 읽고, 무엇을 판단하거나 계산하고, 다음 단계에 무엇을 넘기는지 시간 순서로 풉니다. 함수 이름만 열거하는 것은 설명이 아닙니다.
3. **어떤 실행 경로를 쓰는가?** 실제 Hermes Profile 이름, Graph의 구성과 변경 가능 범위, Temporal의 Workflow·Activity 접점을 밝힙니다. 직접 처리하는 검색처럼 해당 연결이 없으면 없다고 씁니다.
4. **어디에 무엇이 남는가?** 원본 노트, 제안·보고서, State 기록을 구별합니다. 미리보기·접수·평가·파일 반영을 모두 “완료”라고 부르지 않습니다.
5. **다르게 흘러가는 경우는 무엇인가?** 대상이 바뀜, 근거 부족, 모델 불가, 결과 불명처럼 실제 결과를 바꾸는 분기와 사용자가 보게 될 상태를 설명합니다.

모든 페이지를 같은 소제목으로 채울 필요는 없습니다. 독자가 한 사례를 처음부터 끝까지 설명할 수 있는지가 기준입니다. 단계별 설명에는 자연스러운 문단과 번호 목록을 쓰고, 비교할 값이나 역할은 표로 정리합니다.

## 설명의 책임

**동작 설명은 현재 구현을 확인한 작성자가 책임집니다.** “원본 문서가 맞으니 코드를 보라”거나 “표가 더 최신일 수 있다”는 말로 본문의 정확성을 독자에게 떠넘기지 않습니다.

- 구현이 정한 기본값·선택 조건·저장 위치는 관련 코드와 설정을 확인하고 자연어로 설명합니다. 중요한 근거 링크는 페이지 끝에 모으되, 링크를 열지 않아도 본문이 이해되어야 합니다.
- 예시는 실제로 허용되는 경로여야 합니다. Manager가 고를 수 있는 순서의 한 사례를 모든 실행에 고정된 Graph인 것처럼 쓰지 않습니다.
- 명세의 의도, 소스로 확인한 구현, 특정 환경에서 관찰한 결과를 구분합니다. 설치했다고 모든 역할의 새 모델 경로를 실행해 본 것은 아닙니다.
- 확인하지 못한 세부 사항은 확인해 보완합니다. 도구로 확인할 수 없는 한계만 구체적으로 남기고, 추측으로 빈칸을 채우지 않습니다.
- 충돌을 발견하면 해당 원본을 바로잡습니다. 구현이 명세와 다른 경우에는 차이를 숨기거나 위키만으로 새 동작을 정당화하지 않습니다.

## 같은 설명을 반복하지 않는 방법

공통 구조는 [[architecture]], 용어는 [[glossary]], 실행·설치 근거는 [[status]], 남은 일은 [[roadmap]]이 맡습니다. 기능 페이지는 그 기능에 필요한 연결만 짚고 자세한 공통 설명으로 링크합니다.

특히 “사용자 소유”, “책임 분리”, “독립 평가” 같은 원칙을 기능마다 다시 선언하지 않습니다. 대신 그 원칙이 **이 기능의 어떤 처리로 구현되는지** 씁니다. “원본을 보호한다”보다 “평가 뒤에도 원본은 쓰지 않고 `01_AI_Review/Proposals/`에 변경 체크리스트를 만든다”가 필요한 설명입니다.

영문 명세 전체, 일반 Work 흐름도, 과거 검증 숫자를 본문마다 붙이지 않습니다. 인수 ID와 구현·테스트 연결은 기능 페이지 끝의 참고 표로 유지하고, 자세한 규칙은 명세 링크로 찾아가게 합니다.

## 어떤 자료를 확인하는가

| 알고 싶은 사실 | 확인할 자료 |
|---|---|
| 사용자에게 제공해야 하는 동작 | 최상위 [기능 명세](../CAPABILITIES.md), [사용자 의도](../../USER_FEATURE_SPEC.md), [시스템 제약](../../OBSIDIAN_VAULT_BLUEPRINT.md) |
| 실제 처리 순서와 분기 | `src/knowledgeos/`의 기능 처리기·Owner·실행 엔진 |
| 팀원 풀·평가 기준·모델·예약 시각 | `config/capabilities/`, `config/roles.json`, `config/jobs.json` |
| 역할이 받는 지침과 실제 도구 연결 | `roles/`, `roles.py`, `hermes.py` |
| 설치·실행·장치에서 확인한 범위 | [PROJECT_STATE.md](../../PROJECT_STATE.md) |
| 어떤 인수 예시가 어디에 연결되는가 | [기능 추적표](../CAPABILITY_TRACE.md) |

명세는 목표 동작의 기준이고 코드는 구현 사실의 근거입니다. 코드를 읽었다는 이유로 명세의 성공 기준을 낮추지 않습니다. 위키는 둘의 대응을 이해시키는 문서이지, 어느 쪽도 대신하는 새 계약이 아닙니다.

## 원고를 고치고 배포본을 만드는 방법

설명은 `docs/wiki/_source/*.md`에서만 고칩니다. 생성된 HTML과 `assets/`는 직접 편집하지 않습니다. 변경한 기능의 실제 흐름을 확인해 원고를 고친 뒤 다음을 수행합니다.

1. 필요한 명세·추적표와 `PROJECT_STATE.md`의 관련 사실을 맞춥니다. 동작을 바꾸지 않은 집필 작업 때문에 무관한 규칙이나 과거 증거를 다시 쓰지는 않습니다.
2. `make wiki`로 정적 HTML을 생성합니다.
3. `make wiki-check`로 인수 ID·상태 기록 누락, 깨진 링크, 원격 자원 로딩, 생성 결과의 낡음을 검사합니다.
4. 브라우저에서 본문을 읽고 탐색·검색·좁은 화면을 확인합니다. 자동 검사는 문장이 이해되는지, 실행 순서를 정확히 설명했는지 대신 판정하지 못합니다.

위키를 갱신하는 일 자체는 Owner 재시작, Profile 재설치, Vault 수정, 외부 전송을 요구하지 않습니다.

### 원고 문법

기본 Markdown의 제목·문단·목록·표·링크를 씁니다. `[[c1]]`은 기능 페이지, `[[ORG-1]]`은 해당 인수 예시로 연결됩니다. 표 안에서는 표시 글을 바꾸는 `|` 포함 위키 링크를 쓰지 않습니다.

`{{acceptance:C1}}`은 인수 연결 표, `{{state:evidence}}` 같은 지시문은 상태 기록을 생성합니다. 이들은 확인용 자료이며 본문 설명을 대신하지 않습니다. 코드 블록의 Mermaid는 그림으로 변환되지 않으므로, 기존 생성 그림이나 읽기 쉬운 단계 설명을 사용합니다.

## 휴대폰과 정적 배포

좁은 화면에서는 메뉴 버튼으로 목차를 열고 검색창으로 전체 위키를 찾습니다. 넓은 표와 코드는 해당 영역 안에서 좌우로 움직이며, 그림은 **그림 크게 보기 / 그림 전체 보기**로 전환합니다.

현재 HTML은 정적 문서입니다. 휴대폰 접속을 새로 설정한 것은 아닙니다. 집 밖에서 읽는 구성으로는 **위키 파일만 제공하는 별도 loopback 정적 서버 + 비공개 Tailscale Serve HTTPS**를 제안합니다. 본인 기기만 접근하도록 제한하고 Owner·관리 API는 연결하지 않습니다. [Serve 공식 안내](https://tailscale.com/kb/1312/serve)의 tailnet 내부 공유와 공개용 Funnel은 다릅니다.

오프라인으로 복사할 때는 HTML과 `assets/`를 함께 옮깁니다. 위키 밖 저장소 파일을 가리키는 근거 링크는 그 파일도 함께 제공해야 열립니다. 링크를 살리려고 저장소 전체를 웹에 노출하지 않습니다. 검색 색인에도 본문이 들어 있으므로 공개 배포에는 별도 내용 선별이 필요합니다.
