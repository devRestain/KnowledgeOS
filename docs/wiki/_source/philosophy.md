# 위키·명세 운용 원칙

이 페이지는 두 가지를 설명합니다. **KnowledgeOS의 명세는 어떤 규칙으로 관리되는가**, 그리고 **이 위키는 왜 있고, 개발 세션마다 어떻게 갱신하는가**입니다.

## 왜 위키가 있나

KnowledgeOS의 사실은 여섯 개 문서에 나뉘어 있습니다. 동작 기준, 사용자 의도, 시스템 제약, 추적표, 진행 상태, 실행 방법입니다. 각각은 정확하지만 한 문서만 읽어서는 "이 기능이 왜 있고, 어떻게 쓰고, 어디까지 되고, 무엇이 남았는지"를 알기 어렵습니다.

위키는 그 사실들을 **기능 단위로 다시 엮어** 한곳에서 읽게 해 주는 해설판입니다.

- 규칙을 새로 만들지 않습니다. 동작·상태에 관한 문장은 원본 문서에서 온 것입니다.
- 원본에 없는 내용은 해설로 쓰더라도 "해석" 또는 "기록 없음"으로 표시합니다.
- 위키와 원본이 어긋나면 **원본이 맞고**, 위키는 다시 생성해서 바로잡습니다.

## 여섯 개의 원본 문서

| 문서 | 맡은 역할 | 두지 않는 것 |
|---|---|---|
| `docs/CAPABILITIES.md` | **최상위** 동작·인수 기준. 기능별 동작과 인수 시나리오, 구현 순서 | 이력, 증거, 설치 상태 |
| `USER_FEATURE_SPEC.md` | 사용자의 **의도**: 지키는 약속, 다섯 기능, 사용 흐름 | 기능이나 인수 범위를 줄이는 내용 |
| `OBSIDIAN_VAULT_BLUEPRINT.md` | **시스템 제약**: 화면 분담, 역할 조직, Vault 계약, 효과 규칙, Core 준수 | 이력, 증거, 설치 상태 |
| `docs/CAPABILITY_TRACE.md` | 인수 ID마다 구현 `file::symbol`과 pytest 노드를 잇는 **지도** | 통과 여부·배포 보고 |
| `PROJECT_STATE.md` | 진행과 검증 **증거**의 유일한 기계 판독 원본 | 명세 |
| `README.md` | 구성, 실행 명령, 검증 범위 | 명세의 대체 |

> [!note]
> 추적표는 "어떤 테스트가 어떤 시나리오를 확인하려고 있는가"를 보여 주는 지도이지, 테스트가 통과했다거나 실제 환경에 배포했다는 보고가 아닙니다. 통과·배포 근거는 `PROJECT_STATE.md`의 증거 기록에만 있습니다([[status]]).

## 명세는 어떻게 관리되나 (Blueprint §0)

아래는 Blueprint §0 "Spec governance"의 원문입니다. 쉬운 말로는 이렇습니다.

- 명세는 **지금 맞는 것만** 적습니다. 과거·증거·설치 상태는 Git과 PROJECT_STATE에 둡니다.
- 동작을 바꾸는 변경은 **같은 변경 안에서** 명세도 고칩니다. 낡은 문장은 "폐기됨" 표시를 달지 않고 **지웁니다**.
- 인수 시나리오(예: `[[ORG-1]]`)가 곧 실행 가능한 테스트이며, 시나리오를 지우거나 성공 기준을 약하게 하지 않습니다.
- 기능 하나를 얇게 끝까지 만들어 써 보고, 배운 것으로 명세를 고칩니다.
- 아직 정하지 않은 것은 Blueprint §9의 열린 질문에 둡니다. 구현이 이미 답한 질문은 지웁니다([[roadmap]]).
- **명세와 위키는 함께 움직입니다.** 위키를 쓰거나 다시 생성하다 문서끼리 어긋나는 곳을 발견하면 위키에 경고를 남기지 않고, **같은 세션에서 우선순위가 낮은 문서를 고칩니다.** 위키 갱신은 곧 주기적인 명세 점검입니다.

## 위키의 구성: 생성되는 것과 직접 쓰는 것

| 종류 | 예 | 원본 | 고치는 방법 |
|---|---|---|---|
| **원문 블록** | 기능 페이지의 영문 명세, Blueprint 절, 사용자 기능 명세 절 | `docs/CAPABILITIES.md` 등 원본 문서 | 원본을 고치고 위키 재생성 |
| **인수 표** | 인수 ID, 예시, 구현 위치, 테스트 노드 | `docs/CAPABILITIES.md`, `docs/CAPABILITY_TRACE.md` | 원본을 고치고 재생성 |
| **상태 표** | 목표·결정·인수·증거·막힘·인계 | `PROJECT_STATE.md` | PROJECT_STATE를 고치고 재생성 |
| **그림(SVG)** | 시스템 지도, 기능 지도, 작업 흐름, 정책 표, 현황 요약 | 생성기가 원본에서 만듦 | 원본을 고치고 재생성 |
| **해설 문장** | 이 페이지처럼 사람이 쓴 설명 | `docs/wiki/_source/<페이지>.md` | 직접 수정 후 재생성 |
| **생성 결과** | `docs/wiki/*.html`, `docs/wiki/assets/` | 위 모든 것 | **손으로 고치지 않음** |

생성 결과는 시각·난수·환경에 따라 바뀌는 값을 넣지 않아서, 같은 원본이면 항상 같은 바이트가 나옵니다. 아래 목록은 이 위키가 읽은 원본 문서와 그 digest(sha256)입니다. 위키가 어느 판의 원본에서 만들어졌는지 확인할 때 씁니다.

### 원고에 쓰는 문법

해설 문장은 Markdown의 일부(제목, 목록, 표, 코드 블록, 인용, 굵게·기울임·코드, 링크)와 아래 규칙만 씁니다.

```
[[slug]]              페이지 링크 (예: usage, c4)
[[slug|표시할 글]]     표시 글을 바꾼 링크 (표 안에서는 | 때문에 쓰지 않음)
[[ORG-1]]             인수 ID가 있는 기능 페이지의 그 위치로 링크
> [!note] 제목        설명 상자 (note, tip, warning, status)
```

원본에서 가져오는 블록은 한 줄에 하나씩 쓰는 지시문입니다. 원문 포함(`include`), 인수 표(`acceptance`), 상태 표(`state`), 그림(`svg`), 원본 목록(`sources`)이 있고, 존재하지 않는 대상을 가리키면 생성이 실패합니다.

## 개발 세션마다 위키를 갱신하는 방법

위키는 코드·명세와 함께 움직입니다. **모든 개발 세션**은 바뀐 범위에 맞춰 원본 문서와 위키 설명을 함께 갱신하고, 끝내기 전에 아래를 순서대로 합니다. 명세·추적표·`PROJECT_STATE.md`를 바꾼 세션에만 한정하지 않습니다. 이 절차는 저장소의 `AGENTS.md`와 `README.md`, Blueprint §0에도 같은 내용으로 적혀 있습니다.

1. **원본을 고칩니다.**
   - 동작·인수 기준이 바뀌었다면 `docs/CAPABILITIES.md`를 같은 변경 안에서 고칩니다. 필요하면 `USER_FEATURE_SPEC.md`(의도), Blueprint(시스템 제약)도 함께 고칩니다. 낡은 문장은 지웁니다.
   - 인수 시나리오를 더하거나 바꿨다면 테스트와 `docs/CAPABILITY_TRACE.md`의 행도 맞춥니다.
   - 진행·검증 결과는 `PROJECT_STATE.md`에만 기록합니다. 증거에는 종류(class)와 결과를 적고, 돌리지 않은 것은 정확히 "돌리지 않음"으로 둡니다.
2. **해설을 고칩니다.** 쓰는 법·용어·설명이 달라졌다면 `docs/wiki/_source/`의 해당 페이지를 고칩니다. 새 용어는 [[glossary]]에 더합니다. 설명 문장은 여기에서만 고칩니다.
3. **`make wiki`** 로 위키를 다시 생성합니다.
4. **`make wiki-check`** 로 검사합니다. 이 검사는 아래 중 하나라도 해당하면 실패합니다.
   - 명세의 C1~C11이나 인수 ID가 생성 결과에 빠졌다.
   - PROJECT_STATE의 목표·인수·막힘·인계 기록이 빠졌다.
   - 내부 링크나 앵커가 풀리지 않거나, 원고의 위키 링크가 없는 페이지·ID를 가리킨다.
   - 어떤 출력이든 원격 자원(`src=`, `<link href>`, CSS `url()`·`@import`의 스킴, `fetch(`·XHR의 http 호출)을 불러온다.
   - 다시 생성하면 바이트가 달라진다. 즉 생성 파일이 낡았다.
5. **바뀐 페이지를 브라우저로 확인합니다.** `docs/wiki/index.html`을 열어 바뀐 페이지, 표·그림, 링크, 사이드바, 검색 상자를 눈으로 봅니다. 자동 검사는 링크가 풀리는지를 보지만 읽기 편한지, 내용이 서로 맞는지는 알려 주지 않습니다.
6. **발견한 어긋남을 같은 세션에서 고칩니다.** 5단계에서 문서끼리 맞지 않는 곳이 보이면(아래 "명세 점검" 참고) 위키에 경고만 남기지 말고 원본을 고치고 3~5단계를 다시 합니다.
7. **생성 결과를 원본과 같은 변경에 담습니다.** 생성된 HTML과 assets는 저장소에 포함됩니다.

상태·추적표 검사(`make state-check`, `make trace-check`)는 위키와 별개로 각각 돌립니다.

### 명세 점검: 위키를 갱신하며 함께 보는 것

위키를 갱신하는 일은 명세를 한 번 훑어 읽는 기회입니다. 아래를 살펴보고, 어긋나면 **우선순위가 낮은 쪽을 고칩니다.**

| 살펴볼 것 | 예 | 고치는 쪽 |
|---|---|---|
| 같은 사실을 다르게 적은 곳 | 기능 명세와 Blueprint의 기본값·이름이 다름 | 우선순위가 낮은 문서(Blueprint·사용자 기능 명세) |
| 구현이 이미 답한 열린 질문 | Blueprint §9에 남아 있는데 기능 명세와 증거에 값이 있음 | Blueprint §9에서 그 질문을 지움 |
| 증거가 명세에 새어 든 곳 | 명세에 설치 상태·관찰 버전이 적혀 있음 | 명세에서 지우고 `PROJECT_STATE.md`에 기록 |
| 상태가 현실과 다른 곳 | 인수 기록이 오래됨, 막힘이 풀렸는데 남아 있음 | `PROJECT_STATE.md` |

우선순위: 동작·인수 기준에 대해서는 `docs/CAPABILITIES.md`가 가장 높고, 사용자 기능 명세와 Blueprint가 그것을 보충합니다. 최상위 문서의 내용 자체가 틀렸다고 판단되면 그것은 사용자가 지정한 문서를 바꾸는 일이므로 [해석] 임의로 고치지 말고 세션 보고에 남깁니다.

### 무엇이 바뀌면 어디를 고치나

| 무엇이 바뀌었나 | 고칠 곳 | 위키에 반영되는 곳 |
|---|---|---|
| 기능의 동작·인수 기준 | `docs/CAPABILITIES.md`(+ 필요 시 USER·Blueprint), 테스트, 추적표 | 기능 페이지의 원문·인수 표 |
| 검증 결과·막힘·인계 | `PROJECT_STATE.md` | [[status]], [[roadmap]], 각 기능의 "현재 상태" |
| 쓰는 방법 | `README.md` 또는 `_source/usage.md` | [[usage]] |
| 새 용어 | `_source/glossary.md` | [[glossary]] |
| 구조 설명 | Blueprint 또는 `_source/architecture.md` | [[architecture]] |
| 구현이 답한 열린 질문 | Blueprint §9에서 삭제 | [[roadmap]]의 열린 질문 |

> [!warning]
> 위키를 갱신한다고 Obsidian GUI·플러그인·Hermes·State·실행 중인 Owner를 건드리지 않습니다. 위키는 원본 문서를 읽어 정적 HTML을 만들 뿐입니다. 그런 작업은 별도의 명시적 승인이 있어야 합니다.
