# C5 문서 관리

## 한눈에 보기

문서 관리는 Vault가 건강한지 살피고 *지금 사용자가 눈여겨봐야 할 것*을 골라 보여 주는 기능입니다. 담당은 **StewardshipOfficer**이며, 결정적 규칙(static code)으로 움직이는 Owner 코드입니다. 다만 System One이 설정되어 있으면 생활주기 제안에 한해 상태 변경이 필요한지를 System One에게 확률로 묻습니다. 이 기능이 **쓰는 것은 보관 같은 생활주기 제안(lifecycle proposal)뿐**이고, 노트를 만들거나 옮기거나 지우는 일은 하지 않습니다. System One이 판단해도 노트 자체는 절대 바뀌지 않으며, 결과는 늘 사용자가 결정하는 제안입니다.

주의가 필요한 것은 두 곳에 나뉘어 나타납니다. Obsidian Bases로 표현할 수 있는 것(오래된 포착, 오래 안 본 아이디어 등)은 Bases 화면에, Bases로 표현할 수 없는 것(중복 ID, 충돌 표시, 결과 불명 등)은 관리 콘솔과 Discord 요약에 *계산된 주의 항목*으로 나타납니다. 주의 항목은 노트로 저장되지 않습니다.

| 항목 | 내용 |
|---|---|
| 트리거 | Bases 화면은 Vault를 열어 볼 때 항상 보입니다. 주의 항목 계산은 예약 작업 `digest`(매일 08:00, [[C7]])가 시작하며, 콘솔에서도 볼 수 있습니다. 보관 제안도 같은 계산에서 만들어집니다. |
| 담당 | StewardshipOfficer(static; 설정 시 System One에게 상태 판단 질문)와 EvalOfficer(static) |
| 결과물 | Bases 화면, 콘솔·요약의 주의 항목, 보관 등 생활주기 제안 노트(`01_AI_Review/Proposals/`) |
| 사용자 결정 여부 | 제안은 사용자가 [[C6]]에서 적용하거나 거절합니다. 주의 항목은 알림일 뿐 자동으로 바꾸는 것이 없습니다. |

## 왜 이 명세가 필요한가

[USER_FEATURE_SPEC](../../USER_FEATURE_SPEC.md)의 '지키는 약속' 중 이 기능이 지키는 것은 세 가지입니다.

1. **Vault는 사용자의 것입니다.** 노트 생성·이동·이름 변경·삭제는 계속 Obsidian에서 사용자가 합니다. KnowledgeOS가 이를 대신하지 않으므로 Vault를 마음대로 쓰고 옮겨도 시스템이 깨지지 않습니다. 이동은 ID로 따라가고, 지워진 대상의 제안은 낡은(stale) 것으로 취급합니다.
2. **자동으로 바꾸는 것은 작고 기계적인 것뿐입니다.** 판단이 필요한 보관·상태 결정은 직접 바꾸지 않고 제안으로 만들며, 적용은 사용자가 정합니다. System One이 낸 상태 제안도 예외가 아닙니다. 이 운용 방식은 [[philosophy]]에서 다룹니다.
3. **근거를 밝힙니다.** 어느 노트가 왜 주의 항목인지(예: 같은 `id`를 가진 두 노트의 경로) 이름을 들어 보여 줍니다.

이 기능이 없으면 처리하지 않은 포착, 방치된 아이디어, 깨진 YAML이나 충돌 표시가 있는 노트, `confidential`인데 `ai_policy`가 느슨한 노트가 눈에 띄지 않은 채 쌓입니다. 자동화는 그런 노트를 건너뛰기만 하므로, 사용자에게 알려 주는 일은 이 기능이 맡습니다. 용어는 [[glossary]]의 *제안(Proposal)*, *주의 항목(attention item)*, `ai_policy`를 참고하세요.

## 어떻게 쓰는가

문서 관리에는 전용 Thin Client 명령이 없습니다. 노트를 관리하는 일은 Obsidian이, 알림은 콘솔과 Discord가, 제안 결정은 [[C6]]의 적용·거절이 맡습니다(C5 명세, [[C11]]).

**Obsidian Bases 화면** — `99_System/Bases/`에 있는 Vault 자산이며 아래 목록을 보여 줍니다.

- 3일 넘게 처리되지 않은 포착
- 30일 넘게 손대지 않은 아이디어
- 열린 질문
- 대기 중인 제안
- 14일 넘게 손대지 않은 보고서
- 상태별 프로젝트

**관리 콘솔(브라우저, 로컬 전용)**

1. 콘솔을 엽니다([[C11]], Blueprint §3.2).
2. 'Bases로 볼 수 없는 주의 항목'에서 다음을 확인합니다.
   - 중복 ID, 충돌 표시, 깨진 YAML
   - `confidential` 노트인데 더 느슨한 `ai_policy`
   - 낡은 제안
   - 최근 자동 변경(autofix)
   - 결과 불명 효과, 실패하거나 막힌 예약 작업
3. 결과 불명 항목은 콘솔의 확인 기록 기능으로 사람이 관찰한 결과를 남깁니다(과거 기록은 고치지 않습니다).

**Discord 요약** — 매일 08:00 요약에 대기 중인 제안·보고서, 낡은 제안, 결정이 필요한 주의 항목, 다시 볼 아이디어와 열린 질문이 담깁니다([[C8]]). 본문 없이 제목과 링크만 가며, `deny`·`local_only`·`confidential` 노트는 제목도 넣지 않습니다.

**CLI**

- `knowledgeos vault-check`로 깨진 YAML, 충돌 표시, 중복 ID를 점검합니다(README, Blueprint §3.3).
- `knowledgeos job run digest`로 요약 작업을 직접 실행하고 영수증까지 확인합니다.

**보관 제안 받기** — 프로젝트를 `done`으로, 아이디어를 `dropped`로 바꾸면 해당 노트를 `archived`로 바꾸고 `90_Archive/`로 옮기자는 제안이 만들어집니다.

> [!tip] 작업 예시
> 월요일에 프로젝트 노트 하나의 `status`를 `done`으로 바꿉니다. 다음 `digest` 계산에서 StewardshipOfficer가 이 노트에 대한 보관 제안을 `01_AI_Review/Proposals/`에 하나 만듭니다([[DOC-4]]). 같은 노트에 제안은 사용자가 결정할 때까지 정확히 하나뿐이며, 요약에는 '검토 대기'로 한 번 집계됩니다. 제안 노트를 열어 체크리스트와 diff를 보고 **적용**하면 [[C6]]에 따라 대상이 그 사이 바뀌지 않았을 때만 반영되고, **거절**하면 제안 파일이 지워집니다. 마음에 들지 않으면 아무것도 하지 않아도 됩니다. 그 사이 대상이 바뀌어도 열린 제안이 Owner가 쓴 그대로이면 같은 자리에서 다시 만들어지고, 사용자가 고친 제안은 덮어쓰거나 중복 생성하지 않습니다([[C6]] 보존 규칙).

**System One 상태 제안 (설정 시)** — 같은 `digest` 계산이 후보 노트마다 질문 하나(predicate)를 System One에게 보내, 확률이 `min_confidence`(기본 0.7) 이상일 때만 상태 변경을 제안합니다([[DOC-5]]).

| 노트 | System One에게 묻는 것 | 제안하는 변경 |
|---|---|---|
| `open` 질문 | 본문이 이미 답을 담고 있는가 | `status: answered` |
| `planned`·`active`·`paused` 프로젝트 | 끝났다고 스스로 밝히는가 | `status: done` |
| `seed`·`developing`·`mature` 아이디어 | 작성자가 포기했는가 | `status: dropped` |

각 제안은 일반 단일 대상 생활주기 제안이고, 체크리스트 항목에 System One과 확률이 적힙니다. 사용자는 [[C6]]에서 평소처럼 적용·거절합니다. `remote_ok` 노트만 보내며(예약 출처), `deny`·충돌 표시·ID 중복·시스템·검토 노트는 보내지 않습니다. 이미 열린 제안이나 낡은 제안이 있는 대상은 묻지도 제안하지도 않습니다. 내용이 바뀌지 않은 노트는 다시 묻지 않고(State `lifecycle_seen`), 호출이 실패하면 기록하지 않으므로 다음 실행에서 다시 묻습니다. System One이 꺼져 있으면 정적 제안만으로 요약이 완성됩니다.

## 동작 흐름

이 기능에 맞는 계약의 이름 있는 도식은 없어, 짧은 흐름으로 정리합니다.

1. `digest` 작업이 시작됩니다. 모든 요청과 마찬가지로 Director가 정적 코드로 접수합니다([[C7]]).
2. StewardshipOfficer가 Vault를 읽어 주의 항목을 계산합니다. 충돌 표시가 있는 노트는 모든 자동화가 건너뜁니다([[DOC-3]]).
3. 정적 규칙으로 생활주기 제안을 만듭니다. System One이 설정되어 있으면 후보 노트에 상태 질문을 보내 기준을 넘는 답도 같은 제안 형식으로 더합니다. 같은 노트에 열린 제안이 있으면 새로 만들지 않습니다.
4. 정적 EvalOfficer가 결과를 독립적으로 평가합니다.
5. 같은 계산이 [[C8]] 요약의 내용이 되고, 충돌·결과 불명·작업 실패는 즉시 알림으로도 나갑니다.
6. 사용자가 [[C6]]에서 제안을 결정하거나, Bases 화면에서 노트를 고쳐 항목을 사라지게 합니다([[DOC-1]]).

> [!note]
> 주의 항목은 어디에도 파일로 저장되지 않고 현재 Vault와 State로 그때그때 계산됩니다. 그래서 노트를 고치면 다음 계산에서 저절로 사라집니다.

## 현재 상태와 남은 일

- **명세 대비 구현**: DOC-1부터 DOC-5까지 모두 추적표에 구현 위치와 테스트 노드가 있습니다. `PROJECT_STATE.md`는 현재 전체 68개 인수 예시·68행·195개 pytest 노드의 연결(`E_SYSTEM_ONE_TRACE`)과 277개 전체 테스트 통과(`E_SYSTEM_ONE_TESTS`)를 기록합니다. 테스트의 스크립트 대역·합성 Vault 근거를 실환경 관찰로 보아서는 안 됩니다([[status]]). DOC-5의 System One 응답은 loopback 가짜 Decisions API입니다.
- **실환경 근거**: 이 기능에 직접 연결된 기록은 두 가지입니다. 하나는 실제 Vault 설정 정리 후 `vault-check`가 깨진 YAML을 보고하지 않았다는 기록(E_VAULT_CONFIG_CLEANUP)이고, 다른 하나는 요약 알림이 실제 Discord에 전달되었다는 기록(E_DISCORD_DELIVERED, [[C8]])입니다.
- **확인되지 않은 것**: `PROJECT_STATE.md`에는 실제 Obsidian에서 Bases 여섯 화면을 관찰한 기록이나, 자연 스케줄(매일 08:00 `digest`)로 실행된 요약과 실제 보관 제안을 관찰한 기록이 없습니다. System One 상태 제안(DOC-5)도 실제 Owner·실제 노트에서 관찰한 기록이 없으며, `E_SYSTEM_ONE_LIVE`의 실제 호출은 규격화·자유 요청·관련 노트에 대한 것입니다. 열린 인계 항목(handoff)에는 `min_confidence` 조정이 들어 있으므로 이 기능의 기준값도 실제 노트로 보정할 시작값입니다.
- **열린 질문**: Blueprint §9는 문서 관리 화면에 핵심 Bases로 충분한지, 추가 커뮤니티 plugin이 필요한지를 아직 정하지 않은 질문으로 둡니다. 요약 주기(C7 기본값)가 실제 사용과 맞는지도 열린 질문입니다.
- **모바일**: 후속 과제 M3(GitHub Actions)가 push 시 YAML·충돌 표시·중복 ID 같은 결정적 점검을 맡을 후보로 적혀 있으나 아직 구현 전입니다. 자세한 것은 [[roadmap]]에서 봅니다.

## 관련 기능

- [[C1]] 정리: 중복 ID처럼 모호한 ID를 대상으로 한 정리 요청은 거절됩니다([[DOC-2]]).
- [[C2]] 규격화: 충돌 표시·깨진 YAML·중복 ID 노트는 건드리지 않고 건너뜁니다([[DOC-3]]). 최근 자동 변경은 주의 항목으로 집계됩니다.
- [[C3]] 검색: 같은 `id`를 가진 두 노트도 모두 검색 대상으로 남습니다.
- [[C6]] 리뷰: 보관 제안을 적용·거절하고, 낡은 제안은 7일 뒤 삭제됩니다.
- [[C7]] 예약 작업: `digest` 작업이 이 기능의 계산을 시작하고, 실패하거나 놓친 작업이 주의 항목이 됩니다.
- [[C8]] 알림: 요약과 즉시 알림의 내용을 이 기능이 구성합니다.
- [[C11]] 호출·관리 화면: 콘솔이 주의 항목을 보여 주고 결과 불명 확인 기록을 받습니다.
