# C4 강화 (Enhance)

**강화**는 Vault에 이미 쌓여 있는 노트들을 근거로 삼아 지금 다루는 생각·질문·프로젝트를 더 단단하게 정리한 **인용 보고서**를 `01_AI_Review/Reports/`에 새로 만드는 기능입니다. Thinking Team이 맡으며, 원본 노트는 건드리지 않고 내가 이미 쓴 근거(`인용`), 모델의 생각(`추론`), Vault가 다루지 않는 영역(`찾지 못함`)을 문장마다 분명히 나눠 적습니다. 공통 실행 구조·역할별 모델 경로·보안 경계는 [[architecture]]를, 용어는 [[glossary]]를 참고하세요.

## 세 가지 모드: 발전 · 묻기 · 돌아보기

강화는 Obsidian 사이드바·명령 팔레트·문맥 메뉴에서 직접 고르는 정형 요청(`enhance`)이나 자유 요청(`free_text`)으로만 시작하며, 예약 작업이나 CLI 실행 경로는 없습니다.

- **정형 요청**: 클라이언트는 노트 본문 대신 경로·마지막으로 본 파일 해시·질문·기간만 보냅니다([[SUR-1]]). 모델 Director를 부르지 않고 코드가 바로 접수합니다.
- **자유 요청**: "이 아이디어의 반론을 찾아 발전시켜 줘"처럼 보내면, System One이 설정된 경우 먼저 무관한 요청을 거른 뒤 `kos-director` 모델이 정형 `enhance` 요청 초안으로 바꿔 같은 접수 검사를 통과시킵니다([[SUR-3]]).

세 모드는 같은 팀을 쓰지만 **필수 입력, 접수 단계의 분기, `retriever`의 후보 수집, 평가 기준, 보고서 절과 언어 판별**이 코드에서 뚜렷하게 갈립니다.

| 구분 | `develop` (발전) | `ask` (묻기) | `review` (돌아보기) |
|---|---|---|---|
| 입력 | 노트 1개(아이디어·지식·질문 등) | 질문(선택적으로 질문 노트 1개 첨부) | `type: project` 노트 1개 + 해석 기간(`from`~`to`) |
| 접수 시 분기 | `deny`·오류·충돌·중복 ID·`report`·`proposal` 거절 | **노트 없이 질문만 보냈는데 일치하는 공개 노트가 0건이면 Work·Temporal·모델 없이 즉시 "다루지 않음"으로 완료** | 프로젝트 노트가 아니거나 날짜 형식이 잘못됐거나 시작일이 종료일보다 늦으면 즉시 거절 |
| `retriever` 후보 수집 (최대 8개) | 대상 노트 + 관련 노트(System One 이웃 거름 포함) + **제목** 키워드 | 노트가 있으면 관련 노트(이웃 거름 포함) + **질문** 키워드, 없으면 **질문** 키워드만 | 관련 노트(최대 100개, **이웃 거름 미사용**) + **프로젝트 폴더 하위 노트** 중 수정일 또는 `created`가 기간 안인 것만 최신순으로 추림 |
| 평가 기준 | 5개 (읽은 인용, 주장 라벨, 절 구성, 초점 충족, **긴장 근거**) | 5개 (읽은 인용, 주장 라벨, 절 구성, 초점 충족, **긴장 근거**) | **4개** (긴장 근거 기준 제외) |
| 보고서 언어와 절 | 대상 노트 언어 기준 5절: 핵심·이미 쓴 관련 생각·연결과 긴장·빈틈과 열린 질문·다음 걸음 | 질문 언어 기준 4절: 답·뒷받침하는 노트·상충하는 노트·Vault가 다루지 않는 것 | 프로젝트 노트 언어 기준 4절: 움직인 것·멈춘 것·열린 결정·다음 행동 |

> [!note] `review`의 해석 기간은 할 일 완료 필터가 아닙니다
> 시작일과 종료일은 서울 시간 기준 하루의 시작과 끝으로 적용됩니다. 그 기간에 새로 만들었거나(`created`) 수정한(`mtime`) 프로젝트 관련 노트를 추려, 해당 기간 동안 프로젝트에서 무엇이 움직이고 멈췄는지 해석하는 범위입니다.

접수가 통과해 Work가 만들어지면 Owner는 대상 노트의 정확한 바이트를 스냅숏으로 고정합니다.

## Thinking Team 구성과 역할별 실제 작업

모델별 실제 경로와 추론 설정(`config/roles.json`)은 [[architecture]]에서 확인하세요.

| 역할과 Hermes Profile | 맡는 일 | 넘기는 결과 |
|---|---|---|
| ThinkingManager (`kos-thinking-manager`) | 노트 본문을 읽지 않고 모드·예산·미충족 기준에 따라 팀원 순서를 편성, 완료 후 TeamReview 작성 | 구간 Graph 제안, 완료 후 팀원 평점과 조언 제안(최대 3개) |
| `retriever` (Hermes profile 없음 · 코드) | 모드별 규칙에 따라 대상 노트와 관련 후보(최대 8개)를 정적으로 수집 | 미리 읽은 대상·후보의 근거 핸들과 짧은 발췌 |
| `connector` (`kos-connector`) | 이미 써 둔 관련 생각, 서로 이어지는 연결, 서로 부딪히는 긴장을 도출 | 근거 핸들이 붙은 관련·연결·긴장 주장 목록 |
| `challenger` (`kos-challenger`) | 가정의 빈틈, Vault 안의 반론, 다시 물을 열린 질문을 도출 | 근거 핸들이 붙은 빈틈·반론·열린 질문 목록 |
| `synthesizer` (`kos-synthesizer`, 항상 마지막) | 앞선 인계물과 자신이 읽은 노트를 종합해 모드별 전체 보고서를 작성 | 모든 절과 `인용`/`추론`/`찾지 못함` 라벨이 붙은 보고서 |
| EvalOfficer (`kos-eval`) | Manager 설명이나 팀원 자기평가 없이 정적 검사 결과와 인용 발췌만 보고 독립 평가 | 초점 충족 및(모드별) 긴장 근거 판정 |

아이디어 노트에서 **발전**을 누르거나 질문을 입력해 **묻기**를 시작하면 팀 안에서는 다음 순서로 근거와 해석이 쌓입니다.

### 1. `retriever`의 근거 수집과 이전 보고서 차단 (코드 실행)

`retriever`는 모델 없이 Owner 코드로 돕니다. 대상 노트 스냅숏과 모드별 기준에 맞는 후보(최대 8개)를 조각(최대 40줄, frontmatter 제외)으로 나눠 근거 핸들(`e1`, `e2` 등)을 붙이고 미리 읽음 상태로 등록합니다.

- `develop`은 대상 노트의 관련 노트(System One 이웃 거름 포함)와 제목 키워드로 후보를 모읍니다.
- `ask`는 질문에서 한글 조사와 불용어를 떼어 낸 키워드로 후보를 찾고, 질문 노트가 함께 주어졌을 때만 관련 노트까지 합칩니다.
- `review`는 프로젝트 노트의 관련 노트(이웃 거름 없이 최대 100개)와 프로젝트 폴더 하위 노트를 모은 뒤, 수정일이나 생성일이 기간 안에 드는 노트만 최신순으로 추립니다.
- **이전 보고서 차단**: 역할 검색은 `deny`·시스템·제안뿐 아니라 **과거에 만들어진 `type: report` 보고서도 모두 제외**합니다. 사용자가 보고서의 `type`을 바꿔 자기 지식으로 편입하기 전에는 이전 보고서가 다시 근거로 순환하지 않습니다([[ENH-5]]).

### 2. `connector`와 `challenger`의 중간 정리

두 모델 팀원은 `retriever`가 모아 둔 후보를 읽고, 더 확인해야 하면 역할 전용 검색(`search`·`related`)으로 후보를 넓힙니다. 검색 결과는 바로 인용할 수 없고 실제로 `read`로 열어 본 노트만 인용할 수 있습니다.

- `connector`는 대상과 같은 주제를 다룬 기존 노트, 서로 이어지는 연결, 서로 어긋나는 긴장을 뽑아 모든 주장에 근거 핸들을 붙여 넘깁니다.
- `challenger`는 대상과 앞선 인계물을 보고 논리의 빈틈, Vault 안의 반론, 다시 생각해 볼 열린 질문을 근거 핸들과 함께 넘깁니다.

### 3. `synthesizer`의 최종 보고서 조립

`synthesizer`는 앞선 모든 단계·구간에서 완료된 인계물과 자신이 읽은 노트를 바탕으로 모드에 정해진 절 전체를 채웁니다.

- 모든 문장에는 `인용`(읽은 노트가 직접 말하는 내용), `추론`(노트를 바탕으로 확장한 해석), `찾지 못함`(Vault가 다루지 않는 내용) 중 하나의 라벨을 붙입니다. Vault가 다루지 않는 절이라도 억지로 채우지 않고 `찾지 못함` 주장으로 명시해야 합니다.
- `인용` 라벨이 붙은 주장에는 반드시 이번 작업에서 실제로 읽은 핸들이 달려야 합니다. 라벨이나 인용이 빠진 보고서를 교정 턴까지 두 번 연속 제출하면 `synthesizer` 단계가 실패해 보고서가 쓰이지 않고 작업이 미충족으로 끝납니다([[ENH-2]]).

### 4. 조언 전용 `system_one` 도구

`connector`·`challenger`·`synthesizer`는 이번 작업에서 이미 읽은 노트에 대해 빠른 모델(`gpt-6-luna`)에게 닫힌 질문(선택지 중 고르기 또는 예/아니오 확률)을 단계당 최대 10번까지 물을 수 있습니다([[ENH-8]]). 보내기 직전 현재 파일이 여전히 `approve`인지 다시 확인하며, 답은 조언일 뿐 Owner가 보고서에 적지 않습니다. System One이 꺼져 있거나 실패해도 작업은 그대로 진행됩니다.

- 현재 실제 Hermes 연결에서 선택지 배열(`choices`)을 넘길 때 거절되는 제한은 [[status]]를 참고하세요.

## 동적 Graph 구성, 독립 평가와 후속 구간

ThinkingManager는 노트 본문을 읽지 않고 모드, 팀원 풀, 남은 예산(기본 2구간, 생산자 호출 6회), 이전 평가 결과만 보고 구간을 동적으로 짭니다. C1과 달리 **`synthesizer`가 항상 마지막 생산자**로 고정되므로, 1구간이든 후속 구간이든 마지막 단계는 반드시 `synthesizer`입니다.

- **`develop` 전체 1구간 예시**: `retriever → connector → challenger → synthesizer` (생산자 4회 소모, 후속용 2회 남음)
- **가벼운 `ask`·`review` 1구간 예시**: `retriever → connector → synthesizer`, `retriever → challenger → synthesizer`, 또는 `retriever → synthesizer`처럼 모드와 필요에 따라 중간 팀원을 줄일 수 있습니다.
- **긴장 근거만 부족할 때 2구간 예시**: 1구간 4단계 뒤 평가자가 보고서의 긴장 근거만 부족하다고 판정하면, 남은 2회 예산 안에서 `connector → synthesizer`만 다시 수행하는 2구간을 짭니다. `synthesizer`는 앞 구간의 다른 인계물과 새로 보강된 `connector` 인계물을 함께 받아 최종 보고서를 다시 만듭니다([[ENH-6]]). 이 후속 구간에는 긴장 기준과 무관한 `retriever`나 `challenger`를 넣을 수 없습니다.
- **초점·형식 보완 2구간 예시**: 초점 이탈만 지적되면 `challenger → synthesizer`(또는 `synthesizer` 단독), 라벨·절 누락만 지적되면 `synthesizer` 단독으로 다시 수행합니다.

Manager가 EvalOfficer에게 지시를 주거나 평가 위치를 바꾸려 하면 교정 턴 없이 즉시 거절되어 구간이 시작되지 않고 작업이 실패합니다.

실행 접점에서 각 구간은 Temporal `WorkWorkflow`가 사전 등록된 LangGraph 구간을 따라 실행하고, 항상 가장 최근 완료된 `synthesizer` 보고서를 대상으로 정적 검사(읽은 인용, 주장 라벨, 모드별 절 구성)와 `kos-eval`의 독립 의미 평가(초점 충족 및 `develop`·`ask`의 긴장 근거)를 거쳐 Owner가 최종 판정을 내립니다. Temporal·LangGraph·Hermes 세션·교정 턴의 공통 규칙은 [[architecture]]를 보세요.

## 보고서 생성, 정책 상속, TeamReview와 사후 관찰

평가를 통과하면 Owner가 `01_AI_Review/Reports/YYYY-MM-DD <제목>.md` 파일을 **생성 전용**으로 씁니다. 기존 보고서를 덮어쓰지 않고 원본 노트도 건드리지 않으며, 만들어진 직후부터 사용자의 문서가 됩니다([[ENH-1]]).

- **문장 형식과 인용 펼침**: 각 주장은 `[인용]`·`[추론]`·`[찾지 못함]`(영어 노트나 영어 질문은 `[cited]`·`[inference]`·`[not found]`) 라벨로 시작하고, 인용 핸들은 Owner가 `[[경로|제목]] (줄 범위, 8자리 해시)` 형식으로 펼쳐 줍니다.
- **정책 상속과 입력 기록**: 보고서 frontmatter의 `inputs` 목록과 `ai_policy`는 최종 보고서에 인용된 노트뿐 아니라 **대상 노트와 이번 작업에서 읽은 모든 노트**를 합쳐 가장 엄격한 정책을 물려받습니다([[ENH-4]]).
- **작업 도중 원본이 바뀐 경우**: 보고서를 쓰기 직전, 작업에서 읽은 노트의 현재 파일 해시를 스냅숏과 비교합니다. 도중에 수정되거나 사라진 노트가 있으면 보고서 맨 위에 어떤 노트가 바뀌었는지 안내 인용구를 넣고, 본문 인용은 작업이 실제로 읽은 스냅숏 바이트를 그대로 유지합니다([[ENH-3]]).
- **TeamReview와 보고서 사후 관찰**: 보고서가 쓰인 뒤 ThinkingManager가 산출물을 낸 팀원(`retriever` 포함)마다 1~5점 평점과 메모, 최대 3개의 개선 제안을 남깁니다. 이 제안은 조언 기록일 뿐 역할·카탈로그·평가를 바꾸지 않습니다([[ENH-7]], [[c9]]). 또한 Owner는 생성된 보고서를 지켜보다가 사용자가 수정하거나, `type`을 바꿔 자기 지식으로 편입하거나, 삭제하면 그 사실만 본문 없이 `synthesizer`의 `feedback`에 기록합니다.

| `synthesizer` 교정 포함 2회 연속 검증 실패, 예산 소진, 또는 같은 미충족 반복 | Work `unmet`과 미충족 기준 표시, 보고서 미생성([[ENH-2]]) |
| Manager의 평가자 권한 위반 Graph 제출 | 구간 미시작, Work `failed`, 보고서 미생성 |
| Hermes profile·모델·자격 증명 불가 또는 Activity 시간 초과/중단 | 재시도·대체 없이 Work `failed` 또는 재실행 없는 `unknown`, 보고서 미생성 |
| 작업 도중 사용자가 입력 노트를 수정 | 보고서 정상 생성 + 상단에 입력 변경 사실 안내, 원본 노트 유지([[ENH-3]]) |
