# C7 예약 작업 (Owner 내부 스케줄러)

KnowledgeOS에는 호스트 `cron`, Hermes `cronjob`, 분 단위 상주 스크립트가 없습니다. 모든 정기 작업은 **Owner 프로세스가 켜져 있는 동안 Owner 안의 스케줄러 스레드**(`kos-scheduler`)가 시계를 확인해 `job.run` 요청을 접수하는 방식으로만 시작됩니다([`c7_jobs.py`](../../src/knowledgeos/capabilities/c7_jobs.py)).

## 다섯 가지 예약 작업과 실제 실행 경로

작업 선언은 [`config/jobs.json`](../../config/jobs.json)에 있고 모든 시각은 `Asia/Seoul` 기준입니다. 스케줄러 자신은 어떤 노트도 직접 고치지 않고 각 작업의 자식 명령을 접수할 뿐이며, 실제 처리는 연결된 기능의 Officer나 Team이 맡습니다(공통 `WorkWorkflow`·`LangGraph` 실행 원리는 [[architecture]] 참조).

| 작업 | 기본 시각 (서울) | 자식 명령과 실행 주체 | 프로파일·Graph·Temporal 경로 |
|---|---|---|---|
| `standardize` | `0 * * * *` (매시 :00) | `standardize.auto` → [[c2]] `StandardizationOfficer`(정적, 설정 시 System One 직접 호출) | **Hermes 프로파일 없음** · 단일 Officer Graph · `WorkWorkflow` |
| `embed` | `30 * * * *` (매시 :30) | `index.embed` → [[c3]] `EmbeddingOfficer`(정적, 로컬 Ollama 호출) | **Hermes 프로파일 없음** · 할 일 없으면 접수 즉시 종료(`Done`), 있으면 단일 Officer Graph + `WorkWorkflow` |
| `curate` | `0 6 * * *` (매일 06:00) | `organize.auto` → [[c1]] 정리 팀(새 포착·종류 없는 `approve` 노트 최대 10개) | 대상 없으면 접수 즉시 종료(`Done`). 있으면 `WorkWorkflow`에서 `kos-curation-manager`(`gpt-6.1-sol`)가 Graph 동적 조합 → `scout`(정적)·`kos-classifier`·`kos-linker`(`gpt-6.1-terra`) → `kos-eval`(`gpt-6.1-sol`) (모델 모두 `high`) |
| `daily` | `0 7 * * *` (매일 07:00) | `daily.run` → [[c12]] `DailyOfficer`(정적) + 정적 `EvalOfficer` | **모델 프로파일 없음** (할 일 알림 발송 시에만 송신 전용 `kos-ops`) · 단일 Officer Graph · `WorkWorkflow` |
| `digest` | `0 8 * * *` (매일 08:00) | `digest.run` → [[c5]] `StewardshipOfficer`(정적, 설정 시 System One) + [[c8]] 요약 생성 + 정적 `EvalOfficer` | **모델 프로파일 없음** (요약 발송 시에만 송신 전용 `kos-ops`) · 단일 Officer Graph · `WorkWorkflow` |

`curate`의 경우 `kos-curation-manager`가 대상에 따라 Graph 구성을 바꿉니다. 예를 들어 연결할 만한 관련 노트가 없는 포착만 모였으면 `linker`를 뺀 `["scout", "classifier"]`만으로 1차 구간을 짜고, 반대로 `kos-eval`이 분류 기준 미충족을 판정하면 예산 안에서 `["classifier"]`만 넣은 후속 구간을 다시 조합해 실행합니다([`roles.json`](../../config/roles.json), [`kos-curation-manager/SOUL.md`](../../roles/kos-curation-manager/SOUL.md)).

## 시간표 형식, 설정, 시작 지연과 따라잡기

[`scheduler.py`](../../src/knowledgeos/scheduler.py)는 `분 시 * * *` 다섯 필드 cron 식만 허용합니다(일·월·요일은 반드시 `*`). 지원하지 않는 표현식이 있으면 Owner가 부팅할 때 즉시 시작을 멈춥니다. 동작 설정은 [`C7.json`](../../config/capabilities/C7.json)에 기본값이 있고 `owner.json`의 `settings.C7`로 바꿀 수 있습니다.

- **`scheduler_enabled` (기본 `true`)**: `false`면 `kos-scheduler`를 아예 켜지 않아 자동 실행이 없습니다. 그래도 CLI `knowledgeos job run <작업>` 수동 실행은 동작합니다([[JOB-6]]).
- **`startup_delay_minutes` (기본 `3`)**: Owner 시작 직후 이 시간이 지나기 전에는 아무 작업도 트리거하지 않습니다.
- **`tick_seconds` (기본 `30`)**: 깨어나 Owner 시계를 다시 보는 최대 주기입니다. 다음 예정 시각 전이면 시계만 비교하고 아무 요청도 만들지 않습니다.

Owner가 꺼져 있던 동안 지난 시각과 재시작은 다음 규칙으로 다룹니다.

1. **처음 등록된 작업**: Owner가 처음 보는 작업은 `jobs/<작업>.json`에 `observed_at`을 남기므로, 처음 켰을 때 과거 시각을 "놓친 것"으로 소급 실행하지 않습니다.
2. **시작 지연 뒤 1회 따라잡기**: 오후에 Owner를 끄고 다음 날 10:15에 켜면 `standardize` 정각이 여러 번 지났더라도 시작 후 3분 동안은 기다립니다. 3분이 지나면 가장 최근 지난 슬롯(`10:00`)을 마지막 실행·소비 시각과 비교해 밀린 횟수에 상관없이 **딱 한 번**만 트리거합니다([[JOB-4]]).
3. **슬롯당 유일한 트리거 ID**: 자동 트리거의 요청 ID는 항상 `schedule-<작업>-<YYYYMMDDTHHMM>`(서울 시각)입니다. 같은 슬롯 안에 Owner를 재시작하거나 이미 같은 슬롯 ID가 접수돼 있으면 중복 실행하지 않고 슬롯만 소비합니다([[JOB-5]]).

## 부모 트리거(`job.run`)와 자식 요청의 2단계 디스패치

예약 시각이 되면 스케줄러가 작업 본체를 한 요청 안에서 기다리지 않고 **부모 트리거 요청**과 **자식 실행 요청**으로 나눕니다. 덕분에 워커가 1개(`workers=1`)뿐인 환경에서도 부모가 자식을 기다리며 막히지 않습니다.

1. **부모 요청 (`job.run`)**: 스케줄러가 `schedule-<작업>-<시각>` ID와 `schedule/<작업>` 행위자 이름으로 `job.run`을 접수합니다. 이 부모 요청은 `Director` 접수 단계에서 바로 실행되어 즉시 `completed`로 끝나며 **부모 요청 자체는 `WorkWorkflow`나 Graph를 열지 않습니다**.
2. **사전 확인과 차단 기록**: `job.run`은 요청자가 `schedule/<작업>`인지 검사하고 `jobs/<작업>` 잠금을 잡습니다. 작업이 일시정지 상태면 `job_blocked` 학습 신호를 남기고 거부하며, 아직 끝나지 않은 이전 실행(`job_runs`)이 남아 있어도 거부합니다(자동 스케줄러는 이때도 해당 슬롯을 소비해 다음 시각까지 기다립니다).
3. **자식 요청 (`jobchild-*`) 접수**: 통과하면 실행 이력 `job_runs/<실행ID>.json`을 `"received"`로 만들고 `jobs/<작업>.json`의 마지막 실행 시각을 갱신한 뒤, 실제 작업 명령(`standardize.auto`, `index.embed`, `organize.auto`, `daily.run`, `digest.run`)을 `jobchild-<해시>`라는 새 요청 ID와 같은 `schedule/<작업>` 행위자로 접수합니다.
4. **실제 `Work` 실행과 감시 스레드(`kos-jobs`)**: 자식 요청은 별도 워커에서 `Director`를 통과해 대상이 없으면 곧바로 끝나거나, 대상이 있으면 `Work`를 생성해 Temporal `WorkWorkflow`로 넘어갑니다. Owner의 백그라운드 스레드 `kos-jobs`가 자식 영수증이 종료 상태가 될 때까지 지켜보다가 끝나면 `job_runs/<실행ID>.json`과 `jobs/<작업>.json`의 최종 결과(`last_outcome`, `last_result`, `last_finished`)를 채웁니다.

이 구조 때문에 **트리거 영수증(`job.run`)의 `completed`는 "자식 요청을 정상 접수했다"는 뜻이지 실행 성공이 아닙니다**. 실제 작업 성패는 자식 `request_id` 영수증이나 `jobs/<작업>.json`의 `last_outcome`으로 봅니다.

## 일시정지·수동 실행·주의 항목

- **콘솔 일시정지·재개 (`job.pause`, `job.resume`)**: 브라우저 콘솔의 예약 작업 탭은 `GET /api/jobs`를 읽어 `job.pause`·`job.resume`을 보냅니다([`app.js`](../../frontend/app.js)). 두 요청은 접수 단계에서 `jobs/<작업>.json`의 `paused` 상태만 바꾸고 결정 기록을 남긴 뒤 바로 끝납니다(`WorkWorkflow`·`ActionWorkflow` 없음). 일시정지 중 지난 시각은 요청 없이 소비되므로 재개해도 밀린 실행을 몰아 하지 않습니다([[JOB-6]]).
- **CLI 수동 실행 (`knowledgeos job run <작업>`)**: [`cli.py`](../../src/knowledgeos/cli.py)가 `schedule/<작업>` 행위자로 `job.run`을 보낸 뒤, 응답에 담긴 자식 `request_id`가 끝날 때까지 이어서 기다렸다가 트리거 결과와 실행 결과를 함께 출력합니다. 수동 실행도 마지막 실행 시각으로 계산되며, 일시정지된 작업은 거부됩니다(`embed` 전체를 끝까지 돌릴 때는 `knowledgeos index embed`가 남은 노트가 없을 때까지 반복 호출합니다).
- **놓침·실패·차단 주의 항목**: 일시정지되지 않은 작업이 두 슬롯을 넘기도록 실행되지 않으면 `missed_job`, 직전 실행이 `failed`·`unknown`이면 `failed_job`, `unmet`·`refused`·`cancelled`면 `blocked_job` 주의 항목으로 계산되어 콘솔에 뜹니다([[c5]]). 단, [[c8]] 정책상 실패·차단·놓친 작업은 **즉시 Discord 알림을 보내지 않으며**, 최근 실행이 `failed`인 작업 이름만 08:00 검토 요약이 나갈 때 보조 줄로 붙습니다.

> [!tip]
> Docker VM에서 도는 공유 Temporal 서버의 시계가 Mac 잠자기 뒤 호스트보다 십수 분 뒤처질 수 있어, Activity 제한 시간 판정은 서버 시각이 아니라 워커의 로컬 단조 시계 기준으로 계산합니다([`temporal_runtime.py`](../../src/knowledgeos/temporal_runtime.py)). 관련 이력은 [[status]]를 참고하세요.
