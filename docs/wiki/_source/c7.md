# C7 예약 작업 (Owner 내부 스케줄러)

## 1. 한눈에 보기

예약 작업은 정해진 시각에 KnowledgeOS가 스스로 시작하는 일입니다. 규격화·임베딩·정리·요약 네 가지가 있고, 모두 **Owner(KnowledgeOS의 상주 프로세스, [[glossary]] 참조)가 켜져 있는 동안 Owner 안에서만** 실행됩니다. 호스트의 cron, Hermes cron, 분 단위 프로세스는 없습니다.

스케줄러는 "언제 시작할지"만 정합니다. 무엇을 할지는 시작되는 쪽 기능(C1·C2·C3·C5)이 정하므로, 예약 작업은 직접 파일을 쓰지 않고 그 기능들을 통해서만 씁니다.

| 항목 | 내용 |
|---|---|
| 트리거 | 정해진 시각(slot)이 되었을 때 Owner 안의 스케줄러. 수동으로는 CLI `knowledgeos job run <작업>` |
| 담당 | Scheduler(정적 코드, Owner 서비스). 실제 작업은 [[C1]]·[[C2]]·[[C3]]·[[C5]]가 맡음 |
| 결과물 | 스케줄러 자체의 쓰기는 없음. 해당 기능의 결과(제안·자동 규격화 변경·벡터 색인·요약 알림)가 그대로 나옴 |
| 사용자 결정 여부 | 없음. 다만 사용자는 콘솔에서 작업을 일시정지·재개할 수 있고, 판단이 필요한 결과(정리 제안)는 여전히 [[C6]]에서 사용자가 결정함 |

> [!note]
> 출처: `docs/CAPABILITIES.md`의 Capability summary와 C7 절. 작업 선언은 `config/jobs.json`에 있습니다.

### 네 가지 작업

| 작업 | 기본 주기 (Asia/Seoul) | 하는 일 |
|---|---|---|
| `standardize` | 매시 정각 | [[C2]] 자동 경로. 지난 실행 이후 바뀐 노트만 결정적으로 규격화 |
| `embed` | 매시 30분 | [[C3]] `index.embed`. 새로 생기거나 바뀐 노트만 의미 검색용 벡터로 만듦 |
| `curate` | 매일 06:00 | [[C1]]을 새 포착과 종류 없는 `remote_ok` 노트에 실행. 한 번에 최대 10개 |
| `digest` | 매일 08:00 | [[C5]] 계산과 [[C8]] Discord 요약 |

## 2. 왜 이 명세가 필요한가

`USER_FEATURE_SPEC.md`의 "지키는 약속" 중 이 기능이 지키는 것은 다음입니다.

- **4. 자동으로 바꾸는 것은 작고 기계적인 것뿐입니다.** 자동으로 도는 작업이 많아질수록 "무엇이 자동이고 무엇이 제안인가"의 경계가 중요합니다. 스케줄러는 시작만 맡고, 자동 쓰기는 결정적 규격화(`standardize`)에만 있습니다. 판단이 필요한 `curate`는 제안만 만듭니다.
- **1. Vault는 사용자의 것입니다.** Vault는 사용자의 것이므로, 자동 작업이 사용자가 방금 편집 중인 노트를 건드리지 않아야 합니다. `standardize`는 최근 10분 안에 편집한 노트를 건너뜁니다 (`docs/CAPABILITIES.md` C2).

이 명세가 없으면 생길 수 있는 문제는 다음과 같습니다.

- Owner를 재시작할 때마다 같은 시각의 작업이 또 실행되거나, 오래 꺼 두었다가 켜면 놓친 횟수만큼 한꺼번에 몰려 돌 수 있습니다. 명세는 "슬롯당 한 번"과 "놓친 작업은 한 번만"으로 이를 막습니다 ([[JOB-4]], [[JOB-5]]).
- 모델 경로가 막힌 날 `curate`가 몰래 재시도하거나 다른 모델로 바뀔 수 있습니다. 명세는 보이게 실패하고 재시도하지 않는다고 정합니다 ([[JOB-3]]).
- 호스트 스케줄러가 따로 있으면 정책·감사 경로가 둘로 나뉩니다. 모든 실행은 `schedule/<job>` 행위자의 요청으로 Director를 통과합니다 (`docs/CAPABILITIES.md`: 모든 Work는 Director를 거칩니다. 운용 원칙은 [[philosophy]] 참조).

## 3. 어떻게 쓰는가

예약 작업은 대부분 **자동 경로**이며, 사용자가 켜는 스위치는 없습니다. Owner가 켜져 있으면 자동으로 돕니다.

### 자동으로 일어나는 일

1. Obsidian Thin Client의 **Owner 시작**(전원 버튼) 또는 launchd로 Owner를 켭니다 (`README.md`).
2. 시작 후 `startup_delay_minutes`(기본 3분)가 지나면, 꺼져 있는 동안 슬롯을 놓친 작업이 각각 **한 번씩** 실행됩니다.
3. 이후에는 각 작업의 정해진 시각마다 실행됩니다.
4. 결과는 해당 기능의 결과물로 나타납니다. 예를 들어 `curate`는 `01_AI_Review/Proposals/`에 제안 노트를, `digest`는 Discord 요약을 남깁니다.

### 관리 콘솔 (브라우저, 로컬 전용)

- 예약 작업 실행 기록을 볼 수 있습니다 (`USER_FEATURE_SPEC.md` "관리: 브라우저와 CLI").
- 작업을 **일시정지**(`job.pause`)하거나 **재개**(`job.resume`)할 수 있습니다.
- 실패한 실행, 또는 슬롯이 두 번 지나도록 실행되지 않은 작업은 주의 항목으로 나타납니다.

### CLI

```sh
knowledgeos job run standardize|embed|curate|digest   # 작업을 지금 실행하고 실행 결과 영수증까지 따라가 보고
knowledgeos index embed                                # embed와 같은 index.embed 요청을 남은 노트가 없을 때까지 반복
```

- 수동 실행의 결과는 실행 영수증을 따라가 보고합니다. 수동 실행도 "마지막 실행"으로 계산되어 다음 슬롯의 "놓침" 판단에 반영됩니다.
- 일시정지된 작업의 수동 실행은 거부됩니다.
- `settings.C7.scheduler_enabled`가 false여도 `knowledgeos job run`은 동작합니다.

### 설정 (`settings.C7`)

| 설정 | 기본값 | 의미 |
|---|---|---|
| `scheduler_enabled` | true | false면 자동 실행이 전혀 없음 (수동 실행은 가능) |
| `startup_delay_minutes` | 3 | Owner 시작 후 이 시간이 지나기 전에는 아무것도 실행하지 않음 |
| `tick_seconds` | 30 | 시계를 다시 확인하는 최대 간격. 시계 비교만 하며 슬롯이 되었을 때만 요청을 만듦 |

스케줄은 5필드 cron 식(Asia/Seoul)이며 분·시 필드만 바꿀 수 있습니다 (`*`, 숫자, 목록, 범위, 간격). 지원하지 않는 형식이면 Owner가 시작 시 멈춥니다.

### 작동 예시

오후에 Owner를 껐다가 다음 날 오전에 켰다고 하겠습니다.

1. 그 사이 `standardize`의 매시 정각 슬롯이 여러 번 지나갔습니다. Owner가 꺼져 있었으므로 아무 일도 일어나지 않았고, 잃은 것도 없습니다.
2. 오전에 Owner를 켜면 먼저 3분 동안은 아무것도 실행되지 않습니다.
3. 3분이 지나면 `standardize`가 **정확히 한 번**, 행위자 `schedule/standardize`로 실행됩니다 ([[JOB-4]]). 놓친 슬롯 수와 무관합니다.
4. Owner가 계속 켜져 있으면 다음 정각 슬롯에 다시 실행되고, 이때 변경된 노트가 없으면 아무것도 쓰지 않습니다 ([[JOB-1]]).
5. 만약 사용자가 중간에 `curate`를 일시정지했다면, 그 작업의 슬롯은 트리거 없이 지나가며, 재개해도 놓친 실행을 몰아서 하지 않고 다음 슬롯에 실행됩니다 ([[JOB-6]]).

## 4. 동작 흐름

{{svg:scheduler-timeline}}

읽는 법: Owner가 시작되면 3분 지연 동안 아무것도 실행되지 않고, 이후 놓친 작업을 한 번씩 처리한 뒤 정해진 슬롯마다 실행합니다. Owner가 꺼져 있는 구간에는 실행이 없습니다.

슬롯 하나가 처리되는 규칙은 다음과 같습니다 (`docs/CAPABILITIES.md` C7).

1. 슬롯의 트리거 요청 ID는 `schedule-<작업>-<YYYYMMDDTHHMM>`(서울 시각)입니다. 재시작해도 같은 슬롯이 두 번 트리거되지 않습니다 ([[JOB-5]]).
2. 작업은 "마지막 슬롯이 마지막 실행(CLI 수동 실행 포함)보다 늦고, Owner가 이미 소비한 슬롯보다도 늦을 때" 실행 대상입니다. Owner가 처음 보는 작업에는 놓친 슬롯이 없습니다.
3. 이전 실행이 아직 진행 중일 때 슬롯이 오면 그 슬롯은 거부되고 소비됩니다.
4. 트리거된 요청은 별도로 Director에 접수되어 자신의 실행 영수증을 가집니다. 트리거 영수증은 "요청을 트리거했다"만 뜻하고, 실행 성공을 뜻하지 않습니다.

> [!tip]
> 작업이 성공했는지는 트리거 영수증이 아니라 **실행 영수증**(콘솔의 작업 기록, 또는 `knowledgeos job run`의 보고)으로 확인하세요.

## 7. 현재 상태와 남은 일

`PROJECT_STATE.md`와 Blueprint §9 기준입니다. 자세한 근거는 [[status]], 남은 과제는 [[roadmap]]에 있습니다.

- **소스·테스트:** 모든 인수 ID(JOB-1~JOB-7)는 추적 표에 구현 심볼과 테스트 노드가 연결되어 있습니다 (`E_CAPABILITY_TRACE`, `E_TRACED_TESTS`).
- **실환경 근거 (스케줄러):** `KNOWLEDGEOS_REAL_ADOPTION.SCHEDULER`가 통과로 기록되어 있습니다. 근거(`E_REAL_SCHEDULER_SLOT`)는 임시 `20 40` `index.embed` 작업이 3분 시작 지연 뒤 한 번 실행되었고 요청 ID가 `schedule-schedulercheck-20261119T2040`이며, 그 뒤 임시 작업을 지우고 Owner를 재시작했다는 것입니다.
- **콘솔 일시정지·재개:** 임시 Owner(합성 Vault·State)에서 `job.pause`와 `job.resume` 영수증이 브라우저에서 관찰되었습니다 (`E_CONSOLE_BROWSER`). 실제 Vault에 대한 관찰은 아닙니다.
- **Hermes cron 제거:** `kos-ops` profile의 Hermes cron 작업 3개와 생성 스크립트를 제거하고 발송 전용으로 재설치했습니다 (`E_HERMES_CRON_REMOVED`). 이로써 예약은 Owner 한 곳에만 남았습니다.
- **남은 일 (`PROJECT_STATE.md` handoff, 미완):** 실제 환경에서 Owner가 켜져 있는 동안 **자연스러운 매시 `standardize`·`embed` 실행**을 관찰하고, `related_min_score`를 실제 노트에 맞춰 조정하는 일이 남아 있습니다. 실환경 슬롯 검증은 위의 임시 작업 한 번뿐이므로, `standardize`·`curate`·`digest`가 실제 Vault에서 자기 주기로 도는 것은 이 문서 기준으로 관찰된 근거가 없습니다.
- **열린 질문 (Blueprint §9):** 기본 작업 주기가 실제 사용과 맞는지, `ask`가 기본 `ai_policy`로 맞는지(정리 작업이 자동으로 돌 때 영향)가 아직 정해지지 않았습니다.

## 8. 관련 기능

- [[C1]] 정리: `curate`가 새 포착과 종류 없는 `remote_ok` 노트를 최대 10개까지 정리 제안으로 만듭니다.
- [[C2]] 규격화: `standardize`가 자동 경로로 쓰이며, 최근 10분 이내에 편집한 노트는 건너뜁니다.
- [[C3]] 검색: `embed`가 `index.embed`로 의미 검색 벡터를 갱신합니다.
- [[C5]] 문서 관리: `digest`가 주의 항목과 "다시 볼 것" 집합을 계산합니다.
- [[C8]] 알림: 요약(digest)을 Discord로 보내고, 실패한 작업은 즉시 알림이 됩니다.
- [[C6]] 검토: 예약된 `curate`가 만든 제안은 사용자가 적용·거절합니다.
- [[C11]] 호출·관리 화면: 콘솔의 작업 기록·일시정지·재개와 CLI `job run`이 여기 있습니다.
