# C6 검토: 적용·거절·되돌리기

KnowledgeOS는 판단이 들어가는 변경을 노트에 바로 쓰지 않고 `01_AI_Review/Proposals/` 아래 **제안 노트**(`type: proposal`)로 만들어 둡니다. C6은 사용자가 Obsidian 안에서 그 제안을 **적용**(`review.apply`)하거나 **거절**(`review.reject`)하고, 이미 적용된 자동·수동 규격화([[c2]])를 **되돌리는**(`review.undo`) 기능입니다.

## 실행 주체와 Temporal·Graph 접점

Obsidian의 사이드바·명령 팔레트·Note Toolbar가 보내는 세 요청은 **모델을 부르지 않습니다.** System One, 새 Work, LangGraph 구간도 없습니다. Owner가 요청을 접수한 자리에서 제안 파일과 현재 노트를 대조해 직접 처리하고 결과를 기록합니다. Temporal의 `WorkWorkflow`나 `ActionWorkflow`도 시작하지 않습니다.

> [!note]
> `ActionWorkflow`는 수동 규격화 미리보기처럼 **아직 확인을 기다리는 Work**에 사용자가 응답할 때 쓰입니다. 제안 검토는 그와 다릅니다. 제안을 만든 작업은 이미 끝나 있으며, 원래 Work 기록이 사라져도 제안 파일이 남아 있으면 적용·거절할 수 있습니다. 다만 규격화 되돌리기는 변경 전 바이트를 보관한 State 이력이 있어야 합니다.

## 제안 적용: 체크박스 선택부터 파일 이동·삭제까지

[[c1]] 정리가 만든 `01_AI_Review/Proposals/빛과 생각 — organize.md`를 예로 보겠습니다. 제안에는 대상 노트의 식별자와 작성 당시 판본, 변경 체크리스트, 적용 전후 차이, 기계가 읽는 변경 목록이 함께 들어 있습니다. 체크박스마다 짧은 항목 ID가 있어, 사람이 화면에 표시된 항목을 고른 것과 Owner가 적용하는 변경이 정확히 대응합니다.

1. **사용자가 항목을 고르고 적용을 누름**: 사용자가 제안 노트를 열어 이동 항목만 `- [ ] 40_Knowledge/Ideas/로 이동 ^move`로 체크 해제한 뒤 **적용**을 누릅니다. Thin Client는 노트 본문을 보내지 않고 제안 노트의 경로와 방금 읽은 SHA-256 지문(`{path, digest}`)만 새 요청 ID(`request_id`)와 함께 Owner로 보냅니다([`main.js`](../../thin-client/main.js), [[SUR-1]]). Owner는 먼저 요청 영수증(`requests/<요청ID>.json`)을 "접수됨(`received`)"으로 확정합니다.
2. **제안 파일 읽기와 범위 검증**: Owner는 같은 제안 노트가 동시에 수정되지 않게 잠금을 잡고 제안 파일을 다시 읽습니다. 현재 `ai_policy`가 `deny`이거나, YAML 오류·충돌 표시가 있거나, 클라이언트가 읽은 뒤 제안 파일이 바뀌어 지문이 다르면 거부합니다. 이어서 본문 안의 `json kos-changes` 블록을 파싱하고, 코드 블록 안의 예시 문구를 제외한 실제 본문에서 중복 없는 `^항목ID` 체크박스를 매칭합니다. 허용된 속성(`type`, `status`, `title`, `tags`, `aliases`, 링크 속성) 바깥을 고치려 하거나 `99_System/`·`01_AI_Review/`·`00_Inbox/Requests/`·점 폴더·`80_Assets/`로 옮기려는 항목이 들어 있으면 즉시 거부합니다.
3. **결정 먼저 기록**: 대상 노트에 대한 잠금까지 확보하면 요청을 실행 중으로 바꾸고, State의 `actions/<액션ID>.json`에 Core 결정 기록(`HumanActionResponse`)과 `"received"` 상태를 먼저 씁니다. 원래 제안을 만든 `Work`가 State에 남아 있으면 그 작업 기록에도 액션 ID를 연결하지만, State가 초기화된 뒤라 `Work`가 없어도 적용은 멈추지 않습니다.
4. **대상 노트 확인과 체크된 항목만 반영**: `target_id`(있고 유일하며 `deny`가 아닐 때) 또는 `target_path`로 현재 대상 노트를 찾습니다. 체크 표시된(`- [x]`/`- [X]`) 항목만 골라 머리말 편집을 계산하는데, 한 항목에 여러 속성이 묶여 있으면 `type` → `status` → `title` 순으로 쓰고 목록 속성(`tags`·`related` 등)은 기존 값에 없는 항목만 중복 없이 덧붙이며, 이동 항목은 파일명을 그대로 둔 채 폴더만 바꿉니다.
   - 이동이 체크돼 있으면 목적지 폴더에 같은 파일명이 이미 있는지 먼저 확인하고(있으면 아무것도 쓰지 않고 `unmet`으로 종료), 없으면 효과 로그(`effects.jsonl`)에 의도를 먼저 적은 뒤 대상 노트의 현재 SHA-256이 제안의 `target_sha256`과 일치할 때만 새 경로에 원자적으로 쓰고 원래 파일을 지웁니다.
   - 속성 변경만 있거나 체크를 모두 해제한 경우에도 쓰기 직전 `target_sha256` 일치를 다시 확인한 뒤 교체합니다.
5. **제안 파일 삭제와 피드백 기록**: 대상 노트가 정상 반영되면 이어서 제안 파일 자체의 현재 SHA-256을 확인하고 `01_AI_Review/Proposals/`에서 제안 파일을 삭제합니다([[REV-1]], [[ORG-4]]). State의 제안 기록은 `applied`로, 액션 기록도 `"applied"`로 닫힙니다. 일부 항목을 체크 해제한 채 적용했다면 [[c9]] 학습 모듈이 역할 `feedback`과 `proposal_partially_applied` 신호를 남깁니다.

### 적용이 막히거나 제안을 직접 고친 경우

- **대상 노트가 그사이 바뀌었거나 삭제·`deny` 됨**: 적용하려는 순간 대상 노트가 사라졌거나 `deny`로 바뀌었거나 SHA-256이 `target_sha256`과 다르면, 대상 노트는 한 바이트도 건드리지 않습니다. 대신 제안 노트의 상태를 `stale`로 바꾸고 `kos_stale_at` 시각을 남긴 뒤, 요청 결과는 "수락되었으나 적용되지 않음(`unmet`, `state: not_applied`)"으로 기록하고 다시 정리를 요청하라고 알립니다([[REV-2]]).
- **적용 도중 제안 파일 자체가 바뀜**: 대상 노트에는 이미 체크한 변경이 반영되었지만 마지막 삭제 순간 제안 파일의 지문이 달라졌으면, 제안을 지우지 않은 채 `"proposal_deleted": false`와 함께 "다시 적용하지 말라"고 안내합니다.
- **사람이 제안 노트를 직접 수정한 경우**: 체크리스트를 포함해 본문을 직접 고친 제안이나 State에 작성 해시가 없는 제안은 이후 자동·수동 정리가 돌더라도 덮어쓰거나 중복 생성하지 않습니다. 같은 대상에 `open` 또는 `stale` 제안이 하나 있으면 새 제안은 만들지 않으며, 사용자가 다시 정리를 요청한 경우에도 Owner가 만든 바이트 그대로 남아 있는 `stale` 제안만 제자리에서 `open`으로 새로 씁니다([`proposals.py`](../../src/knowledgeos/proposals.py)).

## 거절·7일 만료·규격화 되돌리기

- **거절 (`review.reject`)**: 대상 노트는 읽지 않고 지문도 대조하지 않습니다. 액션 기록에 `"received"`를 먼저 남긴 뒤 제안 파일의 현재 SHA-256만 확인해 `01_AI_Review/Proposals/`에서 삭제합니다. 삭제되면 State 제안 기록을 `rejected`로 표시하고 [[c9]]의 역할 `feedback`과 `proposal_rejected` 신호를 남깁니다([[LRN-1]]). 거절 직전 제안 파일이 수정되어 지문이 어긋났으면 삭제하지 않고 `unmet`(`not_applied`)으로 끝납니다.
- **7일 지난 `stale` 제안 자동 삭제**: C6 자체가 백그라운드로 지우는 것이 아니라, 매일 08:00 `digest` 실행 때 [[c5]]의 제안 유지 단계가 제안 폴더를 점검해 대상이 바뀐 `open` 제안을 `stale`로 바꾸고, `stale`이 된 지 7일(`stale_at` 또는 `kos_stale_at`, 없으면 파일 수정 시각 기준)이 넘은 제안을 삭제한 뒤 State 기록을 `expired`로 바꿉니다([`c5_stewardship.py`](../../src/knowledgeos/capabilities/c5_stewardship.py)). 지워진 제안도 Git 이력에는 남습니다.
- **되돌리기 (`review.undo`)**: 사이드바 **더보기 → 되돌리기**와 명령 팔레트의 "자동 변경 되돌리기"는 제안 적용을 취소하는 기능이 아니라 **[[c2]] 규격화(`manual`, `batch`, `autofix`)의 가장 최근 변경**을 원래대로 되돌립니다.
  1. State의 `changes/`에서 현재 노트 경로 또는 노트 ID와 일치하는 규격화 이력을 찾고, 시각과 효과 적용 순번이 가장 늦은 항목을 고릅니다. 기록이 없으면 State에 남아 있지 않으므로 거부하고 Git 이력을 안내합니다.
  2. `"received"` 액션 기록을 남긴 뒤 State `blobs/`에서 변경 전 원본 바이트를 꺼냅니다. 이미 되돌린 이력(`undone_at`)이 있거나, 현재 노트 지문이 규격화 결과(`result_sha`)와 다르거나(그사이 사용자가 편집함), 원본 데이터가 없으면 한 줄도 쓰지 않고 `refused`(`not_applied`)와 함께 Git 이력을 안내합니다([[REV-3]]).
  3. 일치하면 원본 바이트로 원자적 복원하고 해당 변경 이력에 `undone_at`을 기록하며, 다음 자동 규격화가 상태를 오해하지 않도록 C2 커서(`standardize_seen.jsonl`)를 복원된 지문으로 맞춥니다. 마지막으로 `undo` 학습 신호를 남깁니다.

## 응답 유실과 결과 불명 처리

- 클라이언트가 적용·거절 응답을 시간 초과로 받지 못해도 **같은 요청을 새로 보내지 않습니다**. Thin Client는 같은 `request_id`로 영수증 조회(`GET /api/requests/<요청ID>`)만 반복하며, Owner가 `"404"`(접수 기록이 아예 커밋된 적 없음)를 답할 때만 같은 `request_id`와 본문으로 재전송합니다.
- 이미 처리된 `request_id`로 똑같은 요청이 다시 오면 Owner는 기존 영수증(`200`)만 돌려주며 쓰기를 두 번 실행하지 않습니다([[REV-4]]). 같은 ID에 다른 내용을 담으면 `409 Conflict`로 막습니다.
- 쓰기 도중 예외가 나 결과를 확인할 수 없으면 `unknowns/<불명ID>.json`과 `unknown` 상태가 남습니다. `unknown`은 절대 자동으로 다시 실행하지 않으며, 사용자가 실제 파일 상태를 확인한 뒤 콘솔이나 CLI에서 `outcome.reconcile`로 관찰 결과만 기록할 수 있습니다([[c11]]). 공통 효과·영수증 원칙은 [[architecture]]를 참고하세요.
