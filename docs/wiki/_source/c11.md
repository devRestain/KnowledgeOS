# C11 호출·관리 화면 (Invocation and management surfaces)

## 한눈에 보기

C11은 KnowledgeOS의 **다른 기능(C1–C10)을 사용자가 부르고 관리하는 입구**입니다. 새로운 일을 하는 기능이 아니라, Obsidian의 Thin Client(작은 플러그인)·브라우저 관리 콘솔·CLI·Owner 시작/중지가 각자 맡은 일만 하도록 나눈 계약입니다. 문서 작업은 Obsidian 안에서, 관리는 콘솔과 CLI에서 하며 서로의 일을 겹쳐 하지 않습니다([[architecture]] 참고).

| 항목 | 내용 |
|---|---|
| 트리거 | 사용자가 Thin Client 명령·사이드바 버튼을 누르거나, 콘솔에서 조작하거나, CLI 명령을 실행 |
| 담당 | 없음(고유 역할 없음). 부르는 기능의 역할이 일을 처리하고, 모든 요청은 Director를 거침 |
| 결과물 | 직접 쓰는 것은 없음. 위임한 기능(C1·C2·C3·C4·C6 등)의 결과물로 나타남 |
| 사용자 결정 여부 | 호출은 항상 사용자가 직접 누를 때만 일어남. Owner 시작·중지도 눌렀을 때만 동작 |

> [!note]
> 요청(Request)은 Thin Client 명령, 콘솔 조작, CLI 명령, 예약 작업 실행, Gateway 제출 모두를 가리킵니다. Director가 받아들인 요청이 Work입니다. 자세한 뜻은 [[glossary]]를 보세요.

## 왜 이 명세가 필요한가

[[philosophy]]의 지키는 약속 가운데 이 기능이 직접 지키는 것은 다음입니다([[glossary]]의 용어 참고).

- **"문서 작업은 Obsidian 안에서 합니다."** KnowledgeOS를 부르는 쪽은 최소한의 Thin Client 명령과 사이드바 탭뿐이고, 관리는 브라우저 콘솔과 CLI가 맡으며 거기서 문서 작업은 하지 않습니다(USER_FEATURE_SPEC). 이 경계가 없으면 화면마다 기능이 중복되어 Thin Client가 커지고 유지보수를 오픈소스 플러그인에 맡긴다는 약속이 흔들립니다.
- **"Vault는 사용자의 것입니다."** 요청은 노트 경로와 마지막으로 본 내용의 해시만 보내고 본문은 보내지 않습니다([[SUR-1]]). 화면을 열거나 노트를 옮겨 다니는 것만으로는 설정도, Owner 상태도 바뀌지 않습니다([[SUR-2]], [[SUR-8]]).
- **"자동으로 바꾸는 것은 작고 기계적인 것뿐입니다."** 자유 요청을 해석하는 모델 Director는 정해진 몇 가지 명령으로만 연결할 수 있고, 기준·예산·권한을 스스로 정하려 하면 Work 자체가 만들어지지 않습니다([[SUR-3]]).

이 명세가 없다면 응답을 잃어버린 뒤 같은 요청을 무심코 다시 보내 일이 두 번 일어나거나, "켜졌다/꺼졌다"를 실제 확인 없이 알리는 일이 생길 수 있습니다. C11은 이를 영수증 확인과 health 관찰로 막습니다.

## 어떻게 쓰는가

### Obsidian Thin Client

명령은 명령 팔레트, 파일·편집기 메뉴, 사이드바 탭에서 부를 수 있습니다(CAPABILITIES C11).

| 명령 | 대상 | 부르는 기능 |
|---|---|---|
| 규격화 미리보기 | 노트·선택·폴더 | [[C2]] 수동 경로 |
| 정리 요청 | 노트·선택·폴더 | [[C1]] |
| 강화: 발전 / 묻기 / 돌아보기 | 노트, 질문 입력, 날짜 구간 | [[C4]] |
| 자유 요청 | 자유 문장 | Director 라우팅 |
| 관련 노트 · 의미 검색 | 노트, 검색어 입력 | [[C3]] |
| 적용 · 거절 | 제안 노트 | [[C6]] |
| 자동 변경 되돌리기 | 노트 | [[C6]] |
| 관리 콘솔 열기 | 어디서나 | 브라우저 콘솔 열기 |
| Owner 시작 · 중지 | 어디서나(데스크톱) | Owner 생명주기 |

**사이드바 사용법**

1. 리본의 KnowledgeOS 아이콘을 누르거나 명령 **KnowledgeOS: 사이드바 열기**를 실행하면 오른쪽 탭이 열립니다. 다시 열어도 탭은 하나만 재사용됩니다.
2. 탭 위쪽에는 마지막으로 활성이던 Markdown 노트가 표시되고, 아래에 **규격화 · 정리 · 강화 · 찾기** 네 버튼이 있습니다. 버튼은 아래의 **인라인 기능 창**을 선택할 뿐, 선택만으로 요청을 보내지 않습니다.
3. **규격화**에서는 **미리보기**를 눌러 diff를 받은 뒤, 같은 창의 **적용 · 취소**로 결정합니다. 확정하지 않은 미리보기는 기능이나 대상 노트를 바꾸면 취소되며, 늦게 도착한 응답도 자동 적용되지 않습니다. **정리** 역시 기능 창의 **정리 요청**을 눌러 실행합니다.
4. **강화**의 발전·묻기·돌아보기 선택, 질문·기간 입력과 **찾기**의 관련 노트·의미 검색 입력·결과는 모두 기능 창 안에 있습니다. 결과 링크를 누르면 해당 노트의 줄로 이동합니다. 사이드바는 팝업 메뉴나 모달을 열지 않습니다.
5. 대상 노트가 **제안 노트**일 때만 **적용 · 거절**이 나타납니다. 제안 노트인지는 그 노트의 현재 frontmatter를 따라 판단합니다.
6. **더보기**는 인라인 자유 요청 입력창과 자동 변경 되돌리기·관리 콘솔 동작을 엽니다. **전원 버튼**은 관찰된 연결 상태에 따라 Owner 시작 또는 중지를 부릅니다. 탭을 여는 것만으로는 Owner를 켜거나 끄지 않습니다.
7. 사이드바로 초점을 옮겨도 표시된 노트가 대상으로 유지되고, 다른 파일을 열면 대상이 바뀌며, 대상을 지우면 비워집니다. Markdown 대상이 없으면 노트 전용 동작은 비활성화되고 묻기·의미 검색·자유 요청만 남습니다. 입력 초안은 메모리에만 둡니다.
8. 연결 상태·진행 중 개수와 함께 입력 오류·요청 결과·결과 링크를 사이드바 안에서 표시합니다. 작업 이력이나 관리 패널은 없습니다. 기존 명령 팔레트·문맥 메뉴는 작은 입력·미리보기 모달과 완료 알림을 유지하면서 같은 요청·확인 경로를 사용합니다([[SUR-9]]).

> [!tip]
> 노트 하단의 "적용·거절" 같은 버튼은 Note Toolbar 등 다른 플러그인이 같은 명령을 띄울 수도 있습니다. 어느 쪽에서 눌러도 같은 요청 경로를 지납니다.

### 브라우저 관리 콘솔

Owner의 ExOps 백엔드가 loopback으로 제공하는 로컬 전용 페이지입니다. Thin Client의 **관리 콘솔 열기**로 열 수 있습니다(Blueprint §3.2).

- **볼 수 있는 것**: 작업 이력(WorkSpec, Graph, 역할별 호출·모델, 평가, 남은 작업, TeamReview), 예약 작업 실행 기록, 결과 불명(unknown), Bases로 보기 어려운 주의 항목, 알림 기록, Experience outbox, 역할별 학습 기록, 상태와 관찰 시각.
- **할 수 있는 것**(다른 화면과 같은 ExOps 접수를 거침): 작업 취소, 예약 작업 일시정지·재개, 결과 불명에 대한 확인 기록, TeamReview 제안을 "검토함"으로 표시.
- 취소는 일정 관찰 시간 뒤에 실제 적용 결과를 알려 주고, 확인하지 못하면 불명으로 남깁니다. 확인 기록은 사용자가 적용됨/적용 안 됨을 직접 관찰해 남기는 것이며, 과거 Work·영수증·불명 증거는 고쳐 쓰지 않습니다([[SUR-4]]).

### CLI

운영자용 유지보수 화면입니다(README, Blueprint §3.3).

```sh
knowledgeos serve --config owner.json          # Owner와 ExOps 백엔드, 관리 콘솔
knowledgeos health | vault-check | index rebuild|verify|embed
knowledgeos standardize PATH --dry-run|--apply
knowledgeos job run standardize|embed|curate|digest
knowledgeos reconcile UNKNOWN_ID --resolution applied|not_applied --yes
knowledgeos install profiles --config owner.json [--dry-run]
knowledgeos install service --config owner.json [--dry-run]
```

- 변경을 일으키는 모든 CLI 명령은 다른 화면과 같은 Owner 접수·효과 규칙을 따릅니다.
- `job run`은 트리거 영수증만 보고 끝내지 않고, 별도로 접수된 요청의 실행 영수증까지 따라가 보고합니다.

### Owner 시작·중지와 서비스 설치

Owner는 Mac에서 **필요할 때 켜지는 사용자 서비스(LaunchAgent)** 로 돌기 때문에 Obsidian을 종료해도 계속 실행됩니다. 처음 한 번 CLI로 등록합니다.

1. `knowledgeos install service --config owner.json --dry-run` 으로 plist와 `launchctl` 인자만 확인합니다. 아무것도 쓰지 않습니다([[SUR-7]]).
2. 확인했으면 `--dry-run` 없이 실행합니다. `~/Library/LaunchAgents/com.agentfabric.knowledgeos.owner.plist`가 만들어지고 적재되지만 **실행되지는 않습니다**(`RunAtLoad`·`KeepAlive` 꺼짐, 로그는 Runtime의 `logs/`). 라벨과 plist 경로는 `--label`, `--plist`로 바꿀 수 있습니다.
3. Obsidian에서 **Owner 시작**을 누르면 launchd 라벨을 kickstart하고 `/api/health`가 준비될 때까지 기다린 뒤 "시작됨"을 알립니다.
4. **Owner 중지**는 SIGTERM을 보낸 뒤 health 응답이 끊겼는지 확인해 "중지됨", "아직 실행 중", "확인 불가" 중 하나로 알립니다. `serve`는 SIGTERM에서 Owner와 ExOps를 깨끗이 닫습니다([[SUR-6]]).

예약 작업은 Owner가 켜져 있는 동안에만 돕니다([[C7]]).

### 작업 예시

1. 사용자가 새로 쓴 아이디어 노트를 열고 사이드바의 **규격화**를 눌러 기능 창을 엽니다. 이 선택만으로 요청을 보내지는 않습니다.
2. **미리보기**를 누르면 Thin Client가 그 노트의 경로와 마지막으로 본 해시만 담아 Owner에 요청합니다. 본문은 가지 않습니다.
3. Owner가 영수증을 기록하고 요청 ID로 즉시 답합니다. 사용자는 사이드바 안의 diff를 확인하고 **적용** 또는 **취소**를 누릅니다([[C2]]). 기능이나 대상 노트를 바꾸면 미확정 미리보기는 취소됩니다.
4. 응답이 유실되어도 클라이언트는 원래 영수증을 먼저 조회합니다. Owner가 "기록된 적 없음"이라고 확인한 경우에만 같은 요청을 다시 보낼 수 있고, "결과 불명"으로 기록된 요청은 다시 보내지 않습니다.

반대로 "이 노트들 전부 삭제해 줘" 같은 자유 요청은 카탈로그에 허용된 명령(규격화 미리보기·정리·강화)으로 연결할 수 없으므로 Work가 만들어지지 않습니다. 이유는 사이드바의 인라인 피드백 또는 명령 팔레트의 알림으로 표시됩니다([[SUR-3]]).

## 동작 흐름

{{svg:system-map}}

위 그림은 세 관리 화면이 모두 Owner를 거쳐 일하는 구조입니다. 요청이 접수되는 순서는 다음과 같습니다.

1. 화면(Thin Client·콘솔·CLI)이 요청을 보냅니다. Thin Client는 경로와 해시만 보냅니다.
2. Owner가 영수증을 커밋하고 요청 ID를 즉시 돌려줍니다.
3. 정형 요청(모든 Thin Client 명령·작업·CLI 명령)은 정적 코드가, 자유 문장만 `kos-director` 모델이 접수합니다. 모델 Director는 정해진 명령으로만 연결하며 기준·예산·권한·WorkSpec·입력 연결·경로를 지정하려는 시도는 권한 위반으로 Work 없이 거절됩니다. 일반적인 초안 오류에는 수정 기회가 한 번 주어집니다.
4. 조회(GET)는 효과를 일으키지 않으며, 응답을 잃은 뒤에는 원래 영수증을 조회합니다.

> [!warning]
> "결과 불명"으로 기록된 요청은 다시 실행해도 된다는 허락이 아닙니다. 확인이 필요하면 콘솔의 확인 기록이나 `knowledgeos reconcile`로 사람이 관찰한 결과를 남깁니다.

## 현재 상태와 남은 일

PROJECT_STATE의 기록에서 C11과 직접 관련된 것은 다음과 같습니다.

- **1.1.0 당시 소스·테스트**: `E_SIDEBAR_TESTS`는 C11 Thin Client 테스트 4건 통과, `E_SIDEBAR_TRACE`는 SUR-8까지 포함한 당시 인수 60건과 추적표 60행의 연결 기록입니다. 현재 인라인 계약의 검증과 구분합니다.
- **1.1.0 설치와 GUI 이력**: 실제 Obsidian 1.13.7에 1.1.0을 설치하고 밝은·어두운 테마, 탭 재사용, 노트 대상 전환, 312px 폭을 관찰했습니다(`E_SIDEBAR_INSTALL`, `E_SIDEBAR_GUI`). 그때 Vault Markdown 20개의 해시와 플러그인 설정 부재 상태를 보존했습니다(`E_SIDEBAR_PRESERVATION`). 이 기록을 1.2.0의 근거로 쓰지는 않습니다.
- **1.2.0 인라인 소스·추적**: `E_SIDEBAR_INLINE_TESTS`는 입력 검증·결과·초안 유지·한 번만 확인·늦은 미리보기 취소를 포함한 집중 테스트 5건 통과를 기록합니다. `E_SIDEBAR_INLINE_TRACE`는 SUR-9를 포함한 전체 인수 61건과 추적표 61행·pytest 노드 171개의 연결 기록이며, 171개 노드를 모두 새로 실행했다는 뜻은 아닙니다.
- **1.2.0 설치와 GUI**: `E_SIDEBAR_INLINE_INSTALL`은 현재 소스 payload로 실제 Obsidian에 1.2.0을 설치한 기록입니다. `E_SIDEBAR_INLINE_GUI`는 네 인라인 기능 창·세부 선택·질문·기간 입력·보조 동작·실제 의미 검색 결과 7건을 밝은·어두운 테마와 242px 폭에서 관찰하고 팝업 메뉴·모달이 없었음을 기록합니다. Vault Markdown 20개 해시와 플러그인 설정 상태를 보존하고 원래 테마·Home 대상·사이드바 폭을 복원했습니다(`E_SIDEBAR_INLINE_PRESERVATION`). 목표 `SIDEBAR_INLINE_SOURCE`·`SIDEBAR_INLINE_GUI`는 pass로 기록되어 있습니다.
- **Owner 시작·중지**: 실제 Vault 설정에 Thin Client를 설치하고 Obsidian CLI로 활성화해 Owner 중지(launchd 종료 코드 0)와 시작(health 정상)을 관찰했습니다(`E_OBSIDIAN_OWNER_LIFECYCLE`, 목표 `OWNER_LIFECYCLE` 통과).
- **콘솔**: 임시 Owner·합성 Vault·로컬 Temporal 개발 서버로 브라우저에서 정상 상태와 `job.pause`·`job.resume` 영수증 적용을 관찰했습니다(`E_CONSOLE_BROWSER`).

> [!note]
> **1.1.0 당시의 미확인 기록**: `E_SIDEBAR_NATIVE_MENUS`는 접근성 자동화 거부와 렌더러 DOM에 나타나지 않는 네이티브 팝업 때문에 당시 메뉴 내용을 확인하지 못한 blocked 이력입니다. 이 기록은 그대로 보존합니다. 현재 1.2.0은 팝업 대신 인라인 기능 창을 쓰며, 그 설치·GUI 관찰은 별도 `E_SIDEBAR_INLINE_*` 기록으로 구분합니다.

> [!note]
> README의 검증 범위에 따르면 자동 테스트는 `launchctl`과 Hermes를 가짜 실행 파일로 대체합니다. 실제 launchd 등록과 시작·중지, Obsidian GUI는 위 실환경 근거로 따로 기록됩니다.

C11 자체에 남은 명세 변경이나 열린 질문은 CAPABILITIES와 Blueprint §9에 없습니다. 프로젝트 전체의 남은 일은 "첫 자연 실행(시간별 규격화·임베딩)을 관찰하고 `related_min_score`를 조정하는 것"(handoff)이며, 이는 [[C3]]·[[C7]] 쪽 과제입니다. 전체 목록은 [[roadmap]]을, 검증 현황은 [[status]]를 보세요. 모바일 후속(M1–M3)은 아직 시작 전이라 C11 범위 밖입니다.
