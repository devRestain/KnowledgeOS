# C11 호출·관리 화면 (Invocation and management surfaces)

C11은 사용자가 KnowledgeOS를 부르고 관리하는 세 입구(**Obsidian Thin Client**, **브라우저 관리 콘솔**, **CLI**)와 **Owner 서비스 시작·중지**, 그리고 **자유 요청** 처리 흐름을 다룹니다. 세 입구는 모두 Owner의 로컬 HTTP 입구([[architecture]]의 ExOps)를 공유하지만, 버튼을 눌렀을 때 안쪽에서 타는 실행 길은 요청마다 다릅니다. 어떤 요청은 Work도 Temporal도 열지 않고 Owner가 곧바로 답하며, 어떤 요청만 `WorkWorkflow`, `ActionWorkflow`, 또는 Hermes 역할 Profile을 호출합니다.

## 한눈에 보기: 무엇을 누르면 어떤 길로 가는가

| 조작 | 접수와 영수증 | 실제 실행 경로 | Profile · 외부 서비스 |
|---|---|---|---|
| 사이드바 **찾기** (`의미 검색` · `관련 노트`), 상태 확인 | 영수증·Work 없이 동기 응답 | Owner가 직접 조회 | Profile 없음 (`의미 검색`은 로컬 Ollama, `관련 노트`는 설정 시 System One) |
| 제안 **적용 · 거절 · 되돌리기** (`review.*`) | 요청 영수증과 `actions` 기록 | Owner 접수 단계에서 즉시 처리·종결 (`WorkWorkflow` · `ActionWorkflow` · Graph 없음) | 없음 |
| 콘솔 **작업 취소 · 확인 기록 · 검토함 · 예약 제어** | 요청 영수증과 `actions` 기록 | Owner 접수 단계에서 즉시 처리 (`work.cancel`만 실행 중 Work에 취소 Signal 전송) | 없음 (`job.run`은 별도 자식 요청을 새로 접수) |
| **규격화 미리보기** (`standardize.preview`), CLI `standardize`, `index embed` | 요청 영수증과 Work 생성 | Temporal `WorkWorkflow` + 1단계 정적 Graph(`[Officer, evaluation]`) | Profile 없음 (`규격화` 규칙 9만 System One, `임베딩`은 Ollama) |
| 규격화 미리보기 **적용 · 취소** (`standardize.confirm`, `standardize.cancel`) | 요청 영수증과 `actions` 기록 | 대기 중 미리보기 Work를 `ActionWorkflow`로 재개 (Graph 없음) | 없음 |
| **정리 요청** (`organize`), **강화** (`enhance`) | 요청 영수증과 Work 생성 | Temporal `WorkWorkflow` + Manager가 짠 동적 LangGraph 구간 | 팀별 Hermes Profile(`kos-*`), 평가 `kos-eval` |
| **자유 요청** (`free_text`) | 원본 영수증 + 파생 요청 영수증 | System One 사전 거름 뒤 `kos-director`가 표준 명령 초안을 만들어 파생 요청 실행 | System One → `kos-director` (`gpt-6.1-sol`) → 대상 기능 경로 |

공통 실행 구조와 저장소 경계는 [[architecture]]에, 실제 호스트와 Obsidian에서 확인된 범위는 [[status]]에 정리되어 있습니다.

## Obsidian Thin Client: 사이드바와 명령

Thin Client(`knowledgeos-thin-client` **1.3.0**)는 명령 팔레트, 파일·편집기 문맥 메뉴, 오른쪽 사이드바 탭을 제공합니다. 플러그인 설정에는 Owner 주소(기본 `http://127.0.0.1:8765`, loopback HTTP만 허용)와 Owner launchd 라벨(기본 `com.agentfabric.knowledgeos.owner`) 두 가지만 있으며, 노트를 열거나 옮겨 다녀도 설정 파일은 고치지 않습니다([[SUR-2]]).

### 사이드바 화면과 대상 유지

리본의 KnowledgeOS 아이콘을 누르거나 명령 **KnowledgeOS: 사이드바 열기**를 실행하면 오른쪽에 탭 하나가 열립니다. 이미 열려 있으면 새 탭을 늘리지 않고 그 탭을 다시 보여 줍니다.

1. **대상 표시줄**: 맨 위에는 마지막으로 활성이던 Markdown 노트의 파일명이 보이고, 마우스를 올리면 전체 경로가 뜹니다. 사이드바 안을 클릭해 초점을 옮겨도 직전 노트가 대상으로 남고([[SUR-8]]), 다른 Markdown 파일을 열면 대상이 바뀌며, 대상 파일을 지우면 비워집니다. 열린 Markdown 노트가 없을 때는 노트 전용 버튼(**미리보기**, **정리 요청**, **발전 요청**, **관련 노트 찾기**, **되돌리기**)이 비활성화되고 노트 없이도 쓸 수 있는 **강화: 묻기**, **의미 검색**, **자유 요청**만 동작합니다.
2. **네 개의 이동 버튼과 인라인 영역**: **규격화**, **정리**, **강화**, **찾기** 버튼을 누르면 그 아래 인라인 기능 영역만 바뀝니다. **강화** 안의 발전·묻기·돌아보기 전환과 **찾기** 안의 의미 검색·관련 노트 전환 역시 이 영역 안에서 이뤄지며, 이동 버튼만 눌러서는 어떤 요청도 보내지 않습니다([[SUR-9]]).
3. **인라인 폼과 메모리 초안**: 질문 입력(**묻기**), 날짜 구간(**돌아보기**, 기본 최근 7일 `YYYY-MM-DD`), 검색어(**의미 검색**), 문장 입력(**자유 요청**)은 팝업 창 없이 기능 영역 안에 그려집니다. 빈 칸을 낸 채 요청하면 인라인으로 안내하고 초점을 옮겨 주며, 입력 중이던 글은 메모리에만 남아 다른 기능 버튼을 눌렀다 돌아와도 그대로 유지됩니다. 반면 명령 팔레트나 문맥 메뉴에서 부르면 작은 입력 창과 미리보기 창, 결과 선택 목록 모달이 열리고, 전송·확인 규칙은 사이드바와 같은 경로를 씁니다.
4. **규격화 미리보기·적용·취소**: **미리보기**를 누르면 Owner가 미리보기 Work를 실행해 변경 대상 노트의 diff와 함께 System One이 고른 항목(예: `System One: status → seed (93%)`)을 기능 영역 안에 보여 줍니다. 이때 미리보기 Work는 아직 파일에 쓰지 않고 사용자 확인을 기다리는 상태(`awaiting_confirmation`)로 멈춰 있습니다. 같은 자리에 나타나는 **적용**이나 **취소**를 누르면 버튼이 바로 잠겨 한 번만 요청되며, 확정 전에 다른 기능 버튼이나 다른 노트로 옮기면 사이드바가 해당 미리보기 ID를 자동으로 취소합니다. 뒤늦게 도착한 미리보기·검색 응답도 현재 열려 있는 기능 영역의 세대가 바뀌었으면 화면을 덮어쓰지 않고 미리보기는 즉시 취소합니다.
5. **제안 적용·거절 막대**: 대상 노트의 현재 frontmatter가 `type: proposal`일 때만 기능 영역 아래에 **적용**·**거절** 버튼이 나타납니다.
6. **더보기와 전원 버튼**: 하단의 `…` 버튼은 인라인 **자유 요청** 입력창과 **되돌리기**, **관리 콘솔**(브라우저에서 `http://127.0.0.1:8765/` 열기)을 펼칩니다. 전원 버튼은 관찰된 연결 상태에 따라 **Owner 중지**(연결됨) 또는 **Owner 시작**(연결 끊김)을 부르며, 연결을 확인 중이거나 시작·중지 전환 중일 때는 비활성화됩니다. 탭을 여는 것만으로는 Owner를 켜거나 끄지 않습니다.

## 버튼을 누른 뒤 요청·영수증·오류 흐름

문서 처리 명령을 제출하면 아래 순서로 요청과 영수증을 다룹니다. 단순한 기능 탭 이동은 실행 요청이 아니고, Owner 전원 조작은 아래의 launchd 경로를 사용합니다.

1. **대상은 경로와 해시로 전송**: 노트를 첨부하는 명령에서는 본문 대신 Vault 상대 경로와 방금 읽은 바이트의 SHA-256 해시를 보냅니다([[SUR-1]]). 질문·기간·자유 요청처럼 사용자가 폼에 쓴 값은 명령의 매개변수로 함께 보냅니다. 폴더나 여러 파일은 대상 Markdown 경로와 해시를 모읍니다. 각 실행 요청에는 중복을 구별할 무작위 요청 ID를 붙여 `POST /api/requests`로 전송합니다.
2. **영수증 먼저 커밋**: Owner는 요청 내용과 기능 카탈로그 버전을 합친 content digest를 계산해 State에 `received` 상태의 영수증을 배타적으로 먼저 저장한 뒤 HTTP `202`로 돌려줍니다. 같은 요청 ID와 같은 내용으로 다시 들어오면 새 작업을 만들지 않고 기존 영수증을 HTTP `200`으로 돌려주며, 같은 요청 ID에 다른 내용이 실리면 HTTP `409` 충돌 오류로 막습니다.
3. **백오프 폴링**: Thin Client는 `0.5초`에서 시작해 2배씩(최대 `5초`, 최장 30분) `GET /api/requests/{request_id}`를 조회해 영수증이 종결 상태(`completed`, `unmet`, `failed`, `refused`, `cancelled`, `unknown`)가 될 때까지 기다립니다(관리 콘솔은 `0.4초`에서 시작해 최대 `3초`, 60초까지 조회합니다). 처리 중에는 상태바에 `KOS 연결됨 · 진행 N`처럼 진행 건수가 표시됩니다.
4. **응답 유실과 결과 불명(`unknown`) 처리**: 요청 전송 중 연결이 끊기거나 시간 초과·`5xx` 오류가 나면 클라이언트는 **같은 요청을 새로 보내지 않고** 원래 요청 ID로 영수증 상태만 먼저 조회합니다. Owner가 `404`("기록된 적 없음")라고 확인해 준 경우에만 같은 요청 ID와 같은 본문을 한 번 다시 보냅니다. 반대로 영수증이 `unknown`으로 남았다면 재전송 허락이 아니므로 다시 실행하지 않고, 브라우저 콘솔의 **결과 불명** 탭이나 CLI `reconcile`로 사람이 실제 파일 상태를 확인해 기록합니다([[SUR-4]], [[c6]]).
5. **결과와 오류 표시**: 요청이 끝나면 사이드바 피드백 영역에 한국어 상태(`완료`, `기준 미충족`, `실패`, `거부됨`, `취소됨`, `결과 불명`)와 Owner의 안내 문구, 그리고 생성된 제안이나 보고서 경로가 클릭 가능한 링크로 뜹니다. 명령 팔레트나 문맥 메뉴에서 실행했을 때는 알림으로 표시되며, 실패·거부·결과 불명 알림은 사용자가 닫을 때까지 사라지지 않습니다.

## 자유 요청(`free_text`): System One 사전 거름 → `kos-director`

사이드바 **더보기**나 명령 팔레트의 **자유 요청**에 문장을 적어 보내면 정적 명령과 다른 2단계 접수 과정을 밟습니다.

1. **System One 사전 거름**: `settings.system_one`이 설정되어 있으면, Owner는 사용자가 입력한 문장만(최대 `max_input_chars` 8,000자, 노트 본문 미전송) OpenAI Decisions API(`gpt-6-luna`)로 보내 `free_text_command` 선택 질문 하나를 묻습니다. 선택지는 `config/capabilities/C11.json`이 허용한 `standardize.preview`, `organize`, `enhance`와 `none_of_these`입니다. 답이 `none_of_these`이고 확신도가 `min_confidence`(기본 `0.7`) 이상이면 **`kos-director`를 띄우지도, Work를 만들지도 않고** 즉시 `refused`로 끝납니다([[SUR-10]]). 실제로 `"오늘 서울 날씨 알려줘"` 같은 문장은 System One이 `none_of_these`(0.95)로 거절해 Director 호출 없이 끝났습니다([[status]]). 반대로 다른 명령을 골랐거나, 확신도가 낮거나, System One이 꺼져 있거나 오류가 나면(`"unavailable"`) 사전 거름 없이 다음 단계로 넘어가며 `kos-director`는 이 사전 판정을 보지 못합니다. 영수증 결과의 `system_one` 필드에 `{choice, confidence}` 또는 `"unavailable"`이 기록됩니다.
2. **`kos-director`의 명령 초안 작성**: `HermesRunner`가 `kos-director` Profile(`config/roles.json` 기준 `openai-codex/gpt-6.1-sol`, `reasoning_effort: high`)을 실행합니다. 이 세션에는 허용된 명령·모드·매개변수 목록과 정책으로 걸러진 대상 참조(`t1`, `t2`…)만 담긴 `catalog_view` 도구, 자신의 과거 접수 결과를 보는 `feedback` 도구, 그리고 제출 도구 `submit_workspec`만 주어집니다. 사용자가 문장에서 제목·위키링크·경로로 언급한 노트 중 `approve`인 일반 노트만 참조 목록에 오르며, `deny`·시스템·제안 노트와 모든 노트의 본문·실제 경로·ID·해시는 모델에게 감춥니다.
3. **권한 차단과 교정 턴**: `kos-director`가 완료 기준, 예산, 평가자, WorkSpec, 입력 연결, 모델 경로처럼 카탈로그와 Owner가 정하는 필드를 쓰려 들면 교정 턴 없이 권한 위반으로 즉시 거절되어 Work가 만들어지지 않습니다. 예약 작업, 검토(`review.*`), 작업 취소 명령으로도 연결할 수 없습니다. 단순한 매개변수 오류는 진단과 함께 교정 턴을 1회 주며, 두 번째에도 못 맞추거나 모델이 `{"refuse": "..."}`를 내면 이유를 알려 주고 Work 없이 거절됩니다([[SUR-3]]).
4. **파생 요청 실행**: 유효한 초안을 받으면 Owner가 `t1` 같은 대상 참조를 실제 경로와 현재 파일 해시로 채워 정식 접수합니다. 원래 ID에서 파생된 `freetext-...` 요청이 생기며, 이후에는 해당 기능 버튼을 직접 누른 것과 같은 길을 갑니다. 실행 대상이 있으면 Work와 Temporal로 이어지고, 대상이 없는 요청은 해당 기능의 즉시 종료 규칙을 따릅니다. 자유 요청의 원래 영수증에도 이 결과를 연결합니다.

## Owner 시작·중지와 서비스 설치 (LaunchAgent)

Owner는 Mac에서 Obsidian을 종료해도 살아 있지만 스스로 항상 켜져 있지는 않는 온디맨드 `LaunchAgent`(기본 라벨 `com.agentfabric.knowledgeos.owner`)로 설치해 씁니다.

1. **서비스 등록**: 터미널에서 `knowledgeos install service --config owner.json --dry-run`을 실행하면 생성될 plist 내용과 `launchctl` 명령 인자만 출력하고 아무것도 쓰지 않습니다([[SUR-7]]). `--dry-run` 없이 실행하면 `~/Library/LaunchAgents/<label>.plist`를 작성하고 `launchctl`에 적재합니다. `RunAtLoad`와 `KeepAlive`가 꺼져 있어 등록 직후에는 실행되지 않으며, 로그는 Runtime `logs/owner.out.log`와 `owner.err.log`에 남습니다.
2. **Owner 시작**: Thin Client의 전원 버튼이나 **Owner 시작** 명령은 먼저 `GET /api/health`로 이미 켜져 있는지 확인한 뒤, 꺼져 있으면 `launchctl kickstart`로 서비스를 깨우고 1초 간격으로 최대 60초 동안 `/api/health`의 `ready` 응답을 기다려 `"시작되었습니다 (health 정상)"`을 알립니다([[SUR-6]]).
3. **Owner 중지**: **Owner 중지**는 `launchctl kill SIGTERM`을 보낸 뒤 1초 간격으로 최대 30초 동안 `/api/health` 응답이 끊기기를 기다립니다. 시작 전부터 이미 응답이 없었다면 중지 여부를 단정할 수 없어 `unknown`으로 알리고, 30초 뒤에도 응답하면 `"아직 실행 중"`으로 알립니다. launchd가 관리하지 않고 터미널에서 직접 띄운 Owner가 응답 중이면 중지하지 않고 그대로 알려 줍니다. `knowledgeos serve` 프로세스도 `SIGTERM`을 받으면 스케줄러를 먼저 멈추고 진행 중인 접수를 마친 뒤 ExOps를 닫습니다.

## 브라우저 관리 콘솔과 CLI

### 브라우저 관리 콘솔

Owner의 ExOps가 `http://127.0.0.1:8765/`에서 직접 서빙하는 로컬 전용 페이지입니다. 모든 조회(`GET`)는 상태를 바꾸지 않으며, 노트 편집이나 제안 적용 같은 문서 작업은 할 수 없습니다.

- **9개 화면**: 상단 `Owner 상태`(15초마다 `/api/health` 갱신) 아래 **작업**(목록과 `#work/<id>` 상세: `WorkSpec`, `Graph 세그먼트`, `역할 호출`, `독립 평가`, `CompletionAssessment`, `RemainingWork`, `TeamReview`), **예약**(스케줄러 상태·실행 기록), **결과 불명**, **주의**(Bases로 볼 수 없는 중복 ID·충돌·깨진 YAML·낡은 제안·실패 작업), **알림**, **Experience**(로컬 `SourceEvent`와 전송 후보), **역할**(Profile·모델 경로·`SOUL`/`skill` 해시·학습 기록), **요청**(현재 브라우저 탭에서 보낸 관리 요청 추적) 탭이 있습니다.
- **4가지 관리 동작**: 작업 상세의 **작업 취소**(`work.cancel`), 예약 탭의 **일시정지**(`job.pause`)·**재개**(`job.resume`), 결과 불명 탭의 **확인 기록**(`outcome.reconcile`: `applied` 또는 `not_applied`, 과거 Work·영수증·불명 기록을 고치지 않고 사람의 관찰만 남김), `TeamReview` 제안의 **검토함 표시**(`teamreview.considered`) 모두 Thin Client와 같은 `POST /api/requests` 경로를 지납니다.

### CLI (`knowledgeos`)

운영자 유지보수·설치용 CLI는 `--config owner.json` 또는 `--endpoint URL`(기본 `http://127.0.0.1:8765`)로 Owner에 연결합니다.

| 명령 | 하는 일 |
|---|---|
| `knowledgeos serve --config owner.json` | Owner, Temporal Runtime, 스케줄러, ExOps 서버와 관리 콘솔 실행 |
| `knowledgeos health` | `GET /api/health` 상태를 JSON으로 출력 |
| `knowledgeos vault-check` | 깨진 YAML, 충돌 표시, 중복 ID 점검 결과 출력 |
| `knowledgeos index rebuild \| verify \| embed` | 키워드 색인 재구축, 의미 색인 준비 상태 점검, 남은 노트가 없을 때까지 `index.embed` Work 반복 실행 |
| `knowledgeos standardize PATH --dry-run \| --apply` | 폴더 또는 노트 대량 규격화(`--dry-run`은 계획과 diff만 출력하고 쓰기 없음, [[SUR-5]]) |
| `knowledgeos job run JOB` | `standardize`·`embed`·`curate`·`daily`·`digest` 중 하나를 트리거하고 별도 접수된 자식 요청 영수증까지 따라가 보고 |
| `knowledgeos reconcile UNKNOWN_ID --resolution applied\|not_applied --yes` | 결과 불명 항목에 사람의 확인 관찰 기록(효과를 재실행하지 않음) |
| `knowledgeos work export WORK_ID` | Work 기록 하나를 JSON으로 출력 |
| `knowledgeos install profiles \| service --config owner.json [--dry-run]` | Hermes Profile(`kos-*` + `kos-ops`) 설치 또는 macOS LaunchAgent 등록 |
