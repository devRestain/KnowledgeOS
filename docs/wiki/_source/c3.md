# C3 검색 (키워드·의미 검색·임베딩)

## 1. 한눈에 보기

C3는 노트를 **찾는** 기능입니다. 단어로 찾는 키워드 검색은 Obsidian 기본 검색이 맡고, KnowledgeOS는 그 위에 "관련 노트", 그리고 로컬 임베딩(글의 뜻을 숫자 벡터로 바꾼 값)을 쓰는 "의미 검색"을 Owner 서비스로 제공합니다. 같은 검색을 Team 역할(role)의 읽기 도구도 Work 안에서 씁니다.

의미 검색을 쓰려면 먼저 노트를 임베딩해 두어야 합니다. 이 일은 정적 코드인 EmbeddingOfficer가 `index.embed` 요청으로 처리하며, 결과(벡터 색인)는 Vault가 아니라 State에 쌓이는 **파생 데이터**입니다. 지워도 다시 만들 수 있습니다.

| 항목 | 내용 |
|---|---|
| 트리거 | Thin Client "관련 노트"·"의미 검색", 예약 작업 `embed`(매시 30분), CLI `knowledgeos index embed`, Work 안의 Team 역할 읽기 도구 |
| 담당 | Owner 서비스(검색), 정적 EmbeddingOfficer(임베딩), 정적 EvalOfficer(평가) |
| 결과물 | 제목·경로·종류·상태·발췌·줄 위치가 붙은 검색 결과 목록. 임베딩 결과는 `<State>/semantic/`의 벡터 색인 |
| 사용자 결정 여부 | 없음. 검색은 읽기 전용이고, Vault 노트를 바꾸지 않으며 제안도 만들지 않습니다 |

## 2. 왜 이 명세가 필요한가

검색은 사용자가 쓴 노트를 다시 꺼내 쓰게 하는 가장 기본적인 길이지만, 동시에 노트 내용이 처음으로 다른 프로세스(임베딩 서비스)에 건네지는 자리이기도 합니다. 그래서 이 명세는 USER_FEATURE_SPEC의 "지키는 약속" 가운데 다음을 직접 지킵니다.

- **Vault는 사용자의 것입니다(약속 1).** 검색 결과는 어떤 노트도 바꾸지 않습니다. frontmatter가 없는 Markdown도 그대로 검색 대상입니다. 이 명세가 없으면 색인을 위해 노트에 표시를 심는 식의 침범이 생길 수 있습니다.
- **잃으면 안 되는 것은 Vault에 둡니다(약속 6).** 벡터는 State 아래 `<State>/semantic/`에만 두고 Vault나 Git에 올리지 않습니다. State를 잃어도 다시 임베딩하면 되고 지식은 남습니다.
- **근거를 밝힙니다(약속 7).** 모든 결과에 줄 위치가 붙고, 의미 검색에는 가장 비슷한 조각의 끝 줄과 유사도 점수도 붙습니다. 관련 노트는 링크·백링크·공통 태그·의미 이웃 중 **어떤 이유**인지 표시합니다.
- **하지 않는 일: "의미 검색이 안 될 때 키워드 결과로 몰래 대체하기"를 금지합니다.** 준비가 안 됐으면 "unavailable"이라고 알리고 결과를 내지 않습니다. 사용자가 의미 검색 결과로 오해하지 않게 하려는 규칙입니다.
- **개인정보 `ai_policy`.** 검색은 표면마다 독자(사람, 역할, 외부 Gateway)에 맞는 필터를 통과해야 합니다. `deny` 노트는 어떤 모드·어떤 표면에서도 나오지 않습니다. 용어는 [[glossary]], 정책 원칙은 [[philosophy]]를 보세요.

> [!note]
> 임베딩은 모델을 호출하는 일이 아니라 로컬 결정적 처리로 분류됩니다(Blueprint §5.4). 그래서 `local_only`·`confidential` 노트와 보고서도 임베딩 대상이 됩니다. 이 노트들의 내용은 loopback 주소의 로컬 Ollama에만 가고, 게이트웨이나 원격 모델에는 가지 않습니다.

> [!warning]
> **이웃 거르기(System One)는 임베딩과 다릅니다.** 설정되어 있으면 관련 노트가 의미 이웃에 `semantic` 이유를 붙이기 전에, 중심 노트와 이웃의 제목·가장 비슷한 조각의 발췌를 원격 모델 System One에게 보내 "정말 의미 있게 관련된 노트인가"를 묻습니다. 그래서 이 단계는 정책을 따릅니다. 사용자가 직접 보는 화면은 `remote_ok`·`ask` 노트를, 역할과 예약 작업의 출처는 `remote_ok` 노트만 보내고, `local_only`·`confidential`·`deny` 노트는 보내지 않습니다. 보낼 수 없는 이웃은 거르지 않은(unvetted) 코사인 결과로 남습니다.

## 3. 어떻게 쓰는가

### Obsidian Thin Client·사이드바

1. 키워드로 찾을 때는 Obsidian 기본 Search를 씁니다. KnowledgeOS가 필요 없고 한국어·영어 부분 단어도 찾습니다.
2. 열어 둔 노트와 이어진 노트를 보려면 사이드바에서 **찾기 → 관련 노트**를 선택한 뒤 **관련 노트 찾기**를 누릅니다. 링크, 백링크, 공통 태그, 의미 이웃이 이유 라벨과 함께 같은 기능 창에 나옵니다. 명령 팔레트의 **관련 노트**는 기존 선택 창을 사용합니다.
   - System One이 설정되어 있으면 의미 이웃은 **거르기**를 거칩니다. 확률이 `related_min_probability`(기본 0.5) 이상이면 `semantic` 이유가 `vetted: true`로 표시되고, 미만이면 `semantic`을 잃고 링크·백링크·태그 이유도 없으면 목록에서 사라집니다([[SRC-9]]). System One이 꺼져 있거나 실패하면 거르지 않은 코사인 이웃 목록이 그대로 나옵니다.
3. 질문이나 말로 찾으려면 사이드바에서 **찾기 → 의미 검색**을 선택하고 아래 검색창에 질문을 입력해 제출합니다. 유사도 순 결과가 같은 영역에 표시되고, 결과 링크를 누르면 해당 노트의 줄 위치가 열립니다. 명령 팔레트의 **의미 검색**은 기존 입력창·선택 창을 사용합니다.
4. 의미 검색이 준비되지 않았으면 "unavailable"과 빈 결과가 나옵니다. 이는 오류가 아니라 규칙입니다([[SRC-3]]).

요청에는 노트 경로와 마지막으로 본 내용의 해시만 실리고 본문은 가지 않습니다([[SUR-1]]). 사이드바에는 노트가 없어도 의미 검색이 활성 상태이고, 관련 노트는 대상 노트가 있어야 합니다([[c11|C11]]).

### 자동·CLI·콘솔

- **자동**: 예약 작업 `embed`가 매시 30분에 `index.embed`를 요청합니다(행위자 `schedule/embed`). Owner가 켜져 있는 동안에만 실행됩니다. 자세한 일정 규칙은 [[c7|C7]]을 보세요.
- **CLI**: `knowledgeos index embed`가 남은 노트가 없을 때까지 반복해 임베딩합니다. `knowledgeos index rebuild`·`index verify`는 색인 재구축·점검입니다.
- **준비 상태 확인**: `knowledgeos index verify`는 `semantic` 항목에 대상(eligible)·임베딩(embedded)·오래됨(stale)·누락(missing)·대상 아님(extra) 수를 노트 경로 없이 보여 줍니다. `GET /api/health`의 `search_semantic`도 같은 준비 상태를 알립니다.
- **설정**: `settings.C3.semantic`에서 `ollama_url`(기본 `http://127.0.0.1:11434`, loopback이 아니면 설정 오류), `model`(기본 `qwen3-embedding:8b-q4_K_M`), `batch_size`, `timeout_seconds`, `max_notes`, `related_neighbors`(기본 5), `related_min_score`(기본 0.5), `related_min_probability`(기본 0.5, System One이 이웃을 거르는 기준)를 정합니다. `ollama_url`이나 `model`을 비우면 의미 검색이 설정되지 않은 상태가 됩니다. System One 자체의 설정(`settings.system_one`)은 [[glossary]]의 System One 항목을 보세요.

### 작동 예시

1. 새 노트 `사고실험 노트.md`에 "사고실험"이라는 단어를 쓰고 저장합니다. Obsidian 검색에서 "사고"를 찾으면 그 줄이 나옵니다([[SRC-1]]). KnowledgeOS 검색 도구도 같은 줄 위치를 돌려줍니다.
2. 그 노트는 아직 임베딩되지 않았으므로 의미 검색·관련 노트의 의미 이웃에는 나오지 않습니다([[SRC-5]]).
3. 다음 매시 30분에 `embed` 작업이 돌면 이 노트만 임베딩되고, 변하지 않은 노트는 비용이 없습니다.
4. "생각을 실험으로 시험하는 방법"처럼 질문을 의미 검색에 입력하면, 질문 텍스트만 임베딩되어 노트의 가장 비슷한 조각과 비교됩니다. 사이드바의 결과 링크나 명령 팔레트의 결과 선택 창에서 고르면 그 조각의 줄로 이동합니다([[SRC-7]]).
5. Ollama가 꺼진 채 `embed` 작업이 돌면 작업이 실패로 남고, 이미 만든 벡터는 유지되며 다음 실행에서 남은 것만 이어서 임베딩합니다([[SRC-8]]).

## 4. 동작 흐름

임베딩과 검색은 한 줄기로 이어집니다. 먼저 대상 노트를 가리고(적격성), 조각으로 나누어, 로컬 Ollama로 임베딩하고, State에 벡터를 저장한 뒤, 검색과 관련 노트가 그 벡터를 읽습니다.

{{svg:semantic-pipeline}}

- 적격성은 임베딩 직전 노트의 **현재 내용**으로 다시 검사합니다. 그사이 대상이 아니게 된 노트는 보내지 않고 버립니다.
- 노트의 의미 이웃은 이미 저장된 벡터를 쓰므로 임베딩 요청이 필요 없습니다. 의미 검색만 질문 텍스트를 한 번 임베딩합니다.
- **이웃 거르기**(System One 설정 시): 관련 노트 화면, Team 역할의 `related` 도구, [[c1|C1]] `scout`와 [[c4|C4]] `retriever`의 후보가 모두 같은 거르기를 씁니다. 중심 노트 하나와 이웃 전체를 한 요청에 담아 이웃마다 "관련 있는가" 확률을 묻습니다. 판정은 중심 노트 내용·이웃 내용·모델 조합마다 메모리에 캐시되어, 바뀌지 않은 노트에 같은 호출을 반복해도 새 요청이 나가지 않으며, 읽기라서 State에 아무것도 쓰지 않습니다([[SRC-9]]).

## 7. 현재 상태와 남은 일

- **구현과 추적**: C3의 인수 시나리오 SRC-1~SRC-9는 모두 추적표에 구현 위치와 테스트가 연결되어 있습니다(전체 68개 인수 예시·68행·195개 pytest 노드, `E_SYSTEM_ONE_TRACE`. 전체 테스트 277개 통과는 `E_SYSTEM_ONE_TESTS`, [[status]]).
- **실환경 근거**: `E_REAL_SEMANTIC`(PROJECT_STATE)는 로컬 Ollama `qwen3-embedding:8b-q4_K_M`로 적격 노트 7개를 21개 조각으로 27초에 임베딩하고, Obsidian Thin Client에서 줄 위치가 붙은 순위 결과를 돌려준 것을 기록합니다. 목표 `KNOWLEDGEOS_REAL_ADOPTION.SEMANTIC`은 pass입니다.
- **예약 실행**: `E_REAL_SCHEDULER_SLOT`은 임시 20:40 `index.embed` 작업이 시작 3분 지연 뒤 정확히 한 번 돈 것을 기록합니다. 다만 실제 `embed`(매시 30분)의 자연스러운 슬롯 실행은 아직 관찰하지 못했습니다.
- **남은 일**(PROJECT_STATE의 열린 인계): "열린 정리 제안을 검토하고, 첫 자연 시각의 매시 standardize 실행을 System One과 함께 관찰하며, `related_min_score`·`related_min_probability`·`min_confidence`를 실제 노트에 맞춰 조정"하는 일입니다. 0.5는 시작값이며(기능 명세 C3도 같은 말을 합니다), 모델이 바뀌면 다시 조정해야 합니다. 실제 시각의 `embed` 슬롯 관찰은 위 "예약 실행" 항목에 따로 적었습니다.
- **System One 거르기의 실환경 근거**: 실제 Owner에서 관련 노트 검색이 후보를 0.3초에 거른 것이 `E_SYSTEM_ONE_LIVE`에 기록되어 있습니다. 결과 3건 중 의미 이웃 2건이 `vetted: true`로 표시됐고 나머지 1건은 백링크 이유뿐이라 거르지 않은 상태였습니다. Vault Markdown 22개 해시는 그대로였습니다(`E_SYSTEM_ONE_PRESERVATION`). 이 한 번의 관찰은 `related_min_probability` 0.5가 실제 노트에 맞는지를 증명하지 않습니다.
- **GUI 근거의 버전 경계**: 인라인형 사이드바 1.2.0은 설치(`E_SIDEBAR_INLINE_INSTALL`)와 GUI 관찰(`E_SIDEBAR_INLINE_GUI`)이 기록되어 있습니다. 네 기능 영역, 세부 선택, 질문·날짜 입력, 보조 동작, 실제 의미 검색 결과 7개를 라이트·다크·폭 242px에서 확인했습니다. 이후 System One 결정 줄을 그리는 1.3.0이 활성 플러그인 폴더에 설치되었고(`E_SYSTEM_ONE_CLIENT_INSTALL`) 규격화 미리보기 화면을 관찰했습니다(`E_SYSTEM_ONE_CLIENT_GUI`). 다만 그 관찰은 화면 잠금 때문에 사이드바 영역의 CDP 렌더이고, 관련 노트·의미 검색의 거르기 결과를 1.3.0 GUI에서 따로 관찰한 기록은 없습니다. `E_SIDEBAR_NATIVE_MENUS`의 blocked는 구형 1.1.0의 네이티브 팝업 내용을 확인하지 못했던 이력이며, 인라인 UI가 미확인이라는 뜻은 아닙니다.
- **명세 정리**: 벡터 색인은 State(`semantic/`)에 두고, 검색 자체는 Owner 서비스이며 색인을 최신으로 유지하는 일만 정적 EmbeddingOfficer가 맡습니다. Blueprint §2·§4.2도 이렇게 맞췄고, "어떤 임베딩 모델을 쓸지"라는 §9 열린 질문은 닫혔습니다. 남은 열린 질문은 실제 노트에서 `related_min_score`·`related_min_probability`와 이웃 수가 적절한지입니다.

더 넓은 진행·후속 과제는 [[roadmap]]에 있습니다.

## 8. 관련 기능

- [[c7|C7 예약 작업]]: `embed` 작업이 매시 30분에 `index.embed`를 요청합니다. Owner가 꺼져 있으면 실행되지 않고, 켜진 뒤 놓친 것을 한 번만 실행합니다.
- [[c1|C1 정리]]: 예약 정리(scheduled C1)에 묶인 역할 도구는 의미 이웃으로 `remote_ok`이면서 보고서가 아닌 노트만 받습니다([[SRC-7]]).
- [[c4|C4 강화]]: Thinking Team의 읽기·검색 도구가 이 검색 서비스를 씁니다. 역할 도구는 보고서를 돌려받지 않습니다.
- [[c10|C10 Gateway]]: 외부 조회는 `remote_ok`이면서 보고서가 아닌 노트만 응답합니다.
- [[c11|C11 호출·관리 표면]]: "관련 노트·의미 검색"이 Thin Client 명령, 사이드바 "찾기"와 CLI `index` 명령으로 노출됩니다.
