# C3 검색 (키워드 · 의미 검색 · 임베딩)

C3는 Vault 노트를 찾는 읽기 서비스와, 로컬 임베딩 벡터 색인을 최신 상태로 유지하는 작업을 함께 다룹니다. 사람이 단어로 노트를 찾을 때는 Obsidian 기본 Search를 쓰고, KnowledgeOS는 그 위에 Owner의 검색 서비스(**키워드·의미 검색·관련 노트**)와, 로컬 Ollama(`qwen3-embedding:8b-q4_K_M`)로 벡터를 만드는 **임베딩 관리 Work**를 제공합니다. 같은 검색 엔진을 [[c1]] 정리 팀과 [[c4]] 강화 팀의 읽기 도구, [[c10]] Gateway 조회도 함께 사용합니다.

## 1. 직접 검색과 임베딩 Work는 경로가 다릅니다

C3의 모든 호출이 Work나 Temporal을 거치는 것은 아닙니다. 읽기 검색은 Owner가 즉시 답하고, Vault 전체를 스캔해 로컬 Ollama로 벡터를 계산해 State에 쓰는 일만 Work로 실행합니다([[architecture]]).

| 경로 | 무엇이 실행되는가 | Hermes Profile | Graph / Temporal |
|---|---|---|---|
| 사람 검색 (`POST /api/search`) | Thin Client의 **의미 검색**·**관련 노트** 요청을 Owner 메모리·벡터 색인이 동기 처리 (관련 노트만 필요 시 System One 직접 호출) | 없음 | 없음 (직접 호출, Work 없음) |
| 팀 역할 도구 (`search`, `related`) | [[c1]]·[[c4]] 팀 Work 안에서 역할이 호출하면 Owner 검색 서비스가 결과를 `e1` 같은 **근거 핸들**로 감싸 반환 | 호출하는 팀원 세션은 있으나 검색 자체에 별도 Profile 없음 | 검색 자체에 새 Graph·Workflow 없음 (소속 팀 Work의 증거 표에 핸들 등록) |
| 색인 점검·재구축 (`index verify`, `index rebuild`) | 디스크와 메모리 색인·`<State>/semantic/` 대조 또는 메모리 색인 재구성 | 없음 | 없음 |
| Gateway 조회 (`POST /interops/query`) | 승인된 외부 Operation에 `approve` 비보고서 노트의 키워드 결과만 반환 | 없음 | 없음 |
| 임베딩 갱신 (`index.embed`) | 매시 30분 `embed` 예약 작업([[c7]]) 또는 `knowledgeos index embed` CLI가 호출. 할 일이 없으면 접수에서 즉시 종료(`work_id` 없음). 할 일이 있을 때만 정적 `EmbeddingOfficer`와 정적 `EvalOfficer` 실행 | 없음 (`kos-eval`도 미호출) | `EmbeddingOfficer → evaluation` **1개 생산자 직렬 LangGraph** + `WorkWorkflow` |

## 2. 세 가지 검색 모드와 정책·청중 필터

Owner 안의 검색 색인은 재구축할 수 있는 메모리 데이터입니다. 어떤 검색이든 요청이 들어오면 먼저 Vault의 모든 `.md` 파일을 `stat`으로 훑어 **파일 크기·수정 시각이 바뀐 노트만** 다시 읽고 파싱합니다([[SRC-4]]). `.`으로 시작하는 숨김 경로, `80_Assets/`, `.gitignore` 제외 경로는 색인하지 않습니다. `ai_policy: deny`이거나 퇴역·알 수 없는 정책값(빠지거나 빈 값만 `approve`)을 가진 노트는 파일 식별자만 남기고 제목·본문·태그를 색인에 올리지 않으므로, **어느 모드와 어느 표면에서도 절대 검색되지 않습니다**([[SRC-2]]).

노트 종류에 따른 노출 범위(**청중 필터**)도 표면에 따라 다릅니다.

- **사람 표면(`people`, Thin Client·콘솔)**: `99_System/` 아래 파일과 `type: proposal`(또는 `01_AI_Review/Proposals/` 아래) 제안 노트를 제외하며, `01_AI_Review/Reports/`의 보고서(`report`)는 검색 결과에 포함합니다.
- **역할 표면(`role`, 팀 도구·Gateway)**: 사람 표면 조건에 더해 **보고서(`type: report`)도 제외**합니다([[ENH-5]]). 모델이 과거 보고서를 다시 근거로 순환 인용하지 않도록 하기 위함이며, 사용자가 보고서의 `type`을 다른 종류로 바꾼 뒤에만 포함됩니다.

### 키워드 모드 (`keyword`)

Thin Client는 키워드 검색을 Obsidian 기본 Search에 맡기므로, KnowledgeOS의 `keyword` 모드는 주로 팀 역할의 `search` 도구, `scout`·`retriever`의 후보 보강, 그리고 [[c10]] Gateway 조회가 씁니다. 검색어를 공백으로 나눈 모든 단어가(대소문자 구분 없이) 노트의 제목 또는 본문 줄에 부분 문자열로 들어 있어야 일치합니다. 예를 들어 한국어 `"사고"`를 찾으면 본문의 `"사고실험"` 줄이 바로 걸립니다([[SRC-1]]). 순위는 **제목에 모든 검색어가 들어간 노트(가중치 +100) + 본문 일치 줄 수**가 높은 순이며, 결과에는 일치한 첫 본문 줄 번호(`line`)와 검색어 주변 160자 발췌가 붙습니다.

### 의미 검색 (`semantic`)

Thin Client **찾기 → 의미 검색**에서 질문을 제출하면 `POST /api/search`(`mode: "semantic"`)가 실행됩니다. 이미 임베딩된 노트는 다시 임베딩하지 않고, **질문 문장만** 앞에 검색 지시문(`Instruct: Given a search query, retrieve the notes that answer or relate to it\nQuery: `)을 붙여 앞 8,000자까지 로컬 Ollama `POST /api/embed`에 1회 요청합니다.

반환된 질문 벡터와 저장된 모든 노트 조각 벡터 사이의 코사인 유사도를 계산해 **노트마다 가장 점수가 높은 조각 하나만** 고르고, 현재 디스크 내용 해시(`sha`)가 색인 시점과 같으며 청중·정책 필터를 통과한 노트만 상위 `limit`(기본 20, 최대 100)개까지 돌려줍니다([[SRC-7]]). 결과 항목에는 조각의 시작 줄(`line`), 끝 줄(`end_line`), 유사도(`score`), 조각 본문 발췌(최대 160자)가 포함되므로, 사이드바에서 클릭하면 해당 조각의 첫 줄로 바로 이동합니다.

중요한 규칙으로, 설정이 비어 있거나, 설정된 모델로 임베딩된 노트가 하나도 없거나, Ollama 연결 실패·차원 불일치가 나면 `{status: "unavailable", results: []}`를 반환하며 **키워드 검색 결과로 몰래 대체하지 않습니다**([[SRC-3]]).

### 관련 노트 (`related`)

Thin Client **찾기 → 관련 노트 → 관련 노트 찾기**, 팀 역할의 `related` 도구, [[c1]] `scout`, [[c4]] `retriever`(`develop`·`ask`·`review`)가 같은 계산을 씁니다. 지정한 중심 노트가 청중·정책 필터를 통과하면 다음 네 가지 출처를 합칩니다.

1. `link`: 중심 노트의 frontmatter 링크 속성과 본문 `[[...]]` 위키링크가 가리키는 노트.
2. `backlink`: 다른 허용 노트의 줄 중 중심 노트를 위키링크로 가리키는 노트와 그 첫 번째 줄 번호.
3. `tag:<태그>`: 중심 노트와 대소문자 무시 기준으로 겹치는 태그가 있는 노트.
4. `semantic`: 의미 색인이 준비되어 있을 때, 중심 노트의 **모든 조각 벡터를 평균 내 정규화한 중심 벡터**와 코사인 유사도가 가장 가까운 이웃 노트(이 계산은 저장된 벡터끼리 내적하므로 **Ollama를 부르지 않습니다**).

후보가 모이면 **이유 종류 개수 내림차순 → 의미 유사도 내림차순 → 경로 사전순**으로 정렬합니다. 의미 이웃이 System One 거르기를 통과한 경우에는 `vetted: true` 표시가 함께 붙습니다.

## 3. 로컬 Ollama 임베딩과 벡터 신선도 관리

의미 색인의 원본 파생 파일은 Vault나 Git 밖인 **`<State>/semantic/`** 에만 저장됩니다. `manifest.json`에는 현재 색인 모델명과 노트별 `sha`·조각 줄 범위·벡터 파일명이 적히고, `vectors/<경로해시20>-<내용해시20>.npy`에는 L2 정규화된 `float32` 조각 행렬이 들어갑니다. State를 지워도 지식은 잃지 않으며 다시 임베딩하면 복구됩니다.

### 적격성과 조각 분할

`EmbeddingOfficer`는 `ai_policy`가 `approve`(누락·빈 값 포함)인 노트만 임베딩합니다. `sensitivity: confidential` 노트나 `01_AI_Review/Reports/`의 보고서도 `approve`라면 임베딩 대상에 들어갑니다. 반면 ① `deny`·퇴역·알 수 없는 정책값, ② `99_System/` 아래 파일, ③ `type: proposal`이거나 `01_AI_Review/Proposals/` 아래 제안 노트, ④ Git 병합 충돌 표시가 있는 노트는 절대 임베딩하지 않습니다([[SRC-6]]).

적격 노트는 frontmatter를 제외한 본문만 1-based 줄 번호를 유지하며 약 **1,500자**(`CHUNK_CHARS`) 창으로 나눕니다. Markdown 제목(`#`~`######`) 줄이 나오면 현재 조각에 본문 텍스트가 있을 때 새 조각을 시작하고(연속된 제목은 뒤 문단에 붙음), 한 섹션이 1,500자를 넘으면 직전 빈 줄(문단 경계)이나 줄 경계에서 자릅니다. Ollama에 보내는 실제 입력 문자열은 `"<제목>\n\n<조각 본문>"`의 앞 8,000자입니다.

### 신선도(freshness)와 모델 변경 규칙

`manifest.json`이 곧 **신선도의 기준점**입니다.

- **편집한 노트의 즉시 탈락**: 검색과 관련 노트 이웃 계산은 매번 현재 Vault 파일의 SHA-256과 manifest에 적힌 `sha`를 비교합니다. 노트를 한 줄이라도 고쳐 저장하면 다음 `index.embed`가 돌기 전까지 그 노트는 의미 검색 결과와 의미 이웃에서 **즉시 빠지며**, 키워드 검색만 새 본문을 반영합니다([[SRC-5]]).
- **증분 임베딩과 삭제**: `index.embed`를 실행하면 변경되지 않은 노트는 비용 없이 건너뛰고, 새롭거나 수정된 적격 노트만 **최근 수정 시각 순**(`-mtime`)으로 최대 `max_notes`(기본 100)개씩 스냅샷해 `Work`를 만듭니다. 삭제되었거나 이름이 바뀌었거나 `deny`·제안·충돌로 부적격해진 노트는 제거 목록으로 들어가 벡터와 `.npy` 파일이 정리됩니다.
- **보내기 직전 재확인**: Work의 `finish` 단계가 실제로 Ollama `POST /api/embed`에 조각 배치를 보내기 바로 전, 디스크에서 현재 파일을 다시 읽어 아직 적격인지 확인합니다. 접수 후 `deny`로 바뀐 노트는 Ollama에 보내지 않고 기존 벡터도 삭제합니다.
- **모델 변경 시 무효화**: 설정의 `model`을 다른 모델로 바꾸면 `manifest.json`의 모델과 불일치하므로 `ready`가 꺼지고 의미 검색이 `unavailable`이 됩니다. 이후 새 모델로 첫 노트가 임베딩되는 시점에 이전 모델의 모든 엔트리와 벡터 파일이 비워집니다([[SRC-3]]).

### 시간 제한과 실패 시 동작

한 번의 `index.embed` Work는 Activity 실행 시간(`activity_timeout_seconds`, 기본 120초; 실제 호스트 설정 600초)에서 요청 제한 시간(`timeout_seconds`, 기본 60초)과 여유 10초를 뺀 시점까지만 새 노트를 시작합니다. 도중에 20개마다(`CHECKPOINT_NOTES`), 그리고 종료 시점에 `manifest.json`을 원자적으로 갱신해 이미 끝낸 노트는 잃지 않습니다.

Ollama 서버가 꺼져 있거나 HTTP 오류·잘못된 벡터·차원 불일치가 발생하면 **그 즉시 작업을 `failed`로 멈추고 같은 실행 안에서 재시도하지 않습니다**([[SRC-8]]). 앞서 저장해 둔 다른 노트의 벡터는 그대로 살아 있으므로 기존 노트 사이의 `related` 의미 이웃은 계속 작동하며, 다음 매시 30분 실행이나 CLI 실행에서 남은(`pending`) 노트부터 이어서 임베딩합니다. CLI `knowledgeos index embed`는 `pending`이 0이 되거나 더 이상 진전이 없을 때까지 여러 번의 `index.embed` Work를 자동으로 이어 실행합니다.

## 4. System One 이웃 거르기와 주요 설정·임계값

단순히 비슷한 단어가 겹쳐 코사인 유사도가 높게 나온 이웃을 걸러 내기 위해, `settings.system_one`이 설정되어 있으면 사람 표면의 `related`, 팀 역할의 `related` 도구, [[c1]] `scout`, [[c4]] `retriever`(`develop`·`ask` 모드)가 의미 이웃을 반환하기 전에 **System One**(`gpt-6-luna`, Hermes Profile 없음)으로 2차 확인을 합니다([[SRC-9]]).

1. **전송 직전 재확인**: 코사인 유사도 후보(`related_neighbors`개)를 얻은 뒤, 중심 노트와 각 후보 노트를 디스크에서 다시 읽어 `sha`가 색인 시점과 같고 현재 `ai_policy`가 `approve`인지 확인합니다. `deny`이거나 도중에 바뀐 후보는 제외합니다.
2. **메모리 캐시와 단일 요청**: `(중심 sha, 후보 sha, System One 모델)` 조합이 메모리 캐시(최대 4,096건)에 있으면 재사용하고, 처음 보는 후보들만 모아 중심 노트 1개 + 후보별 제목(200자)과 가장 비슷한 조각 발췌(600자)를 담은 `predicate` 질문 묶음으로 `POST /v1/decisions`를 **1회** 호출합니다.
3. **State 무기록**: 읽기 요청(`ref=None`)이므로 State의 `system_one.jsonl`에 아무것도 쓰지 않고 로그만 남깁니다.
4. **확률 판정과 탈락 규칙**: 응답 확률이 `related_min_probability`(기본 `0.5`) 이상이면 `"semantic"` 이유와 `vetted: true`를 유지합니다. 기준 미만이면 `"semantic"` 이유를 제거하므로, 링크·백링크·공통 태그 이유가 함께 있는 노트는 그 이유만으로 목록에 남고 의미 이웃뿐이던 노트는 결과에서 빠집니다.
5. **실패 fallback**: System One이 꺼져 있거나 응답 오류·거절이 나면 그 후보는 판정하지 않고 **원래 코사인 이웃(`semantic`, `vetted` 없음)** 그대로 돌려줍니다.

결과 품질과 처리 범위를 좌우하는 설정(`settings.C3.semantic`)은 다음과 같습니다.

| 설정 키 | 기본값 | 역할과 바꿨을 때의 결과 |
|---|---|---|
| `ollama_url` | `http://127.0.0.1:11434` | 로컬 Ollama 주소. 비우면 의미 검색 미설정, `127.0.0.1`·`localhost`·`::1` 외의 `http` 주소는 시작 시 설정 오류 |
| `model` | `qwen3-embedding:8b-q4_K_M` | 임베딩 모델. 바꾸면 새 모델로 다시 임베딩할 때까지 `unavailable` |
| `batch_size` | `16` | 한 번에 Ollama로 묶어 보내는 조각 수 |
| `timeout_seconds` | `60` | Ollama 요청당 제한 시간(초) |
| `max_notes` | `100` | `index.embed` 1회 Work가 가져가는 최대 노트 수 |
| `related_neighbors` | `5` | `related`가 뽑는 의미 이웃 최대 후보 수 |
| `related_min_score` | `0.5` | 중심 노트 평균 벡터와 후보 조각 간 최소 코사인 유사도(`-1`~`1`). 높이면 후보가 줄고 낮추면 늘어남 |
| `related_min_probability` | `0.5` | System One이 실제 관련 있음으로 통과시키는 최소 확률(`0`~`1`). 높이면 거르기가 엄격해짐 |

## 5. 실제 입력과 결과 예시

### 예시 1: 새 노트 저장, 임베딩 전·후 검색, Ollama 중단

`40_Knowledge/Ideas/사고실험 노트.md`에 `"오늘의 사고실험"`이라는 문장을 저장합니다.

- **임베딩 전**: Obsidian Search와 Owner `keyword` 검색에서 `"사고"`를 찾으면 즉시 그 줄 번호(`line`)를 돌려주지만, 아직 벡터가 없으므로 `semantic` 검색과 `related` 의미 이웃에는 나오지 않습니다([[SRC-1]], [[SRC-5]]).
- **매시 30분 `embed` 후**: `EmbeddingOfficer`가 이 노트만 조각내 Ollama로 임베딩해 `<State>/semantic/`에 저장합니다. 이제 **찾기 → 의미 검색**에 `"생각을 실험으로 시험하는 방법"`이라고 물으면, 질문만 임베딩한 뒤 가장 가까운 조각의 `line`·`end_line`·`score`·발췌를 보여 줍니다([[SRC-7]]).
- **Ollama가 꺼진 경우**: 새 노트 하나를 추가한 뒤 Ollama를 끈 채 `index.embed`가 돌면 그 실행은 `failed`(`unreachable`)로 끝나지만, 기존 노트들의 벡터는 보존되어 `related` 의미 이웃은 계속 나오고, Ollama를 다시 켠 뒤 실행하면 빠진 노트 1개만 이어서 임베딩합니다([[SRC-8]]).

### 예시 2: 관련 노트의 System One 이웃 거르기

중심 노트 `Focal.md`와 같은 어휘를 공유하는 `Good.md`(`approve`), `Bad.md`(`approve`), `Local.md`(퇴역 정책 `local_only` → `deny` 처리)가 모두 비슷한 코사인 유사도를 가진 상황이라고 합시다. **찾기 → 관련 노트**를 누르면 `Local.md`는 애초에 제외되어 System One에 전송되지 않습니다. System One이 `Good.md`에 0.9, `Bad.md`에 0.1을 답하면 결과에는 `Good.md`만 `reasons: ["semantic"], vetted: true`로 남고 `Bad.md`는 빠집니다. 곧바로 같은 노트에 **관련 노트 찾기**를 한 번 더 누르면 메모리 캐시를 타므로 System One에 새 요청을 보내지 않습니다([[SRC-9]]).
