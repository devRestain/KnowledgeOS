# C9 학습·Experience

C9는 KnowledgeOS의 모델 역할이 사용자의 실제 반응에서 점진적으로 판단을 다듬고, 근거가 뚜렷한 실패나 교정 사건만 별도 분석 Operation인 **HermesTrace**와 공유하는 기능입니다. 사용자가 따로 켜는 버튼은 없습니다. 평소처럼 제안을 적용·거절하거나 보고서를 고치고 지우면 Owner가 그 결과를 세 층으로 나누어 기록합니다.

1. **역할 수준(`feedback` + 개별 Hermes 프로필)**: 각 모델 역할이 자기 책임 범위 안에서 과거 출력의 성적표를 보고 학습합니다.
2. **팀 수준(`TeamReview` 로컬 관찰)**: 팀 작업이 끝난 뒤 Manager가 팀원을 평가하고 개선 제안을 남기되, 이 제안은 로컬 관찰 기록으로만 머무릅니다.
3. **Fabric 수준(`ExperienceCandidate` 전송)**: 실제 근거가 있는 사건만 선별해 본문 없이 참조·분류·다이제스트 형태로 HermesTrace에 전달합니다.

## 런타임 접점 (Hermes · Graph · Temporal)

| 구성 요소 | 어디서 실행되는가 | 런타임 접점 |
|---|---|---|
| 역할 피드백 기록·보고서 감시·Candidate 추출·HermesTrace 전송 | Owner 내부 훅과 `kos-experience` 스레드(기본 60초 주기) | **Temporal · LangGraph · Hermes 모델 없음** (Owner 직접 서비스) |
| 역할 피드백 조회와 프로필 자체 학습 | C1·C4·자유 요청 실행 중 각 역할 세션 | 해당 Work의 Temporal `WorkWorkflow`(또는 자유 요청 Director 단계) 안의 각 **Hermes `kos-*` 프로필** |
| 팀 사후 검토 (`TeamReview`) | C1·C4 팀 Work가 성공 완료(`completed`)된 직후 | Temporal `WorkWorkflow`의 `commit` 직후 단일 `review` Activity에서 Manager 프로필(`kos-curation-manager` · `kos-thinking-manager`) 호출 (새 LangGraph 세그먼트 아님) |
| 콘솔 "검토함" 표시 (`teamreview.considered`) | 사용자가 관리 콘솔에서 TeamReview 제안을 확인 표시할 때 | **Temporal · LangGraph · Hermes 없음** (Owner 접수 단계에서 즉시 처리) |

## 1층: 역할별 피드백과 격리된 Hermes 프로필

### 어떤 반응이 어느 역할의 `feedback`으로 가는가

사용자의 결정이나 Work 결과는 State의 `feedback` 스트림에 역할 이름과 함께 쌓입니다. 다음번에 같은 역할이 호출되면 `feedback` 도구를 통해 **자기 역할의 최근 기록 최대 20건**만 읽을 수 있습니다(관리 콘솔 `/api/feedback`은 최근 200건 조회). 이 기록에는 노트 본문, 제목, 파일 경로, 노트 ID, 다이제스트가 일절 들어가지 않고 변경 종류·결과 상태 같은 비식별 요약만 남습니다(문자열은 200자 이내로 자릅니다).

- **`classifier` · `linker`** (수명주기 제안은 `stewardship`): 사용자가 [[c6]]에서 제안을 적용하거나 일부 체크를 풀고 적용하거나 거절하면, 제안 안의 각 변경 항목마다 적용(`applied`)·체크 해제(`unchecked`)·거절(`rejected`) 결과가 담당 역할로 기록됩니다. 예를 들어 폴더 이동 제안을 거절하면 이동 항목의 담당인 `classifier`의 다음 피드백에 그 거절이 나타납니다.
- **`synthesizer`**: [[c4]] 보고서가 생성되면 Owner가 그 보고서를 감시 목록(`report_watch`)에 올리고, `kos-experience` 스레드가 주기적으로 확인해 사용자가 본문을 고치면 편집(`edited`), `type`을 바꿔 일반 노트로 승격하면 승격(`promoted`), 지우면 삭제(`deleted`)를 한 번씩 기록합니다. 보고서가 `deny` 정책으로 바뀌면 감시를 건너뜁니다.
- **`curation_manager` · `thinking_manager`**: 각 세그먼트의 평가 결과(어떤 단계 조합이 통과하거나 미충족이었는지)와 완료 후 `TeamReview` 결과 요약이 기록됩니다.
- **`eval_officer`**: 모델 평가자가 "만족"으로 통과시킨 Work의 제안을 사용자가 나중에 거절하면 평가 번복(`eval_overruled`) 피드백이 기록됩니다.
- **`director`**: 자유 요청([[c11]])의 접수 성공·거절·형식 오류·호출 불가 결과를 매핑된 명령 이름과 함께 기록합니다(사용자 입력 원문은 넣지 않음).

### 피드백과 Profile 내부 학습은 다릅니다

Owner가 제공하는 `feedback`은 “내 제안이 적용됐는가, 어느 항목이 거절됐는가” 같은 운영 기록입니다. Hermes가 자기 Profile의 기억과 스킬을 다듬는 것은 별도의 네이티브 학습 기능입니다. Profile을 실행했다는 사실만으로 실제 스킬 파일이 갱신됐다고 볼 수는 없습니다.

모델 역할마다 독립된 Profile 홈을 사용합니다. 예를 들어 `kos-classifier`가 익힌 스킬은 `kos-linker`와 공유하는 변경 파일이 아닙니다. 설치 명령은 공통·역할 지침을 합친 `SOUL.md`와 실행 설정·배포 정보를 갱신하지만, Profile 자체의 스킬·기억·자격 증명을 덮어쓰지는 않습니다.

모델 역할에는 기억·스킬 학습을 허용하고 셸·파일·웹·브라우저·위임 도구는 막습니다. 학습 내용이 달라져도 Owner가 단계마다 부여하는 도구 권한과 평가 기준은 넓어지지 않습니다. 발송용 `kos-ops`에는 이 학습 기능도 없습니다. 전체 Profile·모델 목록과 세션 연결은 [[architecture]]에서 봅니다.

다섯 모델 팀원이 받은 `system_one` 도구의 선택지 배열 전달에는 현재 HTTP 검사 한계가 있습니다. 이 도구 선언을 실환경 완성 근거로 읽지 않도록 [[status]]에 구별해 두었습니다.

## 2층: TeamReview와 "자동 승격 없음" 규칙

C1(정리)이나 C4(강화) 팀 Work가 평가를 통과해 실제 결과물(제안 또는 보고서)을 커밋하고 `completed`로 끝나면, `WorkWorkflow`가 바로 이어 `review` Activity를 실행합니다.

1. 해당 팀의 Manager(`kos-curation-manager` 또는 `kos-thinking-manager`)가 `team_view`와 자기 `feedback`을 읽고 `submit_team_review`로 참여 팀원별 평점(1~5점과 짧은 메모)과 개선 제안(최대 3건)을 제출합니다.
2. Owner가 제출 형식을 검증한 뒤 Work 기록의 `team_review`에 저장합니다. 이 단계에서 오류가 나거나 응답이 끊겨도 이미 커밋된 Work의 결과나 완료 상태는 뒤집히지 않으며, `team_review` 상태만 `failed` 또는 `unknown`으로 남습니다.
3. Owner는 각 개선 제안마다 State(`experience/`)에 **로컬 전용 `ExperienceSourceEvent`** 한 건을 기록합니다. 이 기록은 Core 분류가 일상 진행(`routine_progress`), 평가 상태가 미평가(`not_evaluated`), 전달 상태가 로컬 전용(`local_only`)으로 저장됩니다.
4. **Candidate 미생성 · 자동 승격 없음**: 일상 진행(`routine_progress`) 사건은 Core 규칙상 Candidate 자격이 없으므로 `ExperienceCandidate`도, 전송 대기열(`outbox`) 항목도 만들지 않으며 HermesTrace로 보내지 않습니다. 로컬 관찰 기록도 보관 기간(기본 30일)과 용량 제한(기본 4건) 안에서 만료·정리될 뿐 영구 승격 대기열이 되지 않습니다.
5. 관리 콘솔의 Work 상세 화면에서 사용자는 각 제안을 읽고 **"검토함"**(`teamreview.considered`) 표시만 남길 수 있습니다. 이 동작은 Work 기록에 확인 시각만 적고 역할·카탈로그·프로필을 바꾸지 않습니다. 실제 역할 개선은 사용자가 명세와 선언 파일을 직접 고쳐야 반영됩니다.

## 3층: Fabric 수준 Experience 후보와 HermesTrace 전달

### 어떤 사건만 Candidate가 되는가

Owner는 "제안이 있었다"거나 "Work가 성공했다"는 이유만으로 후보를 만들지 않습니다. 실제 근거가 있는 다음 8가지 사건만 Core 분류에 맞춰 `ExperienceSourceEvent`와 `ExperienceCandidate` 및 `outbox` 항목으로 추출합니다.

| 발생 사건 | Core 분류 | 평가 상태 |
|---|---|---|
| 평가 미충족으로 끝난 Work (`work_unmet`) | `failure` | `fail` |
| 실행 실패로 끝난 Work (`work_failed`) | `failure` | `not_evaluated` |
| 결과 불명으로 끝난 Work (`work_unknown`) | `failure` | `unknown` |
| 사용자가 제안을 거절함 (`proposal_rejected`) | `human_correction` | `fail` |
| 사용자가 일부 항목을 체크 해제해 부분 적용함 (`proposal_partially_applied`) | `human_correction` | `fail` |
| 사용자가 자동 규격화를 되돌림 (`undo`) | `human_correction` | `fail` |
| 일시정지된 예약 작업 실행이 거부됨 (`job_blocked`) | `policy_denial` | `not_evaluated` |
| `ai_policy: deny` 때문에 요청이 거부됨 (`privacy_refusal`) | `policy_denial` | `not_evaluated` |

만약 앞서 TeamReview 제안이 남아 있던 정리 작업의 제안을 사용자가 나중에 거절하면, 그 거절이 `proposal_rejected`(`human_correction`)라는 **새롭고 독립된 Candidate**를 만들 뿐이며, 먼저 기록된 TeamReview 로컬 이벤트는 끝까지 `local_only`로 남습니다.

### 본문 없는 페이로드, 용량 제한, 그리고 실패 처리

- **참조와 다이제스트만 전송**: Candidate에는 Owner 기록 참조, Core 분류·버전·다이제스트, 고정된 요약 문장(Work 사건이면 기능·명령 이름 추가)만 들어갑니다. 노트 본문, 제목, 경로, 노트 ID는 포함하지 않으며, 로컬 이벤트에 붙은 내부 증거 참조도 Candidate에서는 비워 전송 경계를 넘기지 않습니다.
- **용량과 보관 기한**: State `experience/`는 기본적으로 최대 4건(`C9.outbox_limit`, 로컬 관찰과 Candidate 합산)을 유지하며, 새 항목이 들어올 때 한도를 넘으면 오래된 완료·거절·로컬 전용 기록부터 먼저 비우고 그다음 결과 불명·대기·전송 중 순으로 축출합니다. 전송 중이던 항목이 축출되면 결과 불명 기록을 남겨 재전송을 막습니다. 모든 항목은 기본 30일(`C9.retention_days`)이 지나면 자동 만료·삭제됩니다.
- **전달과 미연결 내성**: `C9.hermestrace_socket`(절대 경로 Unix 소켓)과 `C9.hermestrace_credential_file`(소유자 전용 `0600` 32바이트 키 파일)이 모두 설정돼 있으면 `kos-experience` 스레드가 주기적(기본 60초)으로 HMAC-SHA256 서명 메시지(최대 32KiB)를 보내고, 수신측의 영속 저장이 확인된 영수증(`owner_durable`)이 원본 요청과 정확히 일치할 때만 전달 완료(`delivered`) 또는 거절(`rejected`)로 확정합니다.
- **가시적 실패와 재전송 금지**:
  - HermesTrace가 미설정이거나 소켓이 꺼져 있으면 후보가 대기(`pending`) 상태로 머물며 다음 주기를 기다리다 30일 뒤 만료됩니다. 이때 `/api/health`의 `dependencies.hermestrace`만 미설정(`unconfigured`) 또는 연결 불가(`unreachable`)로 표시될 뿐 Owner는 정상 준비(`ready`) 상태를 유지하고 모든 사용자 기능은 그대로 동작합니다.
  - 전송 중 연결이 끊기거나 영수증이 깨졌거나 Owner가 전송 도중(`delivering`) 재시작되면 상태를 결과 불명(`unknown`)으로 바꾸고 `experience_delivery` 결과 불명을 남깁니다. 이후 주기에서는 같은 제출 요청(`admit`)을 다시 보내지 않고, 원래 요청 다이제스트로 수신 여부만 조회(`query_admission`)합니다.
- **승격 능력의 채택**: HermesTrace가 승격한 능력을 KnowledgeOS에 받아들이는 자동 경로는 없습니다. 사용자가 버전과 다이제스트를 고정한 KnowledgeOS 설정 변경으로 직접 반영할 때만 적용됩니다.

## 실제 확인 범위

역할의 실제 모델 실행과, Hermes 스킬 정리기가 학습 파일을 갱신하는 것은 다른 확인입니다. 상시 HermesTrace 수신기로의 실제 전달, 실환경 스킬 갱신, 승격 능력을 실제 채택한 사례의 관찰 한계는 [[status]]와 [[roadmap]]에서 확인합니다.
