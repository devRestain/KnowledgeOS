# C9 학습·Experience

## 한눈에 보기

KnowledgeOS의 모델 역할은 사용자가 제안을 적용하거나 거절하고, 보고서를 고치거나 지우는 **실제 반응**에서 배웁니다. 배움은 세 층으로 나뉩니다. 역할 하나가 자기 책임 안에서 배우는 **역할 수준**, Manager가 teammate를 돌아보는 **팀 수준**(TeamReview), 그리고 근거가 확실한 사건만 다른 Operation(HermesTrace)과 나누는 **Fabric 수준**입니다.

세 층 모두 노트 본문을 옮기지 않고(참조·분류·digest만 사용), HermesTrace에 닿지 못해도 사용자 기능은 멈추지 않습니다. 용어가 낯설면 [[glossary]]를 보세요.

| 항목 | 내용 |
|---|---|
| 트리거 | 사용자의 반응(적용·부분 적용·거절·되돌리기·보고서 수정/승격/삭제), Work의 비정상 종료, 차단된 작업, 개인정보 거부, 완료 후 TeamReview |
| 담당 | Owner와 모든 모델 역할의 Hermes profile (표: 대상 "Owner and role profiles", 역할 "All model roles") |
| 결과물 | 역할별 `feedback` 보기, 로컬 `ExperienceSourceEvent`, 자격이 있는 사건의 `ExperienceCandidate`(전송 대기열) |
| 사용자 결정 여부 | 학습 자체는 사용자가 결정하지 않습니다. 사용자가 결정하는 것은 HermesTrace가 승격한 능력을 **채택**하는 일뿐이며, 설정을 명시적으로 고정(pin)해서만 반영됩니다. |

출처: 위 표는 `docs/CAPABILITIES.md`의 Capability summary와 C9 본문을 따릅니다.

## 왜 이 명세가 필요한가

[[philosophy]]와 USER_FEATURE_SPEC의 "지키는 약속"에서 이 기능이 지키는 것은 다음입니다.

- **약속 4 — 자동으로 바꾸는 것은 작고 기계적인 것뿐입니다.** 학습이 권한을 넓히면 이 약속이 깨집니다. C9는 학습이 권한을 넓히지 못하게 못박습니다. 역할이 쓸 수 있는 도구는 언제나 Work 바인딩에서만 나옵니다(Blueprint §4.5).
- **약속 6 — 잃으면 안 되는 것은 Vault에 둡니다.** 학습 기록은 State 쪽의 잃어도 되는 기록이며, 학습 때문에 노트 본문이 밖으로 나가서는 안 됩니다. 그래서 SourceEvent와 Candidate는 참조·분류·digest만 담습니다.
- **개인정보(`ai_policy`)의 한계.** 학습 기록이 있다는 이유로 원본 노트의 공개 범위가 넓어지지 않습니다.

이 명세가 없다면 생길 문제는 이렇습니다.

- 같은 제안이 거절돼도 `classifier`가 같은 실수를 반복합니다.
- 한 역할의 기억이 다른 역할로 새어, 책임 경계가 흐려집니다.
- 단순히 "제안이 있었다"거나 "Work가 성공했다"는 이유로 후보가 쌓여, HermesTrace가 근거 없는 잡음으로 가득 찹니다.
- HermesTrace가 꺼져 있을 때 사용자 기능까지 막힐 수 있습니다.

## 어떻게 쓰는가

학습은 사용자가 따로 켜거나 호출하는 기능이 아닙니다. 평소처럼 제안을 검토하면 그 반응이 기록됩니다. 확인할 수 있는 경로는 다음과 같습니다.

**자동 경로 (평소 사용)**

1. 정리·강화를 요청하면 제안이나 보고서가 생깁니다([[c1]], [[c4]]).
2. 제안 노트에서 항목을 체크 해제하고 **적용**하거나, **거절**하거나, 적용 뒤 **자동 변경 되돌리기**를 누릅니다([[c6]], [[c11]]).
3. 보고서를 고치거나 `type`을 바꿔 승격하거나 삭제합니다.
4. 이 반응이 해당 역할의 `feedback`으로 기록되고, 다음 호출 때 그 역할이 볼 수 있습니다.

**관리 콘솔 (브라우저, 로컬 전용)**

- 역할별 학습 기록(role-profile map과 learning ledger), Experience 대기열(outbox), TeamReview, 작업의 역할별 호출(profile 이름·모델 경로·skill 묶음 digest)을 **볼 수 있습니다**(USER_FEATURE_SPEC "관리", Blueprint §4.4).
- 콘솔은 관리용이며 학습 내용을 편집하는 곳이 아닙니다. 역할 변경은 사용자가 명세와 카탈로그를 고쳐서만 합니다(Blueprint §4.4 TeamReview).

**CLI**

- 이 기능 전용 명령은 명세·README에 따로 없습니다. 역할 profile 설치는 `knowledgeos install profiles --config owner.json`이며([[usage]]), 이 명령이 profile별 route·도구·학습 설정을 고정합니다(LRN-2 구현 `hermes.py::install_profiles`).

**HermesTrace 채택 (사용자가 결정하는 유일한 지점)**

- HermesTrace가 승격한 능력은 버전과 digest를 고정한 KnowledgeOS 설정 변경으로만 반영됩니다. Core 계약과 스키마는 바뀌지 않습니다.

### 따라 해 보기: 거절한 제안이 다음에 반영되는 과정

1. 정리 요청으로 노트 `Draft idea`에 대한 제안이 생겼고, 체크리스트에 "폴더를 `40_Knowledge/Questions`로 이동"이 있습니다.
2. 이동이 맞지 않다고 판단해 **거절**합니다. 제안 파일은 지워지고 기록은 Git에 남습니다.
3. 다음에 `classifier`가 호출되면 `feedback`에 이 거절이 들어 있습니다.
4. 같은 거절은 "사용자 수정·거절"이라는 실제 근거가 있는 사건이라 Core 분류(예: `human_correction`)에 맞으면 Experience 후보가 됩니다. 후보에는 노트 경로나 본문이 아니라 참조·분류·digest만 들어갑니다. 이 시나리오가 [[LRN-1]]입니다.
5. HermesTrace가 꺼져 있으면 후보는 대기하다 Core 보관 기한이 지나면 만료되며, 사용자는 아무 영향도 받지 않습니다([[LRN-3]]).

## 동작 흐름

{{svg:work-flow}}

위 그림은 Work 전체 흐름이며, 마지막 TeamReview가 팀 수준 학습의 입구입니다. C9 자체의 신호 흐름은 아래와 같습니다.

1. **사건 발생**: 사용자 반응이나 Work의 종료 상태가 생깁니다.
2. **역할 수준**: 해당 역할의 `feedback` 보기에 결과가 기록됩니다.
   - `classifier`·`linker`: 적용·부분 적용·거절
   - `synthesizer`: 보고서 편집·승격·삭제
   - Manager: 평가와 TeamReview 이력
   - EvalOfficer: 만족으로 평가한 결과를 사용자가 거절한 경우
   - Director: 접수 성공과 확인 질문 실패
3. **팀 수준**: TeamReview의 제안마다 로컬 `ExperienceSourceEvent`(`category=routine_progress`, `evaluation_state=not_evaluated`)가 남습니다. Candidate나 outbox 항목은 만들지 않고 HermesTrace로도 보내지 않습니다.
4. **Fabric 수준 판정**: Owner가 사건의 **근거**로 Core 분류에 맞는지 가립니다. 제안이 있었다는 사실이나 Work 성공은 자격이 아닙니다.
5. **전달**: 자격이 있으면 SourceEvent와 Candidate가 생기고 InterOps로 HermesTrace에 전달됩니다. 닿지 못하면 대기하다 만료됩니다.

> [!note]
> 자격이 되는 Core 분류는 `failure`, `timeout`, `crash_recovery`, `cancellation`, `human_correction`, `policy_denial`, `verified_unusual_success`입니다. "결과 불명"만으로는 실패의 증거가 아니고, 평가 전의 제안은 검증된 성공이 아닙니다(CAPABILITIES C9).

## 인수 시나리오와 검증

인수 시나리오는 공개 인터페이스로 실행하는 테스트이며, 모델 단계는 스크립트된 역할 응답을 씁니다. 아래 표는 각 ID의 구현 위치와 테스트 노드를 보여줍니다([[LRN-1]]은 사용자 거절 후 feedback·후보, [[LRN-2]]는 역할별 profile 격리, [[LRN-3]]은 HermesTrace 불통 시 동작).

## 현재 상태와 남은 일

- **원천 근거**: 인수 시나리오 3개(LRN-1~3)는 추적표에 구현과 테스트 노드가 연결돼 있고, PROJECT_STATE의 `E_TRACED_TESTS`는 전체 테스트가 skip·xfail 없이 통과했다고 기록합니다. 다만 이 테스트의 모델 단계는 스크립트 대역입니다(CAPABILITIES 머리말, README "검증 범위").
- **정리된 결정**: TeamReview 제안을 `routine_progress` 로컬 SourceEvent로만 남기고, 실제 근거가 있는 사건에서만 Candidate를 만드는 결정은 `D_C9_PENDING_CLASSIFICATION`, `E_C9_CATEGORY_CONFLICT`, `B_C9_TEAMREVIEW_CATEGORY`(해결됨)에 기록돼 있습니다.
- **실환경에서 확인되지 않은 것**: README "검증 범위"는 실제 HermesTrace 수신기를 별도로 확인해야 하는 항목으로 둡니다. PROJECT_STATE에는 실제 HermesTrace 수신이나 Experience 전송을 관찰한 증거가 없습니다. 같은 맥락에서 Hermes native skill curator가 실제로 역할 profile을 갱신하는 모습을 관찰한 기록도 PROJECT_STATE에는 없습니다. 실환경 역할 세션은 `E_REAL_ROLE_SMOKE`로 확인됐지만, 이것은 C9 학습이나 Experience 전달의 증거가 아닙니다.
- **채택 근거의 범위**: PROJECT_STATE에는 HermesTrace가 승격한 능력의 채택이나 예정 일정이 기록되어 있지 않습니다 [해석]. 이는 채택이 일어나지 않았다는 증거는 아닙니다. TeamReview 제안이 나중에 자동으로 승격·전송되는 일도 약속하지 않습니다.
- **Delivery order**: C9와 C10은 다섯 번째 단계(Fabric)이며 모바일(M1~M3) 앞입니다. 현재 진행 중인 전체 목표는 `KNOWLEDGEOS_REAL_ADOPTION`입니다.

현황의 전체 근거는 [[status]], 시작 전·막힌 과제는 [[roadmap]]에서 보세요.

## 관련 기능

- [[c4]] — TeamReview(ENH-7)가 팀 수준 학습의 원천입니다. 그 제안은 이 기능에서 로컬 관찰로만 남습니다.
- [[c1]] — `classifier`·`linker`가 거절·부분 적용을 `feedback`으로 받습니다.
- [[c6]] — 적용·거절·되돌리기라는 사용자 결정이 학습 신호가 되는 곳입니다.
- [[c7]] — 차단(일시정지)된 작업이 Fabric 수준 신호 중 하나입니다.
- [[c8]] — 알림도 본문 없이 제목과 링크만 보냅니다. Experience 전달 역시 본문 없이 참조·digest만 보내는 같은 원칙을 따릅니다.
- [[c10]] — 같은 Fabric 단계의 다른 절반입니다. 다른 Operation과의 정보 교환은 Gateway가, 성장은 이 기능이 맡습니다.
- [[c11]] — 콘솔이 역할별 학습 기록과 Experience 대기열을 보여줍니다.
