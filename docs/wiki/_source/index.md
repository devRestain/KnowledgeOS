# KnowledgeOS 위키

> [!note]
> 이 위키는 KnowledgeOS의 명세·진행 상태 문서를 **읽기 쉽게 엮은 해설판**입니다. 규칙의 원본은 여섯 개의 원본 문서이고, 위키는 그것을 그대로 가져오거나(영문 "원문" 블록, 표) 쉬운 말로 풀어 쓴 것입니다. 둘이 어긋나면 원본이 맞습니다. 만드는 방식은 [[philosophy]]에 있습니다.

## KnowledgeOS는 무엇인가

KnowledgeOS는 KnowledgeHub Vault에 자유롭게 쓴 아이디어와 노트를 **다시 쓸 수 있는 형태로 정리·축적**하고, 쌓인 생각으로 **지금의 사고를 강화**하는 AgentFabric Operation입니다. 문서 작업(쓰기·검색·보기)은 늘 Obsidian 안에서 하고, KnowledgeOS는 Mac에서 필요할 때 켜지는 Owner 서비스로서 규격화·정리 제안·검색·보고서·점검 알림을 맡습니다. 자동으로 바꾸는 것은 작고 기계적인 규격화뿐이며, 판단이 필요한 변경은 언제나 제안으로만 만들어지고 **적용은 사용자가 결정**합니다.

아래 그림은 누가 누구에게 요청하고 무엇을 읽고 쓰는지를 한 장에 모은 것입니다. 입구는 세 개(Obsidian Thin Client, 브라우저 콘솔, CLI)이고 모두 같은 접수 경로(ExOps → Owner)를 지납니다. 자세한 설명은 [[architecture]]에 있습니다.

## 다섯 가지 기능, 그리고 그것을 받치는 기능

사용자가 직접 얻는 것은 다섯 가지이고(C1~C5), 나머지(C6~C11)는 그 다섯 가지를 안전하게 검토하고, 때맞춰 돌리고, 알리고, 배우고, 연결하고, 부르는 장치입니다.

| 구분 | 기능 | 한 줄 설명 |
|---|---|---|
| 사용자 기능 | [[c1]] 정리 | 노트의 종류·제목·태그·관련 노트·위치를 **제안 노트**로 만들어 줍니다 |
| 사용자 기능 | [[c2]] 규격화 | 빠진 `id`·`type`·`created`·`status`·`ai_policy`를 규칙으로 채웁니다. 선택지가 고정된 값(`type`·`status` 등)은 System One이 충분히 확신할 때만 고릅니다 |
| 사용자 기능 | [[c3]] 검색 | 관련 노트와, 준비된 경우 의미 검색을 제공합니다. 키워드 검색은 Obsidian 검색이 맡습니다 |
| 사용자 기능 | [[c4]] 강화 | 아이디어 발전·Vault에 묻기·프로젝트 돌아보기를 **인용이 달린 보고서**로 정리합니다 |
| 사용자 기능 | [[c5]] 문서 관리 | 처리 안 된 포착, 오래 안 본 아이디어, 충돌 노트 같은 "눈여겨볼 것"을 찾고 보관 제안을 만듭니다 |
| 받치는 기능 | [[c6]] 검토 | 제안의 적용·거절, 자동 변경 되돌리기. 결정은 늘 기록됩니다 |
| 받치는 기능 | [[c7]] 예약 작업 | Owner 안의 스케줄러가 규격화·임베딩·정리·요약을 정해진 시각에 돌립니다 |
| 받치는 기능 | [[c8]] 알림 | Discord로 하루 요약과 즉시 알림을 보냅니다. 알림만 하고 명령은 받지 않습니다 |
| 받치는 기능 | [[c9]] 학습과 Experience | 역할별 스스로 배우기, 사용자 반응에서 배우기, HermesTrace로 근거 있는 사건 전달 |
| 받치는 기능 | [[c10]] Gateway | 다른 Operation이 정보를 보내거나(포착 노트로 들어옴) 조회할 수 있는 문 |
| 받치는 기능 | [[c11]] 호출·관리 화면 | Thin Client 명령·사이드바, 브라우저 콘솔, CLI, Owner 시작·중지 |

기능끼리의 의존 관계(예: 예약 작업 C7은 C1·C2·C3·C5를 부릅니다)는 이 그림에서 볼 수 있습니다. 원본은 `docs/CAPABILITIES.md`의 Capability summary 표입니다.

## 지금 어디까지 왔나

**한 줄 요약**: 명세의 모든 인수 시나리오는 구현과 테스트가 연결되어 있고, 실제 환경에서는 Obsidian·Owner·Discord·의미 검색·예약 실행이 한 번씩 확인된 단계입니다. 아직 확인하지 못한 것과 다음 할 일은 숨기지 않고 따로 적어 두었습니다([[status]], [[roadmap]]).

- 막힌 것·시작 전인 것·후속 과제는 [[roadmap]]에 모았습니다.

## 읽는 길

### 처음 쓰는 사람
1. [[philosophy]]의 "지키는 약속"과 "하지 않는 일"로 KnowledgeOS가 무엇을 약속하고 무엇을 안 하는지 봅니다.
2. [[usage]]에서 Obsidian 사이드바로 **규격화 → 정리 → 제안 적용**까지 한 번 해 봅니다.
3. 궁금한 기능의 페이지를 엽니다. 처음에는 [[c2]](규격화), [[c1]](정리), [[c6]](검토), [[c4]](강화) 순서가 자연스럽습니다.
4. 모르는 말은 [[glossary]]에서 찾습니다.
5. 내 노트가 모델에 보이는지 걱정되면 [[architecture]]의 `ai_policy` 절을 읽습니다.

### 개발하거나 운영하는 사람
1. [[philosophy]]의 "명세 운용"과 "세션마다 갱신하는 방법"을 읽습니다. 명세·코드·상태가 같이 움직이는 규칙입니다.
2. [[architecture]]에서 Owner·Director·Manager·EvalOfficer의 책임, Work 흐름, Vault·State·Runtime 분리, 효과 규칙을 봅니다.
3. 기능 페이지의 **인수 표**(인수 ID → 구현 `file::symbol` → pytest 노드)로 코드를 찾아갑니다.
4. [[status]]에서 어떤 증거가 어떤 종류인지, [[roadmap]]에서 인계(handoff)와 후속 과제를 확인합니다.

## 기능 페이지는 이렇게 읽습니다

각 기능 페이지(C1~C11)는 같은 순서로 구성됩니다.

1. **이 기능은 무엇인가** — 쉬운 말 설명
2. **왜 이 명세가 필요한가** — 지키려는 사용자 약속
3. **어떻게 쓰는가** — Obsidian·콘솔·CLI에서의 구체적인 순서
4. **원문 명세** — `docs/CAPABILITIES.md`의 해당 절(영문)을 그대로 가져온 것
5. **인수 기준** — 시나리오(ID)마다 구현 위치와 테스트
6. **현재 상태와 남은 일** — 증거와 후속 과제 (자세한 것은 [[roadmap]])

## 이 위키에 대해

- 원문 블록·표·그림은 원본 문서에서 **생성**되고, 해설 문장은 `docs/wiki/_source/`에서 직접 씁니다. 생성된 HTML은 손으로 고치지 않으며, 고칠 때는 원본을 고치고 다시 생성합니다([[philosophy]]).
- 위키는 읽기만 하는 정적 HTML입니다. Vault·State·Hermes·실행 중인 Owner에는 아무것도 하지 않습니다.
- 검색 상자로 위키 전체를 검색할 수 있습니다.
