    C10 Gateway (다른 Operation과의 교환)

    C10은 AgentFabric 안의 다른 Operation이 KnowledgeOS에 정보를 맡기거나(받기, intake) 허가된 범위 안에서 검색 결과를 물어볼 수 있게 하는(묻기, query) 교환 창구입니다. 사용자가 Obsidian이나 CLI에서 누르는 전용 명령은 없으며, 결과는 평소처럼 Obsidian 인박스와 로컬 관리 콘솔에서 확인합니다.

    실제 지원하는 두 경로와 런타임 접점#

    Gateway가 로컬 ExOps HTTP 서버에 열어 두는 엔드포인트는 딱 두 개입니다.

    작업 HTTP 경로 하는 일 런타임 접점 (Hermes · Graph · Temporal)
    받기 (intake)POST /interops/intake허가된 Operation의 제출을 00_Inbox/의 capture 노트 1개로 저장하고 영수증 반환Temporal WorkWorkflow + 단일 정적 LangGraph(Owner 정적 Officer → 정적 EvalOfficer 검증 → 파일 생성). Hermes 모델 없음, LLM Director 없음
    묻기 (query)POST /interops/query허가된 수신자에게 approve 비보고서 노트의 키워드 검색 결과만 제한 반환Temporal · LangGraph · Hermes 모델 모두 없음 (Owner가 HTTP 요청 안에서 C3 키워드 검색을 동기 처리)

    두 경로 모두 ExOps 공통 경계(loopback 127.0.0.1/localhost 바인딩, Host·Origin 확인, application/json, 본문 최대 1MiB)를 통과해야 하며, C10.authorized_operations 설정에 발신 Operation이 등록돼 있어야 합니다. 기본값은 빈 허가표({})이므로 운영자가 owner.json에 상대 권한을 설정하기 전에는 모든 교환 요청이 거절됩니다.

    허가 설정에는 Operation별로 다음 항목을 적습니다.

    • intake: true 또는 query: true (허용 작업)
    • purposes: 허용 목적 목록. 시스템이 인정하는 목적 5종(status, consultation, domain_task, experience_submission, human_control) 중 허가된 것만 통과합니다.
    • 질의 권한이 있을 때 max_results(양의 정수)와 max_excerpt_chars(양의 정수) 상한.

    흐름 1: 받기 (POST /interops/intake)#

    예를 들어 research라는 허가된 Operation이 조사 중 발견한 메모를 domain_task 목적으로 보내는 상황입니다.

    입력 봉투와 검증 규칙#

    요청 JSON은 정확히 일곱 항목만 담아야 하며, 빠지거나 여분 필드가 있으면 즉시 HTTP 400(형식 오류)으로 거절되고 State나 Vault에는 아무것도 남지 않습니다.

    • 메시지 번호(message_id, 최대 96자), 발신 Operation 이름(sender_operation_id, 최대 64자), 중복 방지 키(idempotency_key, 최대 128자)
    • 요청 목적(purpose, 허용 5종 중 하나)과 타임존 오프셋이 포함된 발행 시각(issued_at)
    • 내용 묶음(payload): 제목(title, UTF-8 200바이트 이하)과 본문(text, 16,384바이트 이하)이 필수이며, 선택 항목은 포착 종류(capture_kind, 기본 text 외 link·voice·image)와 출처 주소(source_url, 2,048바이트 이하) 두 개뿐입니다.
    • 내보내기 정책(export_policy): Git 동기화 저장 허용 여부(git_sync_allowed, true 또는 false) 불리언 하나만 허용합니다.

    단계별 처리와 멱등성#

    1. 안정적 식별자 고정과 충돌 차단: Owner가 발신자 이름과 중복 방지 키를 조합해 gateway-<해시> 요청 ID를 만들고 State(gateway/)에 요청 원문 다이제스트와 함께 기록합니다. 같은 키로 내용이 다른 요청이 오면 HTTP 409 충돌로 거절합니다.
    2. 경계 권한·Git 정책 검사: 발신자에게 받기 권한이 없거나, 목적이 허용 목록 밖이거나, git_sync_allowed가 false이면 조용히 버리지 않고 State(gateway/)에 거부 결정과 재시도 금지(retry_disposition: "never") 명시 오류를 남긴 뒤 HTTP 403을 반환합니다. Vault는 GitHub private 저장소와 동기화되므로 Git 저장이 금지된 정보는 절대 받아들이지 않습니다.
    3. 영수증 선확정 후 응답: 검사를 통과하면 gateway.intake 명령(행위자 operation/<발신ID>)으로 Owner에 접수하고 영수증을 State(requests/)에 먼저 커밋한 뒤 응답합니다. 최초 제출은 HTTP 202, 같은 제출을 다시 보내면(동시에 겹쳐 들어와도) 새 쓰기 없이 HTTP 200으로 최초 영수증을 그대로 돌려줍니다.
    4. 정적 Work 실행과 포착 파일 생성:
      • 정적 Director가 접수(admission) 단계 권한을 다시 확인하고 intake 모드 Work를 엽니다.
      • 별도 자율 Officer를 두지 않고 Owner 정적 Officer가 00_Inbox/<안전하게 치환된 제목>.md 초안을 만듭니다(금지 문자는 -로 치환, 최대 100자, 비면 Capture).
      • 정적 EvalOfficer가 UUID4 형식, capture/unprocessed 상태, 본문 일치, 출처(captured_from), ai_policy: approve를 검증합니다.
      • 파일 쓰기 직전(effect 단계) 권한을 한 번 더 확인한 뒤 00_Inbox/에 노트를 생성합니다(같은 이름의 파일이 이미 있으면 충돌을 피해 유일한 파일명으로 저장). 생성된 경로와 work_id는 State(gateway/) 기록에 덧붙입니다.

    만들어지는 포착 노트의 모습#

    새 포착 노트의 frontmatter에는 출처가 평평한 속성으로 기록되고, 본문에는 제출된 text가 그대로 들어갑니다.

    id: "<새 UUID4>"
type: capture
status: unprocessed
created: "<수신 시각>"
ai_policy: approve
title: "<제출 제목>"
captured_from: operation/research
capture_kind: text
kos_provenance: "<message_id>"
kos_provenance_sender: research
kos_provenance_received_at: "<수신 시각>"

    source_url이 포함돼 있었다면 같은 frontmatter에 source_url 속성도 추가됩니다.

    흐름 2: 묻기 (POST /interops/query)#

    예를 들어 허가된 Operation(예: ExecutiveOffice)이 consultation 목적으로 특정 주제의 노트를 조회하는 상황입니다. 묻기는 Work를 열지 않고 동기 HTTP 요청 안에서 끝납니다.

    1. 입력과 권한 검사: 발신 Operation 이름(sender_operation_id), 요청 목적(purpose), 비어 있지 않은 검색어(query, 최대 1024자)가 필수이며, 선택적으로 결과 수 상한(max_results)과 발췌 글자 수 상한(max_excerpt_chars)을 줄 수 있습니다. 형식이 틀리면 HTTP 400, 발신자나 목적이 허가되지 않았으면 State(gateway/)에 거부 기록을 남기고 HTTP 403을 반환합니다.
    2. 한도 계산 (축소만 허용): 요청자가 보낸 한도, authorized_operations에 설정된 상한, 그리고 시스템 하드 상한(결과 최대 100개, 결과당 발췌 최대 160자) 중 가장 작은 값을 택합니다. 요청자가 허가 범위를 줄일 수는 있어도 넓힐 수는 없습니다.
    3. 키워드 검색과 내보내기 필터: C3의 키워드 검색(역할 공개 범위 audience="role")으로 찾습니다. 이 단계에서 deny 노트, 99_System/ 시스템 파일, 01_AI_Review/Proposals/ 제안 노트, 그리고 type: report 보고서 노트는 모두 제외됩니다. approve이면서 비보고서인 노트만 후보로 통과하며 sensitivity 값은 제외 기준이 아닙니다.
    4. 실행 직전 권한 재확인 (effect)과 파일 재검증: 결과를 내보내기 직전 권한을 다시 한 번 확인한 뒤, 후보 노트를 현재 Vault에서 직접 다시 읽습니다. 검색 직후 파일이 바뀌었거나, 병합 충돌이 생겼거나, report·proposal로 바뀌었거나, ai_policy가 approve가 아니게 되었거나, 제목·줄 번호가 어긋나면 그 항목은 응답에서 뺍니다.
    5. 반환 페이로드: 최종 통과한 항목마다 제목(title), 경로(path), 줄 번호(line), 위치 정보(locator: {path, line}), 그리고 한도 길이로 자른 한 줄 발췌(excerpt)만 돌려줍니다. 전체 노트 본문은 나가지 않습니다.

    수신 후 소유권과 후속 정리 연쇄#

    접수 영수증은 제출을 받아 실행에 넘겼다는 뜻이며, 포착 파일 생성 완료와는 다릅니다. Work가 실제로 포착을 만든 뒤에는 사용자의 일반 노트로 다룹니다.

    • 단일 기록자와 사용자 소유권: 외부 Operation은 Vault에 직접 쓰거나 이미 만든 포착을 다시 덮어쓸 수 없습니다. 생성된 00_Inbox/ 파일은 사용자가 직접 작성한 일반 capture 노트와 완전히 같아서, 사용자가 자유롭게 편집하거나 ai_policy: deny로 바꾸거나 삭제할 수 있습니다.
    • 후속 자동화 연쇄: Gateway 전용 정리·규격화 경로는 따로 없습니다. 만들어진 포착 노트는 일반 포착과 같은 흐름에 합류합니다. 다음 기능을 곧바로 연속 호출하는 파이프라인은 아닙니다. 각 예약 시각이나 사용자 요청이 따로 대상을 고르므로, 실제 실행 순서는 언제 포착을 받았는지에 따라 달라집니다.
      1. C2 규격화: 파일 수정 직후 대기 시간(10분 quiet period)이 지난 뒤 시간당 standardize 작업(standardize.auto)이나 사용자의 규격화 미리보기 대상이 됩니다.
      2. C1 정리: type: capture·status: unprocessed·ai_policy: approve 조건을 만족하므로 매일 06:00 curate 예약 작업(organize.auto, 오래된 순 최대 10개)이나 사용자의 정리 요청 대상이 됩니다. 정리 팀이 만들어 내는 것도 원본 수정이 아닌 01_AI_Review/Proposals/ 제안 노트뿐이며, 실제 반영 여부는 사용자가 C6에서 결정합니다.
      3. C5 · C8 관리와 알림: 3일이 넘도록 미처리로 남아 있으면 3일 넘은 포착으로 집계되어 08:00 검토 요약과 주의 목록에 표시됩니다.

    구현 범위와 관찰 한계#

    • 실환경 관찰 한계와 현재 제약:
      • 실제 다른 Operation(예: ExecutiveOffice)이 실환경에서 KnowledgeOS로 제출하거나 질의한 관찰 기록은 아직 없습니다(현재 상태).
      • 기본 설정 C10.authorized_operations는 비어 있으므로, 실제 교환을 열려면 운영자가 owner.json에 상대 Operation 권한과 한도를 명시 설정해야 합니다.
      • POST /interops/query는 현재 C3 키워드 검색만 제공하며 의미 검색(semantic)은 노출하지 않습니다.
      • 현재 /interops/intake·/interops/query는 로컬 loopback ExOps HTTP 위에서 요청 본문의 sender_operation_id와 설정 허가표를 대조하는 구조이며, C9의 HermesTrace 전송에 쓰는 Unix 소켓 HMAC 상호 인증과는 별개 경로입니다. 실제 타 Operation을 연동할 때 호출자 인증 경계를 함께 점검해야 합니다.
