    C10 Gateway: 다른 Operation과의 교환

    한눈에 보기#

    KnowledgeOS는 AgentFabric 안에서 기초 Operation입니다. 다른 Operation은 정보를 KnowledgeOS에 맡길 수 있고, ExecutiveOffice는 KnowledgeOS에 물어볼 수 있습니다. 이 교환을 맡는 창구가 Gateway(C10)입니다.

    창구는 두 방향입니다. 받기(intake) 는 허가된 Operation이 보낸 제출을 Vault의 00_Inbox/에 capture 노트 하나로 만듭니다. 묻기(query) 는 remote_ok 노트만 대상으로 제한된 검색 결과(제목·위치·짧은 발췌)를 돌려줍니다. 두 방향 모두 영수증(receipt)을 먼저 기록한 뒤에 응답합니다.

    항목 내용
    트리거다른 Operation의 제출 또는 질의. 사용자가 Obsidian에서 누르는 명령은 없습니다
    담당Owner(정적 코드 효과). 접수만 Director가 맡고, 새 Officer는 없습니다
    결과물받기: 00_Inbox/의 capture 노트 1개와 영수증. 묻기: 제한된 결과 목록
    사용자 결정 여부받기·묻기 자체에는 없음. 만들어진 포착은 이후 C2·C1이 다른 포착과 똑같이 다룸

    참고

    이 문서에서 "Operation"은 AgentFabric 안의 독립된 서비스 하나(KnowledgeOS, ExecutiveOffice 등)를 뜻합니다. 낯선 용어는 용어를 보세요.

    왜 이 명세가 필요한가#

    KnowledgeOS가 지키는 약속 가운데 Gateway와 직접 관련된 것은 다음입니다(운용 원칙 참고).

    • Vault는 사용자의 것입니다. 다른 Operation이 Vault에 마음대로 쓰거나 읽어 가면 안 됩니다. 그래서 쓰기는 항상 Owner 한 곳이 하고(Blueprint §6의 "One writer"), 밖에서 온 정보도 평범한 capture 노트가 되어 사용자가 자유롭게 고치거나 지울 수 있는 문서가 됩니다.
    • 개인정보는 ai_policy가 정합니다. Blueprint §5.4 표에서 Gateway로 내보낼 수 있는 값은 remote_ok뿐이며 ask·local_only·deny는 내보내지 않습니다. Gateway가 없다면 외부 조회가 정책을 우회할 수도 있고, 반대로 정책을 지킬 방법이 없어 아예 교환할 수 없을 것입니다.
    • Git이 백업이자 이력입니다. Vault는 GitHub private repo와 동기화되므로, Git에 올라가면 안 되는 내용을 Vault에 저장하는 제출은 거절합니다.
    • 잃거나 중복되면 안 됩니다. 같은 제출이 두 번 와도 노트는 하나여야 하고, 응답이 유실돼도 영수증으로 확인할 수 있어야 합니다(Blueprint §6의 "Idempotent requests").

    즉 Gateway는 "다른 Operation과의 교환을 허용하되, Vault 소유권·개인정보·멱등성을 우회로로 잃지 않도록" 하는 명세입니다. 용어는 용어의 Request, Work, Receipt를 참고하세요.

    어떻게 쓰는가#

    C10은 Operation 간 교환용이라 Thin Client 명령, 사이드바 버튼, CLI 명령이 따로 없습니다. 기능 명세와 README의 C11 표에도 Gateway 전용 명령은 등장하지 않습니다. 사용자는 결과를 평소 도구로 확인합니다.

    자동 경로: 다른 Operation이 보낼 때

    1. 허가된 Operation이 제출을 보냅니다. 제출에는 발신 Operation, 목적, 내용, 내보내기 정책(Git 동기화 허용 여부)이 들어갑니다.
    2. Director가 제출을 정적 코드로 접수합니다. 허가되지 않은 발신자·목적이거나 형식이 맞지 않으면 거절됩니다(근거: GW-1의 테스트, docs/CAPABILITY_TRACE.md).
    3. Owner가 00_Inbox/에 capture 노트를 만들고 영수증을 확정한 뒤 응답합니다.
    4. 사용자는 Obsidian에서 인박스를 열어 새 포착을 확인하고, 정리가 필요하면 C1의 정리 요청을 합니다. 포착에는 Owner의 기본 ai_policy가 붙으며 기본값은 ask이므로, 그대로는 예약 정리 대상이 아닙니다. 예약 정리를 원하면 사용자가 ai_policy를 remote_ok로 바꾼 뒤 매일 06:00의 curate(C7)를 기다립니다.

    자동 경로: 다른 Operation이 물을 때

    1. 요청자는 발신자, 목적, 질의를 보냅니다. 설정된 허가 범위 안에서 결과 수와 발췌 길이를 더 줄일 수는 있지만 넓힐 수는 없습니다(결과 최대 100개, 결과당 발췌 최대 160자).
    2. Owner가 C3의 검색으로 remote_ok 노트만 찾아 제목, 위치, 짧은 발췌를 돌려줍니다.

    사용자가 확인하는 곳

    • 인박스에 쌓인 포착: Obsidian(Bases 뷰는 C5, 처리되지 않은 포착이 3일을 넘으면 주의 항목으로 올라옵니다).
    • 접수·영수증 기록: 제출은 Gateway 제출로 분류되는 Request이고 Director가 접수하면 Work가 됩니다(CAPABILITIES의 Shared terms). Work 목록은 브라우저 콘솔에서 관찰합니다(Blueprint §3.2). 이 목록에 Gateway 항목이 어떻게 표시되는지는 명세에 따로 적혀 있지 않습니다.

    작업 예시

    (아래 Operation 이름과 값은 설명용 가정입니다.) example-ops라는 허가된 Operation이 "회의에서 나온 아이디어"를 보냅니다.

    1. 제출이 접수되고 00_Inbox/에 노트가 생깁니다. frontmatter에는 다음처럼 출처가 평평한 필드로 남습니다.
    type: capture
captured_from: operation/example-ops
kos_provenance: <메시지 ID>
kos_provenance_sender: <발신 Operation>
kos_provenance_received_at: <수신 시각>
    1. 같은 제출을 한 번 더 보내도 노트는 늘지 않고 처음 영수증이 그대로 돌아옵니다.
    2. 기본 ask 포착은 사용자가 직접 정리 요청을 할 수 있습니다. 사용자가 ai_policy를 remote_ok로 바꾼 경우에는 다음 06:00 curate의 대상이 될 수도 있습니다. 예약 정리에서 모델은 remote_ok 노트만 받으며(C1), 제안을 적용할지는 사용자가 정합니다(C6).
    3. 그동안 ask 노트를 가리키는 외부 질의가 와도 그 노트는 결과에 나오지 않습니다(GW-2).

    동작 흐름#

    이 기능에 맞는 명세 도해(svg)는 없어서, 받기와 묻기를 짧은 순서로 적습니다.

    받기(intake)

    1. 제출 도착
    2. Director 접수: 허가된 발신자·목적인지, 내보내기 정책이 Git 동기화된 Vault 저장을 막지 않는지 확인
    3. Owner가 00_Inbox/에 capture 노트 작성(출처 필드 포함)
    4. 영수증을 먼저 확정 → 응답. 같은 제출이 다시 오면 처음 영수증을 돌려줌
    5. 이후 C2와 C1이 일반 포착과 똑같이 적용

    묻기(query)

    1. 발신자·목적·질의 도착. 허가 범위는 줄일 수만 있음
    2. C3 검색: remote_ok이며 보고서가 아닌 노트만
    3. 제목·위치·짧은 발췌를 한도 안에서 반환

    주의

    정책으로 내보낼 수 없는 제출(Git 동기화된 Vault에 저장하면 안 된다는 내보내기 정책)은 조용히 버려지지 않고 명시적 오류 기록과 함께 거절됩니다(CAPABILITIES C10). 보낸 쪽은 이를 실패로 알게 됩니다.

    C10 Gateway#

    KnowledgeOS is a foundational Operation: other Operations may submit information to it, and ExecutiveOffice may query it.

    • Intake: the Director admits a submission from an authorized Operation. The Owner creates a capture note in 00_Inbox/ with captured_from: operation/<id> and flat provenance fields kos_provenance (message ID), kos_provenance_sender and kos_provenance_received_at; C2 and C1 then apply to it as to any capture. Intake is an Owner effect, not a new Officer. A submission whose export policy forbids storage in a Git-synchronized Vault is refused with an explicit error record.
    • Query: bounded C3 results over remote_ok notes only. The request supplies sender, purpose and query, and may narrow configured grants with result and excerpt limits, never widen them (at most 100 results and 160 excerpt characters per result). Results are titles, locators and short excerpts within those limits.
    • Receipts: committed before acknowledgment. A duplicate submission returns the original receipt.

    Acceptance:

    • GW-1 Given a valid submission, then exactly one capture note exists, and resubmitting it returns the same receipt.
    • GW-2 Given a query matching an ask note, then that note is not in the result.

    현재 상태와 남은 일#

    • 명세·추적과 실행 검증: 현재 인수 예시는 61개(GW-1·GW-2, SUR-9 포함)이며, PROJECT_STATE.md의 E_SIDEBAR_INLINE_TRACE는 61개 인수 ID와 추적표 61행·pytest 노드 171개의 연결을 기록합니다. 추적표는 실행 통과 보고가 아닙니다. E_TRACED_TESTS는 당시 전체 248건 통과, E_SIDEBAR_INLINE_TESTS는 이후 인라인 사이드바 관련 5건 통과 기록으로 구분합니다.
    • 실환경 근거: PROJECT_STATE.md의 실환경 항목(역할 세션, Owner 수명주기, Discord, 의미 검색, 스케줄러, 사이드바)에는 C10 전용 기록이 없습니다. 다른 Operation(예: ExecutiveOffice)이 실제로 제출하거나 질의한 관찰 근거는 아직 없습니다. README의 "검증 범위"도 실제 수신기·외부 연동은 별도로 확인해 PROJECT_STATE.md에 따로 적는다고 구분합니다.
    • 열린 질문·막힘: Blueprint §9의 열린 질문과 PROJECT_STATE.md의 blocker·handoff에 C10 항목은 없습니다. 현재 handoff는 열린 정리 제안 검토, 첫 자연 실행의 스케줄러 관찰, 임계값(related_min_score·related_min_probability·min_confidence) 조정입니다.

    상태

    C10의 남은 일은 "실제 Operation 사이의 제출·질의를 관찰하는 실환경 확인"입니다. 이는 명세에 적힌 사실이 아니라 PROJECT_STATE.md에 해당 증거가 없다는 점에서 나온 결론입니다. 전체 계획은 로드맵에서 볼 수 있습니다.

    관련 기능#

    • C1 정리: 받은 포착은 일반 포착처럼 정리 대상이 되고, Gateway가 트리거가 되는 Work는 remote_ok 노트만 모델에 줍니다. 예시: ORG-1.
    • C2 규격화: 새 포착도 같은 결정적 규격화 규칙의 대상입니다.
    • C3 검색: 묻기가 쓰는 검색 서비스입니다. (C3의 "게이트웨이는 쓰지 않는다"는 말은 모델 게이트웨이를 뜻하며, 이 C10과는 별개입니다.)
    • C5 문서 관리: 처리되지 않은 포착을 주의 항목으로 올립니다. 예시: DOC-1.
    • C7 예약 작업: curate가 새 포착을 매일 처리합니다.
    • C11 호출·관리 화면: 다른 Operation은 Thin Client가 아니라 C10을 쓰고, 사용자는 콘솔에서 결과를 관찰합니다.
