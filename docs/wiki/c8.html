    C8 알림 (Discord 단방향 알림)

    C8은 KnowledgeOS가 사용자에게 지금 확인하거나 결정할 일이 있을 때만 Discord로 보내는 단방향 알림 기능입니다. Obsidian에서 누르는 버튼은 따로 없으며, 알림은 사용자를 Obsidian 노트나 로컬 관리 콘솔로 안내하는 출구 역할만 합니다. Discord 채널에 답장이나 이모지 반응을 남겨도 KnowledgeOS는 아무 작업도 시작하지 않습니다.

    알림이 출발하는 세 가지 경로#

    KnowledgeOS가 Discord로 메시지를 보내는 실제 경로는 크게 세 갈래입니다. 이 중 C8이 직접 책임지는 경로는 검토 요약과 즉시 알림이며, 매일 아침 할 일 알림은 C12가 같은 발송 통로를 공유해 보냅니다.

    흐름 1: 매일 08:00 검토 요약 (digest)#

    아침 8시가 되어 Owner 안의 스케줄러가 digest 작업을 실행하거나 사용자가 터미널에서 knowledgeos job run digest를 실행하면, schedule/digest 행위자로 digest.run 요청이 접수됩니다. 이 요청은 하나의 정적 Work로 열려 StewardshipOfficer가 먼저 수명주기 제안(완료 프로젝트·중단 아이디어 보관 제안, System One이 설정돼 있으면 상태 전환 제안)과 낡은 제안 만료 정리를 끝낸 뒤, 같은 완료(commit) 단계에서 검토 요약 생성으로 이어집니다.

    1. 선행 스캔과 중복 방지: 요약 생성 직전에 같은 요청 ID로 이미 만든 요약이 있으면 기존 결과를 돌려주고 끝냅니다. 처음 실행이라면 먼저 즉시 알림 스캔을 한 번 돌려 빠진 충돌·결과 불명이 있는지 확인합니다.
    2. 현재 상태 집계: Owner가 Vault 인덱스를 새로고침해 deny 노트와 시스템 폴더(99_System/)를 뺀 문서들을 훑고, 다음 일곱 항목을 계산합니다.
      • 검토할 제안: 상태가 열려 있거나(open) 낡은(stale) 제안 노트.
      • 오래된 제안: 그중 대상 노트가 바뀌었거나 사라져 낡은 상태가 된 제안.
      • 새 보고서: 직전 검토 요약이 끝난 기준 시각(cursor)보다 나중에 생성된 보고서(첫 요약이면 전체 보고서).
      • 3일 넘은 포착: 아직 처리되지 않은(unprocessed) 포착 노트 중 생성된 지 3일이 지난 항목.
      • 확인 대기 작업: 규격화 미리보기처럼 사용자 확인을 기다리는(awaiting_confirmation) Work의 개수. 노트 제목은 드러내지 않고 개수와 콘솔 #works 링크만 붙입니다.
      • 확인 필요: 병합 충돌, 노트 ID 중복, 깨진 YAML·인코딩 오류, 아직 해결되지 않은 결과 불명 목록.
      • 다시 볼 노트: 30일 넘게 손대지 않은 아이디어와 열린 질문 중 날짜 기준으로 순환해 고른 최대 3개.
    3. 개인정보 최종 재검증: 목록에 오른 노트는 발송 직전 Vault에서 현재 파일을 다시 읽어 ai_policy가 approve인지 확인합니다. deny나 알 수 없는 정책값은 제목과 링크를 모두 뺍니다(sensitivity는 공개 여부에 영향을 주지 않습니다). 제안이나 보고서 노트라면 그 문서가 참조한 원본·대상 노트까지 모두 현재 approve여야만 포함합니다. 본문 내용은 어떤 경우에도 요약에 넣지 않습니다.
    4. 발송 여부 결정과 조용한 통과:
      • 검토할 제안, 새 보고서, 3일 넘은 포착, 확인 대기 작업, 확인 필요 중 하나라도 1건 이상 있으면 제목 KnowledgeOS 검토 요약으로 Discord에 보냅니다. 0건인 항목은 줄을 만들지 않습니다.
      • 위 다섯 항목이 모두 0건이면 다시 볼 노트나 실패한 자동 작업이 있더라도 알림을 보내지 않고 조용히 끝납니다. 이때도 다음 요약에서 같은 보고서를 중복 집계하지 않도록 요약 기준 시각(cursor)은 현재 시각으로 전진합니다.
      • 최근 자동 규격화(autofix) 내역은 콘솔 주의 목록에만 남기고 검토 요약에는 넣지 않습니다.
      • 실패한 자동 작업 처리: 각 예약 작업의 가장 최근 실행이 실패(failed)한 경우 작업 이름을 별도로 모아 두되, 실패 자체만으로는 알림을 보내지 않습니다. 다른 발송 사유가 있어 요약을 보낼 때만 맨 아래에 자동 작업 점검 필요: <작업 이름> 한 줄을 덧붙입니다. 일시정지로 막힌 작업이나 실행 시점을 놓친 작업은 요약 줄에 넣지 않습니다.
    5. 결과물: 발송 조건을 만족하면 항목별 제목·개수, 해당 노트를 바로 여는 obsidian:// 링크, 콘솔 #attention 링크가 담긴 메시지가 Discord 채널로 나가고, State의 알림 기록(notices)에 한 건이 저장됩니다.

    흐름 2: 기다리지 않고 보내는 즉시 알림 (alert)#

    즉시 알림은 사용자가 콘솔을 열거나 요약을 실행하지 않아도 Owner가 스스로 변화를 감지해 보냅니다. Owner가 켜지면 kos-notices라는 백그라운드 스레드가 약 0.1초 간격으로 Vault 파일과 State의 unknowns·jobs 기록의 파일 상태 변화를 살피고, 변화가 생길 때마다 즉시 알림 스캔을 돌립니다.

    즉시 알림이 나가는 경우는 다음 두 부류로 엄격히 제한됩니다.

    • Vault 병합 충돌(conflict): 동기화 충돌 표식(<<<<<<<)이 들어간 approve 노트가 발견되었을 때.
    • 실제 파일이나 사용자 행동에 영향을 줄 수 있는 미해결 결과 불명(unknown):
      • Vault 파일 쓰기 결과 불명(effect)
      • 적용·거절·되돌리기·취소·조정 같은 사용자 동작 결과 불명(action)
      • 실행 중인 Work 취소 결과 불명(cancellation)
      • Temporal 실행 단계(runtime_phase) 중 실제 반영을 수행하는 commit으로 시작하는 단계의 결과 불명

    반대로 다음 항목들은 즉시 알림을 보내지 않습니다. 모두 콘솔과 API(/api/attention, /api/unknowns)에는 남아 관리 화면에서 확인할 수 있습니다.

    • 분류기·연결자 같은 모델 단계의 runtime_phase 결과 불명, 역할 호출(role_invocation) 결과 불명
    • 요청 처리(request), Experience 전달(experience_delivery), 알림 전달(notice) 자체의 결과 불명
    • 실패한 작업, 일시정지된 작업, 놓친 예약 작업

    중복 방지와 지속 노출: 예를 들어 approve 노트에 병합 충돌이 생기면 Owner가 해당 항목 ID를 State(alerts)에 먼저 기록한 뒤 즉시 알림을 딱 한 번 보냅니다. 충돌을 고치지 않고 이틀이 지나면 즉시 알림은 다시 오지 않지만, 매일 08:00 검토 요약의 확인 필요 줄에는 해결될 때까지 계속 표시됩니다. 만약 충돌이 난 노트가 deny 정책이면 즉시 알림도 요약도 그 노트를 언급하지 않습니다.

    흐름 3: 매일 07:00 아침 할 일 알림 (C12 연동)#

    매일 07:00에 도는 daily 작업은 C8의 검토 요약과 별개입니다. C12의 DailyOfficer가 이전 데일리 노트의 미완료 항목을 오늘 노트로 옮겨 적은 뒤, 발송 시점에 현재 approve 상태인 오늘 데일리 노트의 #task 항목과 Vault 내 다른 approve 노트에 적힌 오늘 마감·기한 지난 #task 항목을 모읍니다.

    • obsidian:// 링크나 노트 경로 없이 할 일 이름만 최대 20개(초과 시 남은 개수 한 줄 추가) 정리해 따뜻한 아침 인사말과 함께 보냅니다.
    • 같은 날짜의 같은 데일리 노트(노트 ID 기준)에 대해서는 한 번만 보냅니다. 오늘 노트를 지우고 새로 만들었을 때만 새 인계로 봅니다.
    • 발송 통로는 C8과 동일한 Owner 알림 발송 경로와 kos-ops 프로필을 함께 사용합니다.

    발송 전용 kos-ops 프로필과 결과 불명 처리#

    KnowledgeOS는 Discord 발송을 모델 역할과 완전히 분리합니다. config/roles.json의 운영 프로필로 선언된 kos-ops는 모델 경로가 비어 있고(null), 학습·도구·예약 실행이 모두 꺼져 있습니다. knowledgeos install profiles --config owner.json으로 설치하면 프로필 안에 gateway.parked(수신 정지 표식) 파일이 함께 생성되어 Hermes gateway가 Discord 수신 어댑터를 열지 못하게 막습니다.

    알림 한 건이 실제로 전달되는 순서는 다음과 같습니다.

    1. 의도 먼저 기록: Owner가 발송 명령을 부르기 전에 State(notices)에 알림 내용을 대기(pending) → 전달 중(delivering) 상태로 먼저 저장합니다.
    2. 단일 발송 시도: 기본 발송기가 hermes -p kos-ops send --to discord:<채널ID> --json --file -를 한 번만 호출해 제목·본문 줄·링크를 그대로 보냅니다(설정에서 외부 발송 명령 C8.notifier_command를 따로 지정한 경우 그 명령을 대신 실행합니다).
    3. 응답 판정:
      • 종료 코드가 0이고 Hermes JSON 응답이 성공(success: true 또는 skipped: true, 오류 없음)이면 전달 완료(delivered)로 확정합니다.
      • 종료 코드가 1이고 실패 JSON이 돌아오면 미전달(not_delivered)로 기록합니다. 결정 사항에 따라 전달 실패 사유 문구는 알림 기록에 남기지 않습니다.
      • 응답 시간 초과(기본 10초), 프로세스 오류, 깨지거나 모순된 JSON, 또는 발송 도중 Owner가 꺼졌다가 재시작해 대기·전달 중 상태로 남은 알림은 모두 결과 불명(unknown)으로 전환하고 notice 결과 불명 항목을 남깁니다.
    4. 재전송 금지와 가시적 실패: 결과 불명으로 남은 알림은 Owner가 재시작되더라도 절대 자동으로 다시 보내지 않습니다. 또한 알림 전달 자체가 결과 불명이 되었다고 해서 또 다른 Discord 즉시 알림을 만들지도 않습니다. 사용자는 로컬 관리 콘솔의 알림 기록(#notices)과 결과 불명(#unknowns) 화면에서 전달 결과를 확인하고, 필요하면 콘솔이나 CLI에서 관찰 결과를 정리할 수 있습니다.

    실제 Discord 연결에 필요한 봇 토큰은 kos-ops 프로필의 .env에 보관하며, 봇이 대상 서버에 초대되어 있고 설정된 채널의 보기·메시지 보내기 권한을 갖고 있어야 합니다. 권한이 없으면 첫 발송이 not_delivered로 남고 채널에는 메시지가 뜨지 않습니다.

    실제 확인 범위#

    실제 Discord 요약·데일리 전달과 발송용 Profile 설치의 근거는 현재 상태에 모았습니다. 기본 08:00 시각의 자연 실행, 실제 충돌·쓰기 결과 불명에 따른 즉시 알림, Discord 입력 무응답의 직접 관찰은 별도 확인 범위입니다.
