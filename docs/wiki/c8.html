    C8 알림 (Discord 알림)

    한눈에 보기#

    C8은 KnowledgeOS가 Discord로 보내기만 하는 알림 기능입니다. 매일 아침 하루치 상황을 모은 요약(digest) 을 보내고, 충돌·결과 불명·작업 실패처럼 늦으면 곤란한 일은 즉시 알림(alert) 으로 바로 알립니다. 알림에는 노트 본문 없이 제목과 링크만 들어가며, 링크를 누르면 Obsidian이나 관리 콘솔이 열립니다. Discord에서 메시지·반응·답장을 보내도 아무 일도 일어나지 않습니다.

    항목 내용
    트리거요약: 예약 작업 digest(매일 08:00, C7) 또는 CLI knowledgeos job run digest. 즉시 알림: Owner가 Vault와 작업 기록의 변화를 스스로 관찰해 발송
    담당내용은 StewardshipOfficer(C5), 전달은 Notifier(운영 profile kos-ops를 통한 Discord 발송). Owner가 알림 의도를 먼저 기록
    결과물Discord 알림(요약·즉시 알림)과 Owner가 남기는 알림 기록
    사용자 결정 여부없음. 알림은 알려 주기만 하고, 승인·적용·거절은 Obsidian과 콘솔에서 합니다

    참고

    용어: Owner는 권한과 기록을 맡는 KnowledgeOS의 중심 서비스, attention item(주의 항목) 은 사용자가 봐야 할 일(노트로 저장되지 않고 Bases 화면이나 콘솔·요약에서 계산됨)입니다. 자세한 뜻은 용어를 보세요.

    왜 이 명세가 필요한가#

    알림은 사용자에게 가장 쉽게 새어 나가는 통로입니다. 그래서 USER_FEATURE_SPEC의 "지키는 약속" 가운데 다음을 직접 지켜야 합니다.

    • Vault는 사용자의 것입니다 / 판단이 필요한 변경은 사용자가 결정합니다(약속 1·4). Discord에서 어떤 반응으로든 변경이 승인되면 이 약속이 깨집니다. 그래서 C8은 단방향이며, 명세는 "Discord로 명령 받기"를 하지 않는 일로 명시합니다(USER_FEATURE_SPEC "하지 않는 일").
    • 문서 작업은 Obsidian 안에서 합니다(약속 2). 알림은 사용자를 Obsidian이나 콘솔로 데려다 주는 링크일 뿐이고, 처리는 거기서 합니다.
    • 개인정보(ai_policy). deny·local_only·confidential 노트의 제목이나 식별 정보가 알림에 실리면, 외부 서비스인 Discord로 비밀이 나갑니다(Blueprint §5.4). C8이 없으면 알림 하나로 개인정보 경계가 무너질 수 있습니다.
    • 잃으면 안 되는 것은 Vault에 둡니다(약속 6). 알림 기록은 State에 있어서, 잃어도 알림만 사라지고 지식은 남습니다(Blueprint §2). 알림이 전달됐는지 확실하지 않을 때 다시 보내지 않는 규칙도 같은 맥락입니다. 같은 알림이 반복되면 알림이 소음이 되기 때문입니다.

    철학 쪽 배경은 운용 원칙에서, 용어는 용어에서 확인할 수 있습니다.

    어떻게 쓰는가#

    Discord 알림을 받기 위해 Obsidian에서 눌러야 할 명령은 없습니다. Thin Client에는 Discord 관련 명령이 없습니다(C11의 명령 표 참고). 알림은 Owner가 켜져 있는 동안 자동으로 갑니다.

    자동 경로

    1. Owner가 켜져 있으면 매일 08:00(Asia/Seoul)에 digest 작업이 돌아 요약을 보냅니다.
    2. 충돌·결과 불명·작업 실패가 생기면, 요약을 기다리지 않고 Owner가 변화를 관찰해 즉시 알림을 보냅니다. GET 요청이나 콘솔 방문, 요약 실행이 있어야 알림이 나가는 것이 아닙니다.
    3. 알림의 obsidian:// 링크는 해당 노트를 Obsidian에서 엽니다. 모바일에서도 열립니다(USER_FEATURE_SPEC "모바일"). 관리성 항목은 콘솔 링크가 붙습니다.
    4. Owner가 꺼져 있으면 예약 작업이 돌지 않아 요약도 가지 않습니다. 다시 켜고 startup_delay_minutes(기본 3분)가 지나면 놓친 작업이 한 번씩만 실행됩니다(C7).

    수동 경로 (CLI)

    knowledgeos job run digest      # 요약을 지금 보내고, 실행 결과 영수증까지 따라가 보고
knowledgeos install profiles --config owner.json --dry-run   # 먼저 무엇이 설치될지 확인
knowledgeos install profiles --config owner.json    # 역할 profile과 발송 전용 kos-ops profile 설치

    콘솔에서 확인

    • 브라우저 관리 콘솔(로컬 전용)에서 알림 기록, 결과 불명 목록, 주의 항목을 봅니다(Blueprint §3.2). 알림 전달이 불명이 되었다면 거기에 나타납니다.
    • 콘솔은 관리용이며, 문서 작업은 하지 않습니다.

    처음 연결할 때 (사용자 몫)

    • kos-ops profile은 모델 없이 Discord 발송에만 쓰이고 봇 토큰을 보관합니다(USER_FEATURE_SPEC·Blueprint §4.4).
    • 봇은 서버에 초대되어 있어야 하고, 지정된 채널에서 View Channel과 Send Messages 권한이 필요합니다. PROJECT_STATE의 B_DISCORD_TOKEN이 바로 이 조치였고 해결됐습니다(현재 상태).

    예시 (설명용 시나리오)

    1. 월요일: remote_ok 노트 하나에 병합 충돌 표시가 생깁니다. Owner가 변화를 관찰해 노트 제목과 obsidian:// 링크가 담긴 즉시 알림을 한 번 보냅니다.
    2. 월요일 08:00 요약과 화요일 08:00 요약에는 이 충돌이 계속 "주의 항목"으로 적힙니다. 알림은 새로 오지 않습니다(NTF-2).
    3. 같은 시기에 deny 노트에서 문제가 생겨도 어떤 알림에도 그 노트는 언급되지 않습니다(NTF-1).
    4. 사용자가 링크로 Obsidian을 열어 직접 충돌을 정리합니다. Discord에 답장해도 아무 일도 일어나지 않습니다.

    동작 흐름#

    알림은 "누가 내용을 만들고, 누가 보내고, 무엇을 걸러 내는가"를 나눠 맡습니다. 이 기능에 딱 맞는 전용 흐름도는 계약에 없어서, 번호 흐름과 개인정보 표를 함께 둡니다.

    1. 내용 구성: StewardshipOfficer가 요약이나 알림 내용을 정해진 규칙(결정적 코드)으로 만듭니다. 요약은 새 자동 변경의 개수와 제목, 대기 중인 제안·보고서, 오래된 제안, 결정이 필요한 계산된 주의 항목, "다시 볼" 목록을 담습니다. 즉시 알림은 Vault 충돌, 결과 불명, 작업 실패 세 종류이고 항목 ID로 중복을 막습니다.
    2. 개인정보 거르기: 알림에는 remote_ok·ask 노트의 제목과 링크만 실릴 수 있습니다. deny·local_only·confidential 노트는 본문은 물론 식별 정보도 나가지 않습니다.
    3. 의도 기록: Owner가 알림을 보내기 전에 알림 의도를 기록합니다.
    4. 전달: Notifier가 kos-ops profile로 Discord에 보냅니다.
    5. 결과 판정: 전달이 확인되지 않으면 결과는 unknown으로 남고 자동으로 다시 보내지 않습니다. 요약은 항상 현재 상태를 반영하므로, 아직 유효한 내용은 다음 요약에 다시 실립니다. 결과 불명인 알림 전달이 또 다른 알림을 만들지는 않습니다.

    C8 Notifications#

    Outbound Discord notices through the KnowledgeOS bot. The StewardshipOfficer composes the content and the Notifier delivers it.

    • Digest (daily):
      • Counts and titles of new autofix changes.
      • Proposals and reports waiting.
      • Stale proposals.
      • Computed attention items needing a decision.
      • The "revisit" set.
    • Alert (immediate, deduplicated by item ID): a Vault conflict, an unknown effect outcome or a failed job. The Owner observes changes independently of reads; no GET, console visit or digest is needed to trigger an alert. An unknown notification delivery does not recursively generate another alert.
    • Content: titles and counts only, obsidian:// links to eligible notes and console links for management items. Only remote_ok and ask note titles and links may be disclosed. No body text or identifying information from deny, local_only or confidential notes appears in either digests or immediate alerts.
    • Delivery: the Owner records each notice intent before delivery. An unknown delivery is never re-sent. The digest reflects current state, so the next digest carries anything still relevant.

    Acceptance:

    • NTF-1 Given an attention item from a deny note, then no notice mentions it.
    • NTF-2 Given the same unresolved conflict on two days, then one alert was sent and both digests list it.
    • NTF-3 Given a notice with an unknown delivery outcome, then it is not re-sent.

    현재 상태와 남은 일#

    • 구현·테스트: 인수 예시 NTF-1~NTF-3은 모두 구현과 통과한 테스트에 연결되어 있습니다(CAPABILITY_TRACE, PROJECT_STATE의 E_CAPABILITY_TRACE·E_TRACED_TESTS). 이 테스트들은 모델 역할과 Discord 전송에 대역을 씁니다(README "검증 범위").
    • 실환경 Discord 전달: KNOWLEDGEOS_REAL_ADOPTION.DISCORD가 통과했습니다. E_DISCORD_DELIVERED는 요약 알림 하나가 Owner와 kos-ops 발송 경로를 거쳐 knowledgeos 채널에 전달된 기록입니다. 이에 앞서 봇이 서버에 들어오기 전에는 Discord API 403 Missing Access로 첫 요약이 not_delivered로 기록됐고(E_DISCORD_MISSING_ACCESS, 이력으로 보존), 봇 초대와 권한 부여로 B_DISCORD_TOKEN이 해결됐습니다.
    • 알림 기록의 범위: D_NOTICE_NO_FAILURE_REASON에 따라 알림 기록에는 전달 실패 사유를 남기지 않습니다.
    • Hermes cron 제거: 예약은 Owner 안의 스케줄러만 맡습니다. E_HERMES_CRON_REMOVED는 kos-ops의 Hermes cron 작업 세 개를 지우고 발송 전용으로 다시 설치했음을 기록합니다.
    • PROJECT_STATE에 기록되지 않은 것 ([INFERENCE] 기록에서 찾지 못했다는 뜻이며 일어나지 않았다는 뜻은 아닙니다): 정해진 08:00 슬롯에서 자연스럽게 돈 실제 요약 실행, 실제 환경에서 즉시 알림이 나간 사례는 증거 기록에 없습니다. 실환경 스케줄러 증거(E_REAL_SCHEDULER_SLOT)는 임시 index.embed 작업이며, 현재 인계 항목은 열린 정리 제안 검토, 매시간 규격화의 자연 실행 관찰, 임계값 조정입니다.

    참고

    보내기 전용 구성: kos-ops profile에는 Hermes gateway가 이 profile을 Discord 수신·예약 실행 대상에서 빼도록 하는 gateway.parked 표시가 있고, 발송은 hermes -p kos-ops send로만 합니다(E_HERMES_CRON_REMOVED). 그래서 Blueprint §9의 "보내기 전용 Discord" 열린 질문은 닫혔습니다. 봇이 입력을 받지 않는다는 것을 따로 관찰한 기록은 아직 없습니다.

    시작 전·막힘·후속 과제 전체는 로드맵에서 보세요.

    관련 기능#

    • C5 문서 관리: 요약과 즉시 알림의 내용(주의 항목, 오래된 제안, "다시 볼" 목록)을 만드는 StewardshipOfficer의 기능입니다.
    • C7 예약 작업: digest 작업이 매일 08:00에 요약을 보내는 스케줄입니다. Owner가 꺼져 있을 때의 따라잡기 규칙도 여기에 있습니다.
    • C6 검토: 알림에 나온 대기 제안과 오래된 제안을 실제로 적용·거절하는 곳입니다. Discord에서는 결정할 수 없습니다.
    • C2 규격화: 요약이 세는 "새 자동 변경"(autofix)을 만듭니다.
    • C1 정리와 C4 강화: 요약이 "대기 중"으로 알리는 제안(01_AI_Review/Proposals/)과 보고서(01_AI_Review/Reports/)를 만듭니다.
    • C11 호출·관리 화면: 콘솔의 알림 기록과 CLI job run digest를 제공합니다.
