    C5 문서 관리 (Document management)

    문서 관리는 Vault에 쌓이는 문제(충돌 표시·깨진 YAML·중복 ID)와 방치된 노트를 찾아 보여 주고, 수명주기가 끝났거나 상태가 바뀐 노트에 대해 적용 전까지 노트를 건드리지 않는 제안을 만드는 기능입니다. 노트를 직접 만들거나 옮기거나 지우는 일반 편집은 계속 Obsidian에서 사용자가 하며, KnowledgeOS가 만드는 것은 01_AI_Review/Proposals/의 제안 노트뿐입니다.

    1. 세 가지 동작 경로와 실행 구조#

    문서 관리는 세 가지 경로로 나뉘며, 전용 Thin Client 명령은 없습니다. 실행 구조의 공통 단계는 구조에 있습니다.

    경로 무엇을 읽고 무엇을 내는가 Hermes Profile Graph / Temporal
    Obsidian Bases 보기 (99_System/Bases/)Obsidian이 Vault .md 파일의 frontmatter와 수정 시각을 직접 필터링해 여섯 표로 표시없음없음 (KnowledgeOS 미호출)
    주의 항목 조회 (GET /api/attention, vault-check, 콘솔)Owner가 현재 Vault와 State를 스캔해 주의 항목을 즉시 계산해 반환 (파일로 저장하지 않음)없음없음 (직접 동기 조회, Work 없음)
    수명주기 제안 · 만료 · 요약 (digest.run)매일 08:00 digest 작업(C7) 또는 knowledgeos job run digest가 실행. 정적 StewardshipOfficer(필요 시 System One 직접 호출)와 정적 EvalOfficer가 제안 작성·낡은 제안 만료·C8 요약 생성모델 역할 없음 (단, 요약 Discord 발송 시에만 모델 없는 kos-ops 사용)StewardshipOfficer → evaluation 1개 생산자 직렬 LangGraph + WorkWorkflow

    digest.run은 선언상 C8 카탈로그에 연결되어 있지만 실제 작업 수행자와 정적 평가 규칙을 StewardshipOfficer가 맡습니다. 사용자가 나중에 제안 노트를 적용 또는 거절할 때도 C6 처리기가 접수 worker 안에서 동기 처리하므로 ActionWorkflow는 열리지 않습니다.

    2. Obsidian Bases 화면이 보여 주는 여섯 목록#

    99_System/Bases/ 아래 Vault 자산(Inbox.base, Knowledge.base, Review.base, Projects.base)이 다음 여섯 보기를 제공합니다.

    • 3일 넘은 미처리 포착(Inbox.base · Older than 3 days): type: capture, status: unprocessed, created가 3일보다 오래된 노트(DOC-1).
    • 30일 넘게 손대지 않은 아이디어(Knowledge.base · Ideas untouched 30 days): type: idea, status가 seed·developing·mature이고 파일 수정 시각이 30일보다 오래된 노트.
    • 열린 질문(Knowledge.base · Open questions): type: question, status: open.
    • 대기 중인 제안(Review.base · Proposals waiting): type: proposal, status가 open·stale.
    • 14일 넘게 손대지 않은 보고서(Review.base · Reports untouched 14 days): type: report, 파일 수정 시각이 14일보다 오래된 노트.
    • 상태별 프로젝트(Projects.base · By status): type: project, status가 planned·active·paused·done.

    3. 주의 항목 탐지 알고리즘 (GET /api/attention)#

    Bases가 표현할 수 없는 구조·운영 문제는 Owner가 GET /api/attention(브라우저 콘솔 주의 항목 탭과 digest 요약이 함께 사용)에서 매번 Vault와 State를 훑어 계산합니다. 주의 항목은 노트로 저장하지 않으므로 원인을 고치면 다음 조회에서 즉시 사라집니다.

    스캔할 때 ai_policy: deny이거나 퇴역·알 수 없는 정책값(빠지거나 빈 값만 approve)인 노트와 99_System/ 아래 파일은 처음부터 제외합니다. 탐지하는 여덟 종류는 다음과 같습니다.

    1. duplicate_id (중복 ID): deny가 아닌 노트 중 같은 id를 가진 파일이 둘 이상이면 경로 목록을 묶어 표시합니다. 두 노트 모두 C3 검색에서는 계속 찾히지만, id:<값>을 지정한 정리·규격화 요청은 모호하므로 거부됩니다(DOC-2).
    2. conflict (충돌 표시): <<<<<<<, =======, >>>>>>> Git 병합 충돌 표시가 있는 노트입니다(심각도 alert). 모든 자동화가 이 노트를 건너뛰며(DOC-3), C8 감시기가 Discord 즉시 알림도 보냅니다.
    3. invalid_yaml (깨진 YAML·인코딩 오류): UTF-8로 읽을 수 없거나 YAML frontmatter 구문이 깨진 노트입니다. CLI knowledgeos vault-check(GET /api/vault-check)도 위 1~3번(invalid_yaml, conflicts, duplicate_ids)만 검사하며, 역시 deny 노트는 절대 출력하지 않습니다.
    4. stale_proposal (낡은 제안): 01_AI_Review/Proposals/의 유효한 제안 중 대상 노트가 deny로 바뀌지 않았는데, 이미 status: stale이거나 대상이 지워졌거나(또는 중복 ID로 모호해졌거나) 대상의 현재 SHA-256이 제안에 적힌 target_sha256과 다르면 표시합니다. 참고로 대상을 바이트 그대로 다른 폴더로 옮기기만 했을 때는 id로 따라가기 때문에 낡은 제안이 되지 않습니다.
    5. autofix (최근 자동 변경): State changes/ 기록 중 kind: autofix이고 recent_autofix_days(기본 7일, config/capabilities/C5.json) 이내이며 대상이 현재 deny가 아닌 항목입니다. 콘솔 주의 항목에만 나오며 C8 Discord 요약에는 들어가지 않습니다.
    6. unknown (미해결 결과 불명): State unknowns/ 중 아직 사람 확인(resolution)이 없는 항목입니다(심각도 alert, 대상 경로가 deny면 숨김). 콘솔에서 실제 상태를 확인한 뒤 적용됨 / 적용 안 됨 확인 기록을 남기면 목록에서 빠집니다.
    7. 예약 작업 이상 (failed_job, blocked_job, missed_job): C7 작업 상태를 읽어 마지막 실행이 failed·unknown이면 failed_job(alert), unmet·refused·cancelled이면 blocked_job(attention), 일시정지가 아닌데 두 번의 예약 간격 이상 실행 기록이 없으면 missed_job을 올립니다. 작업 이상은 콘솔 전용이며, failed_job만 다른 검토 항목이 있을 때 C8 요약 끝에 보조 한 줄로 붙습니다.
    8. revisit (다시 볼 노트): 제외 사유가 없고 30일 이상 수정되지 않은 미완결 아이디어(idea 중 dropped·archived 제외)와 열린 질문(question 중 open)을 경로순으로 모은 뒤, 오늘 날짜(toordinal() % 후보 수)를 시작점으로 매일 순환하며 최대 revisit_count(기본 3개)를 고릅니다.

    sensitivity: confidential과 ai_policy: approve를 함께 썼다고 해서 "정책 불일치" 주의 항목을 띄우지는 않습니다. 두 속성은 독립적이며 정책 결정은 사용자의 몫입니다.

    4. 수명주기 제안 생성 · System One 상태 판단 · 만료#

    매일 08:00 digest.run이 실행되면 정적 Director가 두 갈래로 대상 노트를 모아 StewardshipOfficer Work를 엽니다(대상이 비어도 만료 점검과 요약을 위해 실행됩니다).

    1단계: 정적 보관 규칙과 System One 후보 선별#

    기본 적격 조건은 deny 아님, 유효한 YAML, 충돌 없음, 제외 경로(99_System/·01_AI_Review/·00_Inbox/Requests/·숨김·80_Assets/) 아님, 중복 ID 아님입니다.

    • 정적 보관 제안 대상: type: project·status: done이거나 type: idea·status: dropped인 노트는 모두 대상이 됩니다. 이 경우 status: archived 설정과 90_Archive/ 이동(파일명 유지) 2개 항목을 담은 보관 제안을 계획합니다(DOC-4).
    • System One 상태 판단 후보: settings.system_one이 설정된 경우에만 추가로 선별합니다. 현재 ai_policy가 approve이고, 열린·낡은 제안이 이미 대상 경로나 id를 예약하고 있지 않으며, State lifecycle_seen/에 저장된 마지막 질문 해시와 현재 파일 SHA-256이 다른 노트 중 아래 세 경우를 뽑습니다.
    현재 종류·상태 System One에게 묻는 참/거짓 질문 확률 >= 0.7일 때 제안하는 변경
    question · open본문에 이미 질문의 답이 적혀 있는가status: answered
    project · planned / active / paused본문에 프로젝트가 완료·종료되었다고 밝히는가status: done
    idea · seed / developing / mature본문에 작성자가 아이디어를 포기했다고 밝히는가status: dropped

    2단계: 전송 직전 재검사와 실패 fallback#

    StewardshipOfficer는 System One(POST /v1/decisions, 기본 모델 gpt-6-luna, Hermes Profile 없음)에 묻기 직전 디스크에서 노트를 다시 읽어 sha 불일치, 충돌, 중복 ID, 예약 제안 발생 여부를 재확인하고, 접수 시점과 현재 모두 approve인 노트만 보냅니다.

    응답 확률이 min_confidence(기본 0.7) 이상이면 단일 status 변경 제안을 만듭니다(체크리스트에 System One 판단과 확률을 표기). 만약 System One이 꺼져 있거나 요청 도중 통신·키 파일 오류(SystemOneUnavailable)가 나면, 그 실행에서는 나머지 System One 질문만 멈추고 정적 보관 제안과 기존 제안 만료·요약은 그대로 끝마칩니다. 실패해 묻지 못한 노트는 lifecycle_seen에 기록하지 않으므로 다음 digest 실행 때 다시 묻습니다(DOC-5). 정적 EvalOfficer는 모든 제안이 허용된 정적/System One 규칙과 approve 정책을 따르는지 검사한 뒤 파일 반영 단계로 넘깁니다.

    3단계: 제안 작성 · 재생성 보존 · 낡은 제안 만료#

    01_AI_Review/Proposals/<제목> — archive.md 또는 <제목> — status.md로 제안을 씁니다. System One 상태 제안은 쓰기 직전에도 기존 예약 제안이 없는지 다시 확인합니다.

    • 중복 방지와 사용자 편집 보존: 같은 대상에 열린(open) 제안이 이미 있으면 두 번째 제안을 만들지 않습니다. State proposals/<id>.json에 기록된 Owner 작성 바이트와 정확히 같을 때만 제자리 갱신(regenerated)하거나 내용 동일 시 건너뛰며(unchanged), 사용자가 체크리스트를 고쳤거나 State 기록이 사라진 제안은 절대 덮어쓰지 않습니다(user_edited, DOC-4). 이미 낡은(stale) 제안이 대상을 예약하고 있을 때도 digest는 새 제안을 만들지 않고 둡니다.
    • 질문 기록 시점: System One에 실제로 보낸 노트의 sha는 제안 파일 쓰기가 끝난 뒤에야 State lifecycle_seen/에 저장합니다. 덕분에 Work가 중간에 실패하면 다음 실행이 다시 질문하고, 정상 완료 뒤 기준 미만으로 판정된 노트는 본문을 수정할 때까지 다시 묻지 않습니다(DOC-5).
    • 낡음 전환과 7일 뒤 삭제: 제안 쓰기가 끝난 뒤 01_AI_Review/Proposals/의 모든 open·stale 제안을 점검합니다(대상이 deny면 건드리지 않음). open 제안의 대상이 사라졌거나 중복 ID가 됐거나 내용 해시가 바뀌었으면 제안의 status를 stale로 바꾸고 kos_stale_at 시각을 남깁니다. 이미 stale인 제안은 stale_at 기록(없으면 kos_stale_at, 파일 mtime 순)으로부터 7일이 지났고 제안 파일 바이트가 그대로일 때 삭제(expired)합니다(C6).
    • 요약 발송: 마지막으로 C8 send_digest를 호출해 검토할 제안·새 보고서·3일 넘은 포착·확인 대기 작업·주의 항목이 1건 이상일 때만 Discord로 요약을 보냅니다.

    5. 실제 입력과 결과 예시#

    예시 1: 완료 프로젝트의 보관 제안, 편집 보존, 이동·만료#

    1. 월요일에 20_Projects/Finished/Finished.md의 status를 done으로 바꿉니다. 다음 digest에서 01_AI_Review/Proposals/Finished — archive.md(status: archived, 90_Archive/ 이동 체크리스트 2개)가 1건 생성되고 요약의 proposals 수에 잡힙니다(DOC-4).
    2. 아무것도 바꾸지 않고 digest가 한 번 더 돌아도 제안은 unchanged로 1건만 유지됩니다. 만약 사용자가 제안에서 이동 체크를 해제하거나 메모를 적었다면 다음 digest는 user_edited로 남기고 덮어쓰지 않습니다.
    3. 제안이 열린 상태에서 Finished.md를 바이트 그대로 20_Projects/Moved/Moved.md로 이동만 하면 id로 대상을 계속 찾으므로 낡은 제안이 되지 않습니다. 반대로 본문을 고치거나 파일을 삭제하면 다음 digest가 제안을 stale로 바꾸고 콘솔 주의 항목(stale_proposal)에 올리며, 7일 뒤 제안 파일을 삭제합니다.

    예시 2: System One 상태 제안과 deny 제외#

    40_Knowledge/Questions/Sky.md(open, approve, 본문에 답이 적힘), Private.md(open, 퇴역 정책 ask → deny로 닫힘), Alive.md(idea, seed, approve, 아직 진행 중)가 있을 때 System One이 켜진 상태에서 digest를 실행합니다. Private.md는 내용이 전혀 전송되지 않고, Sky.md는 확률 0.95로 status: answered 단일 제안이 생성되며, Alive.md는 확률 0.05로 제안이 생기지 않습니다. 두 번째 digest 실행은 바뀐 노트가 없으므로 System One을 한 번도 부르지 않습니다(DOC-5).

    6. 실환경 확인 범위와 구현 근거#

    실제 Bases 보기와 System One 상태 제안의 관찰 범위는 현재 상태에서 확인합니다. 요약 메시지 전달 성공만으로 문서 관리의 모든 분기를 확인한 것은 아닙니다. 기본 확신도와 요약 주기의 적합성, 코어 Bases로 충분한지는 로드맵의 실제 사용 과제입니다.

    • 명세: C5 Document management, 제안 파일 형식
    • 구현·설정: StewardshipOfficer·주의 항목·만료, 제안 렌더링·보존, digest.run 등록·요약, vault-check 계산, System One 클라이언트, C5 설정, C8 설정
    • 관련 기능: C1, C2, C3, C6, C7, C8
