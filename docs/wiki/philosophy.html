    위키·명세 운용 원칙

    이 페이지는 두 가지를 설명합니다. KnowledgeOS의 명세는 어떤 규칙으로 관리되는가, 그리고 이 위키는 왜 있고, 개발 세션마다 어떻게 갱신하는가입니다.

    왜 위키가 있나#

    KnowledgeOS의 사실은 여섯 개 문서에 나뉘어 있습니다. 동작 기준, 사용자 의도, 시스템 제약, 추적표, 진행 상태, 실행 방법입니다. 각각은 정확하지만 한 문서만 읽어서는 "이 기능이 왜 있고, 어떻게 쓰고, 어디까지 되고, 무엇이 남았는지"를 알기 어렵습니다.

    위키는 그 사실들을 기능 단위로 다시 엮어 한곳에서 읽게 해 주는 해설판입니다.

    • 규칙을 새로 만들지 않습니다. 동작·상태에 관한 문장은 원본 문서에서 온 것입니다.
    • 원본에 없는 내용은 해설로 쓰더라도 "해석" 또는 "기록 없음"으로 표시합니다.
    • 위키와 원본이 어긋나면 원본이 맞고, 위키는 다시 생성해서 바로잡습니다.

    휴대폰에서 읽기#

    휴대폰 브라우저에서도 같은 HTML을 읽습니다. 좁은 화면에서는 위쪽 메뉴 버튼으로 전체 목차를 열고, 그 아래 한 줄을 차지하는 검색창으로 페이지·제목·본문을 찾습니다. 본문은 화면 폭에 맞춰 줄을 바꾸며 브라우저 확대를 막지 않습니다.

    • 표·코드: 글자를 화면에 억지로 줄이지 않습니다. 가로로 넘치는 영역 앞에 안내가 나타나며 그 영역 안에서 좌우로 이동합니다.
    • 그림: 먼저 전체 구조를 화면 폭으로 봅니다. 그림 크게 보기를 누르면 글자를 읽을 수 있는 크기로 바뀌고 좌우로 이동할 수 있습니다. 그림 전체 보기로 돌아옵니다.
    • 메뉴: 링크의 터치 영역을 넓혔습니다. 메뉴 밖을 누르거나 메뉴 버튼을 다시 누르면 닫힙니다.

    모바일 접속 경로 제안#

    아래는 배포 제안이며, 접속 주소를 설치하거나 외부에 공개했다는 뜻은 아닙니다. 정적 위키 열람과 KnowledgeOS 실행·관리 API의 원격 접속은 별개입니다.

    경로 적합한 경우 조건·주의
    비공개 HTTPS + Tailscale Serve (권장)집 밖에서도 본인 휴대폰으로 최신 위키 열람정적 위키 전용 loopback 서버와 기기별 Tailscale 연결, HTTPS 활성화 필요. 접근 규칙을 본인 기기로 제한. Mac이 켜져 있어야 함. Owner·관리 콘솔은 연결하지 않음
    같은 Wi-Fi의 정적 서버집 안에서 임시 확인휴대폰의 localhost는 Mac이 아님. Mac의 LAN 주소 사용. 공유기 포트 포워딩 없이 사용하고 다른 LAN 기기에도 노출될 수 있음을 고려
    파일 묶음을 휴대폰으로 복사오프라인 보관HTML과 assets/를 함께 복사. iOS 파일 미리보기는 여러 파일 간 탐색·스크립트를 제한할 수 있어 실제 사용할 뷰어에서 확인 필요
    공개 정적 호스팅공개용 문서 배포현재 위키를 그대로 공개하지 않음. 상태·검색 색인·SVG에 포함된 내부 정보까지 선별한 공개용 묶음 필요

    권장 구성은 정적 HTML·assets만 담은 배포 폴더 → 별도 정적 파일 서버 → 비공개 HTTPS 주소 → 휴대폰 브라우저입니다. 홈 화면에 바로가기를 추가하면 재접속하기 쉽습니다. 서비스 워커나 오프라인 캐시는 추가하지 않으므로 오프라인 앱처럼 동작하지는 않습니다.

    저장소 원문으로 가는 링크는 위키 폴더 밖의 상대 경로입니다. HTML·assets만 배포할 때는 그 원문 링크가 열리지 않으며, 원문이 필요하면 승인된 문서를 함께 배포하고 경로를 맞춰야 합니다. 원문 링크를 살리려고 저장소 전체를 서버 루트로 노출하지 않습니다. 외부 연결·배포는 별도 승인이 필요하고 ExOps의 loopback·Host/Origin 보호는 바꾸지 않습니다.

    Tailscale Serve 공식 안내에 따르면 Serve는 tailnet 내부 공유이며 접근 규칙이 적용됩니다. 공개 인터넷으로 여는 Funnel은 이 권장안에 포함하지 않습니다. macOS 클라이언트별 디렉터리 직접 제공 제약을 피하기 위해 별도 loopback 정적 서버의 포트를 연결하는 방식을 제안합니다.

    명세는 어떻게 관리되나 (Blueprint §0)#

    아래는 Blueprint §0 "Spec governance"의 원문입니다. 쉬운 말로는 이렇습니다.

    • 명세는 지금 맞는 것만 적습니다. 과거·증거·설치 상태는 Git과 PROJECT_STATE에 둡니다.
    • 동작을 바꾸는 변경은 같은 변경 안에서 명세도 고칩니다. 낡은 문장은 "폐기됨" 표시를 달지 않고 지웁니다.
    • 인수 시나리오(예: [[ORG-1]])가 곧 실행 가능한 테스트이며, 시나리오를 지우거나 성공 기준을 약하게 하지 않습니다.
    • 기능 하나를 얇게 끝까지 만들어 써 보고, 배운 것으로 명세를 고칩니다.
    • 아직 정하지 않은 것은 Blueprint §9의 열린 질문에 둡니다. 구현이 이미 답한 질문은 지웁니다(로드맵).
    • 명세와 위키는 함께 움직입니다. 위키를 쓰거나 다시 생성하다 문서끼리 어긋나는 곳을 발견하면 위키에 경고를 남기지 않고, 같은 세션에서 우선순위가 낮은 문서를 고칩니다. 위키 갱신은 곧 주기적인 명세 점검입니다.
    원본: OBSIDIAN_VAULT_BLUEPRINT.md · 0. Spec governance

    0. Spec governance#

    The spec is a living contract, not a phase document. These rules keep it from rotting.

    • Current truth only. The spec states intended behavior. It contains no history, evidence, install status, observed versions or "retained/legacy" sections. History lives in Git; progress and evidence live in PROJECT_STATE.md.
    • Precedence. By explicit user decision, docs/CAPABILITIES.md is the top-level behavior and acceptance specification. USER_FEATURE_SPEC.md supplies intent and this Blueprint supplies system constraints; both supplement capabilities without weakening their acceptance coverage. This precedence does not authorize changes to Core contracts or schemas. A conflict is a defect to fix in the same change, never a tolerated divergence.
    • Spec and code move together. A change that alters behavior edits the spec in the same change. When implementation teaches something the spec did not anticipate, revise the spec immediately rather than coding around it.
    • Delete, don't annotate. Superseded text is removed, not marked deprecated.
    • Examples are the contract. Preserve every acceptance ID and example in docs/CAPABILITIES.md as an executable test through a public interface. Fix implementation or testability gaps without deleting examples or narrowing their success criteria.
    • Thin vertical slices. Build one capability end to end, use it, then refine the spec from what was learned. Unresolved choices stay in §9 until a slice needs them.
    • Stay small. Prefer removing a rule to adding one. Add a type, property, role, capability or check only when real use needs it.
    • Visible development state. The wiki at docs/wiki/ explains capabilities, their purpose, how to use them, what is blocked or not started and what follows next, generated from this spec, docs/CAPABILITY_TRACE.md and PROJECT_STATE.md plus authored explanations in docs/wiki/_source/. Every development session updates the source documents and wiki explanations for its changed scope, regenerates it with make wiki, passes make wiki-check and reviews the changed pages in a browser before handoff. The wiki explains; it never overrides these source documents.
    • Spec and wiki move together. Updating the wiki is also a periodic spec review: when writing or regenerating pages exposes a conflict between docs/CAPABILITIES.md, this Blueprint, USER_FEATURE_SPEC.md and PROJECT_STATE.md, fix the lower-precedence document in the same session instead of leaving a warning in the wiki, and remove §9 open questions that implementation has already answered.
    • Reference material. Tmp/active/knowledgeos-spec-references-2026-11-19/REFERENCES.md maps earlier source that matches this direction. It is non-normative, and the spec wins on conflict.

    사용자와의 약속·범위·운용#

    아래 세 블록은 USER_FEATURE_SPEC.md의 해당 절을 그대로 가져온 것입니다. 일곱 가지 지키는 약속은 KnowledgeOS가 사용자에게 한 것이고, 각 기능 페이지의 "왜 이 명세가 필요한가"는 이 약속 중 어떤 것을 지키려는지 가리킵니다. 하지 않는 일은 범위 밖으로 정한 것이고, 명세 운용은 이 페이지 위쪽의 원칙을 사용자 쪽에서 적은 것입니다.

    원본: USER_FEATURE_SPEC.md · 지키는 약속

    지키는 약속#

    1. Vault는 사용자의 것입니다.
      • 맥·iPhone·iPad 어디서든 어떤 노트든 자유롭게 쓰고, 고치고, 옮기고, 지울 수 있습니다.
      • frontmatter·폴더·등록 없이 쓴 Markdown도 그대로 유효합니다.
    2. 문서 작업은 Obsidian 안에서 합니다.
      • 쓰기·검색·보기는 Obsidian core와 community plugin이 맡습니다.
      • KnowledgeOS 기능 호출은 최소한의 Thin Client 명령과 사이드바 탭이 맡습니다.
      • 관리는 브라우저 콘솔과 CLI가 맡고, 문서 작업은 거기서 하지 않습니다.
    3. 유지보수는 가능한 한 오픈소스에 맡깁니다. 화면·보기·템플릿·버튼은 plugin을 쓰고, Thin Client는 커지지 않게 유지합니다.
    4. 자동으로 바꾸는 것은 작고 기계적인 것뿐입니다.
      • 빠진 frontmatter를 채우는 규격화만 자동입니다. 정해진 선택지(enum) 안에서 고르는 값은 System One이 충분히 확신할 때만 고릅니다.
      • 그 밖에 판단이 필요한 변경은 제안으로 만들고, 적용은 사용자가 결정합니다.
    5. Git이 백업이자 이력입니다.
      • Vault는 GitHub private repo와 동기화됩니다. 맥은 사용자의 동기화 방식으로, iOS는 Working Copy로 합니다.
      • KnowledgeOS는 git 명령을 실행하지 않고, diff가 작고 읽기 쉽게 씁니다.
    6. 잃으면 안 되는 것은 Vault에 둡니다. KnowledgeOS 내부 상태와 자격증명은 Vault 밖에 있어 GitHub로 올라가지 않으며, 잃어도 지식은 남습니다.
    7. 근거를 밝힙니다. 결과는 이미 쓴 노트를 정확히 인용하고, 근거·추론·근거 없음을 구분합니다.
    원본: USER_FEATURE_SPEC.md · 하지 않는 일

    하지 않는 일#

    • 브라우저·CLI에서 문서 작업하기. 둘은 관리용입니다.
    • Thin Client에 명령 호출 탭을 넘어 문서·작업 목록이나 설정을 늘리기. plugin으로 할 수 있으면 plugin을 씁니다.
    • 사용자 노트 삭제, 자동 병합, 판단이 필요한 변경의 자동 적용.
    • git commit·pull·push.
    • 다른 모델로 몰래 바꾸기, 의미 검색이 안 될 때 키워드 결과로 몰래 대체하기.
    • Discord로 명령 받기, 원격·다중 사용자 접속, 모바일 전용 KnowledgeOS.
    원본: USER_FEATURE_SPEC.md · 명세 운용

    명세 운용#

    명세는 단계별 산출물이 아니라 코드와 함께 움직이는 현재 계약입니다.

    • 이력·증거·설치 상태를 담지 않습니다. 이력은 Git에, 진행과 검증은 PROJECT_STATE.md에 둡니다.
    • 동작을 바꾸는 변경은 같은 변경 안에서 명세도 고칩니다. 낡은 문장은 표시하지 않고 지웁니다.
    • 기능 명세의 인수 시나리오가 곧 실행 가능한 테스트입니다.
    • 기능 하나를 끝까지 얇게 만들어 써 보고, 배운 것으로 명세를 고칩니다.
    • 정하지 않은 것은 Blueprint의 열린 질문에 두고, 필요한 시점에 결정합니다.
    • 기존 구현 중 이 방향과 맞는 부분은 참고 자료 목록에 있습니다. 명세가 우선합니다.

    위키의 구성: 생성되는 것과 직접 쓰는 것#

    종류 예 원본 고치는 방법
    원문 블록기능 페이지의 영문 명세, Blueprint 절, 사용자 기능 명세 절docs/CAPABILITIES.md 등 원본 문서원본을 고치고 위키 재생성
    인수 표인수 ID, 예시, 구현 위치, 테스트 노드docs/CAPABILITIES.md, docs/CAPABILITY_TRACE.md원본을 고치고 재생성
    상태 표목표·결정·인수·증거·막힘·인계PROJECT_STATE.mdPROJECT_STATE를 고치고 재생성
    그림(SVG)시스템 지도, 기능 지도, 작업 흐름, 정책 표, 현황 요약생성기가 원본에서 만듦원본을 고치고 재생성

    원고에 쓰는 문법#

    해설 문장은 Markdown의 일부(제목, 목록, 표, 코드 블록, 인용, 굵게·기울임·코드, 링크)와 아래 규칙만 씁니다.

    [[slug]]              페이지 링크 (예: usage, c4)
[[slug|표시할 글]]     표시 글을 바꾼 링크 (표 안에서는 | 때문에 쓰지 않음)
[[ORG-1]]             인수 ID가 있는 기능 페이지의 그 위치로 링크
> [!note] 제목        설명 상자 (note, tip, warning, status)

    원본에서 가져오는 블록은 한 줄에 하나씩 쓰는 지시문입니다. 원문 포함(include), 인수 표(acceptance), 상태 표(state), 그림(svg), 원본 목록(sources)이 있고, 존재하지 않는 대상을 가리키면 생성이 실패합니다.

    개발 세션마다 위키를 갱신하는 방법#

    위키는 코드·명세와 함께 움직입니다. 모든 개발 세션은 바뀐 범위에 맞춰 원본 문서와 위키 설명을 함께 갱신하고, 끝내기 전에 아래를 순서대로 합니다. 명세·추적표·PROJECT_STATE.md를 바꾼 세션에만 한정하지 않습니다. 이 절차는 저장소의 AGENTS.md와 README.md, Blueprint §0에도 같은 내용으로 적혀 있습니다.

    1. 원본을 고칩니다.
      • 동작·인수 기준이 바뀌었다면 docs/CAPABILITIES.md를 같은 변경 안에서 고칩니다. 필요하면 USER_FEATURE_SPEC.md(의도), Blueprint(시스템 제약)도 함께 고칩니다. 낡은 문장은 지웁니다.
      • 인수 시나리오를 더하거나 바꿨다면 테스트와 docs/CAPABILITY_TRACE.md의 행도 맞춥니다.
      • 진행·검증 결과는 PROJECT_STATE.md에만 기록합니다. 증거에는 종류(class)와 결과를 적고, 돌리지 않은 것은 정확히 "돌리지 않음"으로 둡니다.
    2. 해설을 고칩니다. 쓰는 법·용어·설명이 달라졌다면 docs/wiki/_source/의 해당 페이지를 고칩니다. 새 용어는 용어에 더합니다. 설명 문장은 여기에서만 고칩니다.
    3. make wiki 로 위키를 다시 생성합니다.
    4. make wiki-check 로 검사합니다. 이 검사는 아래 중 하나라도 해당하면 실패합니다.
      • 명세의 C1~C11이나 인수 ID가 생성 결과에 빠졌다.
      • PROJECT_STATE의 목표·인수·막힘·인계 기록이 빠졌다.
      • 내부 링크나 앵커가 풀리지 않거나, 원고의 위키 링크가 없는 페이지·ID를 가리킨다.
      • 어떤 출력이든 원격 자원(src=, <link href>, CSS url()·@import의 스킴, fetch(·XHR의 http 호출)을 불러온다.
      • 다시 생성하면 바이트가 달라진다. 즉 생성 파일이 낡았다.
    5. 바뀐 페이지를 브라우저로 확인합니다. docs/wiki/index.html을 열어 바뀐 페이지, 표·그림, 링크, 사이드바, 검색 상자를 눈으로 봅니다. 자동 검사는 링크가 풀리는지를 보지만 읽기 편한지, 내용이 서로 맞는지는 알려 주지 않습니다.
    6. 발견한 어긋남을 같은 세션에서 고칩니다. 5단계에서 문서끼리 맞지 않는 곳이 보이면(아래 "명세 점검" 참고) 위키에 경고만 남기지 말고 원본을 고치고 3~5단계를 다시 합니다.
    7. 생성 결과를 원본과 같은 변경에 담습니다. 생성된 HTML과 assets는 저장소에 포함됩니다.

    상태·추적표 검사(make state-check, make trace-check)는 위키와 별개로 각각 돌립니다.

    명세 점검: 위키를 갱신하며 함께 보는 것#

    위키를 갱신하는 일은 명세를 한 번 훑어 읽는 기회입니다. 아래를 살펴보고, 어긋나면 우선순위가 낮은 쪽을 고칩니다.

    살펴볼 것 예 고치는 쪽
    같은 사실을 다르게 적은 곳기능 명세와 Blueprint의 기본값·이름이 다름우선순위가 낮은 문서(Blueprint·사용자 기능 명세)
    구현이 이미 답한 열린 질문Blueprint §9에 남아 있는데 기능 명세와 증거에 값이 있음Blueprint §9에서 그 질문을 지움
    증거가 명세에 새어 든 곳명세에 설치 상태·관찰 버전이 적혀 있음명세에서 지우고 PROJECT_STATE.md에 기록
    상태가 현실과 다른 곳인수 기록이 오래됨, 막힘이 풀렸는데 남아 있음PROJECT_STATE.md

    우선순위: 동작·인수 기준에 대해서는 docs/CAPABILITIES.md가 가장 높고, 사용자 기능 명세와 Blueprint가 그것을 보충합니다. 최상위 문서의 내용 자체가 틀렸다고 판단되면 그것은 사용자가 지정한 문서를 바꾸는 일이므로 [해석] 임의로 고치지 말고 세션 보고에 남깁니다.

    무엇이 바뀌면 어디를 고치나#

    무엇이 바뀌었나 고칠 곳 위키에 반영되는 곳
    기능의 동작·인수 기준docs/CAPABILITIES.md(+ 필요 시 USER·Blueprint), 테스트, 추적표기능 페이지의 원문·인수 표
    검증 결과·막힘·인계PROJECT_STATE.md현재 상태, 로드맵, 각 기능의 "현재 상태"
    쓰는 방법README.md 또는 _source/usage.md사용 가이드
    새 용어_source/glossary.md용어
    구조 설명Blueprint 또는 _source/architecture.md구조
    구현이 답한 열린 질문Blueprint §9에서 삭제로드맵의 열린 질문

    주의

    위키를 갱신한다고 Obsidian GUI·플러그인·Hermes·State·실행 중인 Owner를 건드리지 않습니다. 위키는 원본 문서를 읽어 정적 HTML을 만들 뿐입니다. 그런 작업은 별도의 명시적 승인이 있어야 합니다.
