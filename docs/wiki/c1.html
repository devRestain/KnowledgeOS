    C1 정리 (Organize)

    한눈에 보기#

    정리는 아직 자리가 없는 노트를 지식 구조 안에 놓아 주는 기능입니다. Curation Team이 노트의 종류·제목·태그·링크·위치를 읽고 제안을 만들며, 원본 노트는 건드리지 않습니다. 제안을 적용할지는 사용자가 검토 단계에서 결정합니다.

    항목 내용
    트리거Thin Client "정리 요청"(현재 노트·선택한 파일·폴더), 예약 작업 curate(C7), Gateway 수신 포착(C10)
    담당Curation Team: CurationManager(모델), scout(정적), classifier(모델), linker(모델), 독립 평가자 EvalOfficer
    결과물01_AI_Review/Proposals/의 제안 노트(대상 노트 하나당 하나)
    사용자 결정 여부예. 제안은 사용자가 적용해야만 반영되고, 정리가 스스로 원본 노트를 바꾸지 않습니다

    한 번의 요청(Work)이 다루는 노트는 최대 10개입니다. 용어(Work, Proposal, Handoff 등)는 용어에 정리되어 있습니다.

    왜 이 명세가 필요한가#

    USER_FEATURE_SPEC.md의 '지키는 약속' 가운데 세 가지를 직접 보호합니다.

    • 약속 1 · Vault는 사용자의 것입니다. 정리 결과는 파일을 직접 고치지 않고 제안 노트로만 나옵니다. 없다면 판단이 필요한 이동·이름 변경·태그 변경이 사용자 모르게 일어날 수 있습니다.
    • 약속 4 · 자동으로 바꾸는 것은 작고 기계적인 것뿐입니다. 종류·제목·링크·위치는 판단이 필요한 변경이므로 자동 적용 대상이 아닙니다. 매일 자동으로 도는 curate도 제안까지만 만듭니다.
    • 약속 7 · 근거를 밝힙니다. 모든 분류와 링크는 이번 Work에서 실제로 읽은 노트 내용에 기대야 하고, 독립 평가자가 그 근거를 따로 확인합니다.

    개인정보 경계(운용 원칙의 ai_policy 설명과 용어 참고)도 이 명세에 들어 있습니다. 예약 실행과 Gateway 실행은 remote_ok 노트만 모델에 보여 줍니다.

    어떻게 쓰는가#

    Obsidian Thin Client (사이드바·명령)#

    1. 정리할 노트를 엽니다. 사이드바는 마지막으로 활성화된 Markdown 노트를 대상으로 표시합니다.
    2. 사이드바에서 정리를 선택한 뒤 아래 기능 창의 정리 요청을 누릅니다. 기능 선택만으로는 요청하지 않습니다. 명령 팔레트·파일 메뉴의 정리 요청으로도 실행할 수 있으며, 선택한 여러 파일·폴더는 해당 명령에서 대상으로 고릅니다(C11 명령표).
    3. 요청에는 노트 경로와 마지막으로 본 내용의 해시만 실리고 본문은 실리지 않습니다(SUR-1).
    4. 끝나면 사이드바에는 완료 상태와 결과 링크가 표시되고, 명령 팔레트·문맥 메뉴에서는 요청당 하나의 완료 알림이 뜹니다. 생성된 제안은 01_AI_Review/Proposals/에서 검토합니다.
    5. 제안 노트를 열어 체크리스트를 보고, 원하지 않는 항목의 체크를 해제한 뒤 적용 또는 거절을 누릅니다(C6). 적용은 체크한 변경만 반영하고, 거절은 제안 파일을 지웁니다.

    도움말

    사이드바에는 Owner가 켜져 있어야 요청이 접수됩니다. 탭을 열기만 해서는 Owner가 켜지거나 꺼지지 않습니다. 자세한 조작은 사용 가이드를 보세요.

    자동 경로#

    • 예약 작업 curate: 매일 06:00(Asia/Seoul)에 새 포착과 종류 없는 remote_ok 노트를 대상으로 정리를 요청하며, 한 번에 최대 10개입니다(JOB-2). Owner가 켜져 있는 동안에만 돌고, 꺼져 있었다면 시작 후 지연(기본 3분)이 지나 놓친 작업을 한 번만 실행합니다(C7).
    • Gateway 수신 포착: 다른 Operation이 보낸 정보는 00_Inbox/의 capture 노트로 들어온 뒤 같은 정리를 거칩니다(C10, GW-1).
    • CLI: knowledgeos job run curate로 같은 작업을 직접 실행할 수 있고, 결과는 실행 영수증까지 따라가 보고됩니다(README).

    작업 예: 인박스의 종류 없는 노트#

    1. 00_Inbox/에 frontmatter 없이 쓴 메모가 있습니다.
    2. 사용자가 사이드바에서 정리를 선택하고 아래 기능 창의 정리 요청을 누릅니다.
    3. scout가 대상 노트, 관련 후보 노트, 기존 태그 목록을 모으고, classifier가 종류·상태·제목·태그·폴더를, linker가 기존 노트와의 링크를 정합니다.
    4. 평가를 통과하면 제안 노트 하나가 생기고, 원래 메모는 그대로입니다(ORG-1).
    5. 사용자가 제안에서 "폴더 이동"만 체크 해제하고 적용하면, 나머지 변경은 반영되고 파일은 제자리에 남습니다(ORG-4).

    제안의 구성#

    제안의 변경 항목은 체크리스트로 나옵니다(CAPABILITIES C1).

    • type과 그 종류에서 유효한 status는 하나의 묶음 항목입니다.
    • title.
    • tags: 기존 태그 목록에서 고르며, 새 태그는 새 것이라고 표시합니다.
    • 링크(related, projects, sources, 또는 타입이 있는 관계).
    • 관례 폴더로의 이동.
    • 포착(capture)인 경우: 목적지 종류의 유효한 상태와 함께 타입이 있는 노트로 바꾸거나(예: idea와 seed), capture로 남기고 status: processed로 표시합니다. 기존 노트에 붙이는 경우에는 같은 포착에 related 링크만 더하고 capture/processed로 남기며, 다른 노트의 본문은 고치지 않습니다. 어느 경우에도 제안 하나는 대상 하나만 바꿉니다.

    동작 흐름#

    정리는 공통 Work 흐름의 Team 경로를 따릅니다. 아래 그림은 요청이 Director에게 접수된 뒤 Manager가 그래프를 구성하고, 팀원이 일하고, EvalOfficer가 평가하는 과정을 보여 줍니다. 정리에서는 Manager가 CurationManager, 팀원이 scout·classifier·linker이며 마지막 쓰기는 제안 노트 하나입니다.

    • CurationManager는 Work에 필요한 팀원만 고릅니다. 예를 들어 관련 노트가 없을 법한 포착에는 linker를 건너뛸 수 있습니다.
    • 평가자는 Manager의 지시를 받지 않습니다. Manager의 그래프 제안에 EvalOfficer에게 주는 지시가 들어 있으면 Owner는 제안을 거부하고 어떤 구간도 시작하지 않습니다(ORG-5).
    • 평가에서 분류 하나가 근거 부족으로 판정되면, CurationManager가 해당 대상에 classifier만 다시 돌리는 후속 구간 하나를 예산 안에서 구성합니다(ORG-6).
    • 제안은 사용자가 결정할 때까지 같은 대상에 대해 하나만 열려 있습니다. 다시 요청하면 Owner가 쓴 바이트 그대로인 제안만 제자리 갱신되고, 사용자가 고친 제안은 보존됩니다(아래 "거부와 보존" 참고).

    C1 Organize#

    The Curation Team places notes into the knowledge structure: classification, naming, tags, links and location.

    • Triggers: Thin Client "정리 요청" on the current note, a selection of files or a folder; the scheduled curate job (C7); a Gateway intake capture (C10).
    • Input: up to 10 target notes per Work. Scheduled and Gateway-triggered Work only gives models notes whose effective policy is remote_ok.
    • Team pool:
      • scout (static): collects the target notes, candidate related notes and the tag vocabulary.
      • classifier (model): decides type, status, title, tags and conventional folder per note.
      • linker (model): decides links and typed relations to existing notes, and whether a capture should attach to an existing note.
    • Manager: CurationManager picks the teammates the Work needs. For example, a capture with no plausible related notes may skip linker.
    • Output: the Owner renders one proposal per target from the handoffs. Each change is a checklist item:
      • type and its valid status together as one atomic checklist item.
      • title.
      • tags, chosen from the existing vocabulary unless marked new.
      • Links (related, projects, sources, or a typed relation).
      • A move to the conventional folder.
      • For a capture, either conversion to a typed note with that destination type's valid status (for example, idea with seed), or retention as capture with status: processed. Attaching to an existing note adds a related link on the same capture and leaves it capture/processed; it never edits the other note's body. Every proposal still changes only its single target.
    • Criteria:
      • Static: every enum value is valid; every link target was read in this Work; new tags are marked; there is at most one open proposal per target.
      • Semantic, judged by the model EvalOfficer: each classification and link is supported by the cited note content.
    • Refuses: deny notes; notes with conflict markers; ambiguous-ID targets. A target with an open or stale proposal never gains a second one. Regeneration may replace only the exact bytes still recorded as Owner-written; user-edited or State-unrecorded proposals are preserved (Blueprint §5.6).

    Acceptance:

    • ORG-1 Given an untyped note in 00_Inbox/, when organize runs, then one proposal lists a type, a title and at least one existing related note, and the note itself is unchanged.
    • ORG-2 Given the linker cites a note it never read in this Work, then that handoff fails validation, the linker gets one corrective turn, and a second failure leaves the link criterion unmet.
    • ORG-3 Given a scheduled run and a note with ai_policy: ask, then no model role receives that note's content.
    • ORG-4 Given a proposal where the user unchecked the move, when it is applied, then all other checked changes apply and the file stays in place.
    • ORG-5 Given the CurationManager's Graph proposal contains an instruction for the EvalOfficer, then the Owner rejects the proposal and no segment starts.
    • ORG-6 Given the EvalOfficer judges one classification unsupported, then the CurationManager composes one successor segment with only classifier for that target, within budget.

    거부와 보존 (명세 요약)#

    • 거부: deny 노트, 충돌 표시가 있는 노트, ID가 겹치는 노트는 정리 대상이 되지 않습니다(C5의 DOC-2도 같은 규칙을 말합니다). 이미 열린 제안이나 오래된(stale) 제안이 있는 대상에는 두 번째 제안이 생기지 않습니다.
    • 보존: 다시 만들 때 교체되는 것은 State에 기록된 Owner가 쓴 바이트와 정확히 같은 제안뿐입니다. 사용자가 고친 제안과 State에 기록되지 않은 제안은 그대로 남습니다(Blueprint §5.6).
    • 링크 검증: linker가 이번 Work에서 읽지 않은 노트를 인용하면 그 handoff는 검증에 실패하고, 교정 기회는 한 번뿐입니다. 두 번째에도 실패하면 링크 기준은 충족되지 않은 것으로 남습니다(ORG-2).
    • 개인정보: 예약 실행에서 ai_policy: ask 노트의 내용은 어떤 모델 역할에게도 전달되지 않습니다(ORG-3).

    현재 상태와 남은 일#

    PROJECT_STATE.md와 CAPABILITY_TRACE.md가 말하는 사실만 적습니다.

    • 구현·추적: C1의 인수 ID ORG-1~ORG-6은 모두 추적표에 구현 위치와 pytest 노드가 연결되어 있습니다. 현재 추적 기록은 전체 61개 인수 예시·61행·171개 pytest 노드의 연결을 확인합니다(E_SIDEBAR_INLINE_TRACE). 전체 테스트 통과는 248개 시점의 E_TRACED_TESTS 기록이며, 이후 인라인 사이드바의 집중 검사 5개는 E_SIDEBAR_INLINE_TESTS에 따로 있습니다.
    • 실환경 근거:
      • 실제 Vault에서 Obsidian으로 요청한 정리·강화·자유 요청이 완료되어, 열린 제안 하나와 보고서 하나가 만들어졌습니다. Hermes 세션은 Director·Manager·평가에 gpt-6.1-sol, 팀원에 gpt-6.1-terra를 썼습니다(E_REAL_ROLE_SMOKE).
      • 사용자가 그 스모크 제안을 체크 항목 7개로 적용해 포착이 40_Knowledge/Questions로 옮겨지고 제안이 삭제된 것이 기록되어 있습니다(E_USER_PROPOSAL_APPLY).
    • 아직 확인되지 않은 것: PROJECT_STATE.md의 남은 인계는 자연 발생한 매시간 규격화·임베딩 실행 관찰과 related_min_score 조정입니다. 매일 06:00 curate의 자연 실행을 관찰했다는 기록은 PROJECT_STATE.md에 없습니다. 예약 시각 실행의 실환경 확인은 임시 index.embed 작업 하나로 이루어졌습니다(E_REAL_SCHEDULER_SLOT).
    • 열린 질문(Blueprint §9): 예약 정리를 쓰기 시작한 뒤에도 기본 ai_policy를 ask로 두는 것이 맞는지, 그리고 C7의 기본 작업 주기가 실제 사용과 맞는지는 아직 정해지지 않았습니다.

    로드맵 전체는 로드맵, 검증 근거 전체는 현재 상태에서 볼 수 있습니다.

    관련 기능#

    • C2 규격화: 정리의 앞 단계입니다. 결정적 규칙으로 빠진 frontmatter를 채우고, 판단이 필요한 변경만 정리가 제안으로 맡습니다.
    • C6 검토: 정리가 만든 제안을 적용·거절·되돌리는 곳이며 ORG-4의 적용 동작을 담당합니다.
    • C7 예약 작업: curate가 매일 정리를 요청합니다(최대 10개, 모델 경로가 없으면 눈에 띄게 실패하고 자동 재시도하지 않습니다, JOB-3).
    • C10 Gateway: 다른 Operation이 보낸 정보가 포착 노트로 들어와 정리 대상이 됩니다.
    • C5 문서 관리: ID 중복·충돌 표시 같은 주의 항목이 정리 거부 조건과 맞닿아 있습니다.
    • C9 학습: 거절·부분 적용된 정리 제안이 classifier·linker의 피드백이 되고 근거가 맞으면 Experience 후보가 됩니다(LRN-1).
    • C11 호출 표면: "정리 요청" 명령과 사이드바 버튼의 정의가 있습니다.
