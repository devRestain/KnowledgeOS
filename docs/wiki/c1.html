    C1 정리 (Organize)

    정리는 아직 자리가 없는 노트를 지식 구조 안에 배치하기 위해 Curation Team이 종류·상태·제목·태그·폴더 위치·링크를 판단하고, 01_AI_Review/Proposals/에 검토용 제안 노트를 만들어 주는 기능입니다. 원본 노트는 한 바이트도 바꾸지 않으며, 제안을 받아들일지 버릴지는 C6에서 사용자가 결정합니다. 공통 실행 구조·역할별 모델 경로·보안 경계는 구조를, 용어 풀이는 용어를 참고하세요.

    언제, 어떤 입력으로 시작하는가#

    정리는 네 경로로 들어오며, 요청 성격에 따라 접수 방식이 다릅니다.

    • Obsidian Thin Client("정리 요청"): 현재 열린 노트, 선택한 여러 파일, 또는 폴더 전체를 대상으로 보냅니다. 사이드바에서 정리 탭을 고르는 것만으로는 실행되지 않고 정리 요청을 눌러야 접수됩니다. 클라이언트는 노트 본문을 보내지 않고 파일 경로와 마지막으로 본 내용의 해시만 보냅니다(SUR-1). 정형 명령(organize)이므로 모델 Director를 부르지 않고 코드가 바로 접수합니다.
    • 예약 작업 curate와 CLI: 매일 06:00(서울 시간)에 예약 작업 curate가 자동 정리(organize.auto)를 요청하며(JOB-2), 터미널에서 knowledgeos job run curate로 직접 실행할 수도 있습니다. 이 경로는 아직 종류(type)가 비어 있거나 처리되지 않은 포착(capture, 상태가 없거나 unprocessed) 중 자동화가 허용된(approve) 노트이면서 마지막 정리 이후 내용이 바뀐 것을 먼저 발견된 순서대로 최대 10개 골라 냅니다. 역시 모델 Director 없이 코드가 접수하며, 10개를 넘어 남은 노트는 다음 실행으로 넘깁니다.
    • Gateway 수신 포착(C10): 다른 Operation이 보낸 정보는 00_Inbox/에 type: capture, status: unprocessed 노트로 들어옵니다(GW-1). 수신 직후 정리가 즉시 돌지는 않고, 다음 curate 실행이나 사용자의 "정리 요청"이 일반 포착과 똑같이 이어받습니다.
    • 자유 요청(free_text): "인박스 메모 정리해 줘"처럼 문장으로 보내면, System One이 설정된 경우 먼저 관련 없는 요청을 거른 뒤 kos-director 모델이 정형 organize 요청 초안으로 바꿔 같은 접수 검사를 통과시킵니다.

    한 번의 작업(Work)이 다루는 대상은 최대 10개입니다. 개별 파일을 직접 지정했을 때 문제가 있으면 요청 전체를 거절하지만, 폴더를 지정하면 문제 있는 노트는 건너뛰고 정상 노트만 진행합니다(단, 자동화를 거부한 deny 노트는 건너뜀 사유 목록에도 드러내지 않습니다).

    • 정리 대상에서 빠지거나 거절되는 노트: 자동화가 허용되지 않은 노트(ai_policy: deny 또는 퇴역 값 ask·remote_ok·local_only 등, ORG-3), 데일리 노트(type: daily, 사유 daily note (never a proposal target), ORG-8), 시스템·검토·탐색·보고서·제안 노트, 본문이 비어 있는 노트, YAML 오류·충돌 표시·중복 ID가 있는 노트(DOC-2), 요청 직전 파일 내용이 바뀐 노트.
    • 유효한 대상이 하나도 없으면 Work를 만들지 않고 바로 끝냅니다. 대상이 정해지면 Owner가 그 시점의 파일 바이트를 스냅숏으로 고정하므로, 작업 도중 사용자가 원본을 고쳐도 팀원들은 일관된 시점의 내용을 읽습니다.

    Curation Team 구성과 역할별 실제 작업#

    모델별 실제 경로와 추론 설정(config/roles.json)은 구조에서 확인하세요.

    역할과 Hermes Profile 맡는 일 넘기는 결과
    CurationManager (kos-curation-manager)노트 본문을 읽지 않고 팀원 실행 순서와 후속 구간을 편성, 완료 후 TeamReview 작성구간 Graph 제안, 완료 후 팀원 평점과 조언 제안(최대 3개)
    scout (Hermes profile 없음 · 코드)대상 노트와 관련 후보, 기존 태그 목록을 정적으로 수집미리 읽은 대상·후보 노트(후보 기본 최대 5개)의 근거 핸들과 태그 목록
    classifier (kos-classifier)대상 내용을 읽고 종류·상태·제목·태그·관례 폴더를 결정대상별 분류 항목과 뒷받침 근거 핸들
    linker (kos-linker)대상과 후보 노트를 읽고 기존 노트와의 연결과 포착 부착 여부를 결정대상별 링크 목록(6종 관계)과 포착 부착 대상(attach_to)
    EvalOfficer (kos-eval)Manager 설명이나 팀원 자기평가 없이 정적 검사 결과와 인용 발췌만 보고 독립 평가분류·링크가 읽은 내용으로 뒷받침되는지 판정

    예를 들어 00_Inbox/에 frontmatter 없이 "도구가 사고 방식을 바꾼다"라는 메모를 적어 두고 정리를 요청했다고 합시다. 내부에서는 각 역할이 다음 순서로 재료를 모으고 판단을 넘깁니다.

    1. scout이 먼저 모으는 재료 (코드 실행)#

    scout은 모델 없이 Owner 코드로 돕니다. 대상 노트의 스냅숏 본문을 문단·제목 단위의 짧은 조각(최대 40줄, frontmatter 제외)으로 나눠 근거 핸들(e1, e2 같은 짧은 식별자)을 붙이고 읽음 상태로 등록합니다. 이어서 두 경로로 관련 후보를 찾습니다.

    • 기존 링크·역링크·공유 태그에 더해, 의미 검색이 준비돼 있으면 System One 이웃 거름(C3)을 통과한 의미 이웃을 가져옵니다.
    • 대상의 제목과 본문 앞부분(600자)에서 뽑은 키워드로 공개 가능한 노트를 찾습니다.

    오류나 충돌이 없는 approve 후보 가운데 기본 최대 5개(설정 범위 0~10개)를 미리 읽어 근거 핸들과 짧은 발췌를 남기고, Vault 전체에서 역할에 공개된 기존 태그 목록도 함께 묶어 다음 팀원에게 넘깁니다. scout은 System One에 분류 힌트를 미리 묻지 않습니다.

    2. classifier가 결정하는 분류#

    classifier는 대상 노트와 scout이 모은 기존 태그 목록·관례 폴더 표를 받아 내용을 읽은 뒤, 각 대상의 종류(6종: capture·idea·knowledge·question·project·source), 해당 종류의 유효한 상태(또는 archived), 노트 언어에 맞춘 짧은 제목, 태그, 관례 폴더(40_Knowledge/Ideas, 90_Archive 등)를 정합니다.

    • 태그는 기존 태그 목록에서 우선 고르고, 꼭 필요한 새 태그만 새 태그라고 표시합니다.
    • 판단의 근거가 된 문단 핸들을 함께 넘기며, 이 작업에서 실제로 읽지 않은 핸들은 인용할 수 없습니다.

    3. linker가 결정하는 연결과 포착 부착#

    linker는 대상 노트와 scout의 후보를 읽고, 더 찾아봐야 한다면 역할 전용 검색(search·related)으로 후보를 넓힙니다. 검색 결과는 바로 인용할 수 없고 실제로 read로 열어 본 노트만 연결할 수 있습니다.

    • 연결 관계는 일반 연관(related), 소속 프로젝트(projects), 근거 출처(sources), 방향이 있는 세 관계(supports·contradicts·derived_from) 가운데 고릅니다. 방향이 있는 관계는 본문에 근거가 분명할 때만 쓰고, 모호하면 related나 미연결을 택합니다.
    • 원본이 포착(capture)이고 독립 노트로 승격하기보다 기존 노트에 이어 붙여야 할 내용이면 부착 대상(attach_to)으로 그 노트를 지정합니다.
    • 이번 작업에서 읽지 않은 노트를 링크로 적으면 제출이 거절되고, 교정 턴에서도 다시 실패하면 링크 기준이 미충족으로 남습니다(ORG-2).

    4. 조언 전용 system_one 도구#

    classifier와 linker는 빠른 모델(gpt-6-luna)에게 짧은 닫힌 질문을 묻는 system_one 도구를 쓸 수 있습니다.

    • 분류 참고 답(classifier): 대상 핸들만 넘기면 종류와(대상에 이미 알려진 종류가 있을 때) 상태에 대해 확신도 기본 기준(0.7)을 넘긴 참고 답과 상위 확률을 받습니다(ORG-7). 결과는 대상별로 작업 기록에 캐시되므로 같은 대상에 다시 물어도 새 요청을 보내지 않습니다.
    • 닫힌 질문(linker·classifier): 이미 읽은 노트 하나에 대해 선택지 중 하나를 고르게 하거나 예/아니오 확률을 물을 수 있습니다. 두 방식 합쳐 단계당 최대 10번까지 호출할 수 있습니다.
    • 보내기 직전 대상 파일의 현재 정책이 여전히 approve인지 다시 확인하며, 답은 참고용일 뿐 Owner가 노트나 제안에 직접 쓰지 않습니다. 예를 들어 System One이 idea(0.9)를 추천해도 classifier가 내용을 보고 question으로 결정하면 제안에는 question이 적힙니다(ORG-7). System One이 꺼져 있거나 실패해도 작업은 그대로 진행됩니다.
    • 현재 실제 Hermes 연결에서 선택지 배열(choices)을 넘길 때 거절되는 제한은 현재 상태를 참고하세요.

    동적 Graph 구성, 독립 평가와 후속 구간#

    정리는 고정된 순서로만 돌지 않습니다. CurationManager는 노트 본문을 보지 않고 남은 예산(기본 2구간, 생산자 호출 6회)과 이전 평가 결과만 보고 이번 구간에 필요한 팀원만 동적으로 고릅니다. C4와 달리 정해진 마지막 생산자가 없어 상황에 따라 다음과 같이 구성할 수 있습니다.

    • 분류와 연결을 모두 보는 1구간 예시: scout → classifier → linker (생산자 3회 소모, 후속용 3회 남음)
    • 연결할 노트가 없는 단독 포착 1구간 예시: scout → classifier (linker를 생략하며, 생략된 경우 링크를 제안하지 않아도 기준을 통과)
    • 분류 근거만 부족할 때 2구간 예시: 1구간 평가에서 특정 노트의 분류 근거만 부족하다고 판정되면 classifier만 다시 수행하는 2구간을 짭니다. 이때 앞 구간에서 통과한 다른 노트의 분류와 linker 결과는 그대로 보존되고 문제가 된 대상의 분류만 교체됩니다(ORG-6).
    • 링크 근거만 부족할 때 2구간 예시: 링크 근거만 미충족이면 linker만 다시 수행하는 2구간을 짭니다.

    후속 구간에는 미충족된 기준을 실제로 다룰 수 있는 팀원만 넣을 수 있으며, 이미 열린 제안이 중복되어 막힌 문제는 팀원 재실행으로 해결할 수 없습니다. Manager가 EvalOfficer에게 지시를 주거나 평가 위치를 바꾸려 하면 교정 턴 없이 즉시 거절되어 구간이 시작되지 않고 작업이 실패합니다(ORG-5).

    실행 접점에서 각 구간은 Temporal WorkWorkflow가 사전 등록된 LangGraph 구간을 따라 생산자 단계를 차례로 실행한 뒤, 대상별 결과를 합쳐 정적 검사(유효한 종류·상태·폴더, 읽은 링크, 새 태그 표시, 대상당 열린 제안 1개)와 kos-eval의 독립 근거 평가(분류·링크의 내용 뒷받침)를 거쳐 Owner가 최종 판정을 내립니다. Temporal·LangGraph·Hermes 세션·교정 턴의 공통 규칙은 구조를 보세요.

    최종 제안 노트 생성, 보존과 TeamReview#

    모든 평가 기준을 통과하면 Owner가 대상 노트마다 01_AI_Review/Proposals/<제목> — organize.md 제안 노트를 만들어 씁니다.

    • 체크리스트 구성: 종류(type)와 그 종류의 유효한 상태(status)는 항상 하나의 묶음 항목으로 나오고, 제목·태그(새 태그는 새 항목으로 표시)·관례 폴더 이동·링크가 개별 체크 항목으로 붙습니다. 포착 노트가 capture로 남는 경우(보관 제외)에는 status: processed를 제안하고, 기존 노트에 붙이는 경우(attach_to)에도 그 포착에 related 링크만 더할 뿐 다른 노트의 본문은 고치지 않습니다. 바꿀 항목이 하나도 없으면 제안 파일을 만들지 않고 마칩니다.
    • 원본 불변과 선택 적용: 정리가 끝나도 원본 메모는 한 글자도 바뀌지 않습니다(ORG-1). 사용자가 제안 노트에서 원치 않는 항목(예: 폴더 이동)의 체크를 해제하고 적용하면 체크된 변경만 반영되고 파일은 제자리에 남으며 제안 파일은 지워집니다(ORG-4, C6).
    • 중복 방지와 사용자 편집 보존: 작업 도중 대상 노트가 수정됐거나 deny가 됐다면 제안을 쓰지 않습니다. 이미 열린 제안이 있을 때 제자리 갱신할 수 있는 것은 Owner가 마지막으로 쓴 바이트 그대로 남아 있는 제안뿐이며, 사용자가 조금이라도 손댄 제안이나 State 기록이 없는 제안은 덮어쓰지 않고 보존합니다. 새로 계산한 결과가 기존 제안과 완전히 같으면 파일을 다시 쓰지 않습니다. 오래된(stale, 대상 변경으로 적용 불가 상태) 제안은 예약 실행에서는 건드리지 않고, 사용자가 직접 다시 정리 요청을 했으면서 미편집 상태일 때만 open으로 갱신합니다.
    • 완료 후 TeamReview: 제안 작성까지 끝나면 CurationManager가 실제 산출물을 낸 팀원(scout 포함)마다 1~5점 평점과 짧은 메모, 최대 3개의 개선 제안을 남깁니다. 이 제안은 조언 기록으로만 남으며 역할·카탈로그·평가를 자동으로 바꾸지 않습니다(C9).
