    로드맵: 막힘 · 시작 전 · 후속 과제

    이 페이지는 무엇이 막혀 있고, 무엇이 아직 시작 전이며, 다음에 무엇을 할 것인가를 한곳에 모읍니다. 이미 되어 있는 것과 그 근거는 현재 상태에 있습니다.

    지금 막힌 것#

    PROJECT_STATE.md의 막힘(blocker) 기록입니다. state가 resolved이면 해결된 기록이며, 이력으로 남겨 둔 것입니다. 열린 막힘이 없다면 모든 행이 resolved입니다.

    ID 상태 조치 출처

    B_C9_TEAMREVIEW_CATEGORYresolvedKeep ordinary TeamReview proposals local and extract Candidates only from genuinely eligible events under existing Core categoriesuser_request
    B_DISCORD_TOKENresolvedInvite the KnowledgeOS bot to the server and grant View Channel and Send Messages on the configured channeluser_request

    과거의 미확인 기록도 남아 있습니다. 사이드바 1.1.0의 macOS 기본 팝업 메뉴는 접근성 자동화가 거부되고 렌더러 DOM에도 나타나지 않아 확인하지 못했습니다(E_SIDEBAR_NATIVE_MENUS, blocked). 이 이력은 지우지 않습니다. 현재 1.2.0은 팝업 대신 인라인 입력·검색 결과·미리보기 결정을 사용하며(D_SIDEBAR_INLINE), 실제 Obsidian에서 인라인 기능과 의미 검색 결과 7개, 밝은/어두운 테마와 242px 레이아웃을 확인했습니다(E_SIDEBAR_INLINE_GUI). 따라서 과거 팝업의 검증을 현재 UI의 후속 과제로 두지 않습니다.

    PROJECT_STATE.md의 인계(handoff) 기록입니다.

    # 상태 다음 작업
    1incompleteReview the open organize proposal for the KOS generation effect smoke note observe the first natural hourly standardize run with System One and tune related_min_score related_min_probability and min_confidence against real notes

    풀어 쓰면 세 가지입니다.

    1. 열린 정리 제안 검토: 실제 Obsidian 사이드바의 정리가 만든 01_AI_Review/Proposals/KOS 점검 - 생성 효과 — organize.md가 사용자의 적용·거절을 기다립니다(E_SYSTEM_ONE_CLIENT_GUI). 결정은 사용자가 C6에서 합니다.
    2. 첫 자연 실행 관찰: 지금까지는 임시로 만든 작업이 한 번 도는 것만 확인되었습니다(E_REAL_SCHEDULER_SLOT). Owner가 켜져 있는 동안 선언된 standardize(매시 정각)가 System One과 함께 제 시각에 저절로 도는지 지켜봅니다. 설명은 C7, 방법은 사용 가이드를 보세요.
    3. 임계값 조정: 관련 노트에 의미 이웃을 올리는 related_min_score(기본 0.5), System One이 이웃을 거르는 related_min_probability(기본 0.5), 선택 질문의 min_confidence(기본 0.7)는 모두 실제 노트로 보고 알맞게 고칠 시작값입니다(C3, C2).

    9. Open questions and follow-ups#

    Open questions:

    • Semantic ranking. Whether the default related_min_score and neighbor count in capability C3 match real notes.
    • Default ai_policy. Whether ask remains the right default once scheduled curation is in use.
    • Schedules. Whether the default job intervals in capability C7 match actual use.
    • Plugin choices. Whether core Bases suffices for document management views or a further community plugin is worth adopting.

    Follow-up M (mobile; specified when started, see docs/CAPABILITIES.md follow-ups):

    • M1 Templates and sync shortcuts. Apple Shortcuts that create notes from the Vault templates with conforming frontmatter and drive Working Copy pull, commit and push.
    • M2 Vault-borne requests. Mobile marks a note with kos_request, or adds a request note in 00_Inbox/Requests/. The Mac KnowledgeOS admits it after the next pull and writes results that sync back.
    • M3 GitHub Actions. Possible deterministic checks on push (YAML validity, conflict markers, duplicate IDs) reported back to the user. Any Action that commits makes it another Git writer and requires a revision of §5.7. Actions never call models and receive no KnowledgeOS credentials.

    각 질문이 무엇을 기다리는지 한 줄씩 풀면 [해석]:

    • Semantic ranking: 위 인계 3번과 같은 일입니다. 실제 노트로 related_min_score·related_min_probability와 이웃 수를 보고 정합니다.
    • Default ai_policy: 예약 정리(curate)를 실제로 쓰기 시작한 뒤에야 ask가 맞는 기본값인지 판단할 수 있습니다. ask 노트는 예약 작업의 모델에게 보이지 않습니다(ORG-3).
    • Schedules: 선언된 주기가 실제 사용과 맞는지는 자연 실행을 지켜본 뒤 판단합니다(C7).
    • Plugin choices: Obsidian 코어 Bases만으로 문서 관리 목록이 충분한지, 다른 커뮤니티 플러그인이 필요한지(C5).

    시작 전: 모바일 후속 과제#

    모바일에서도 처리는 언제나 Mac의 KnowledgeOS가 합니다. 모바일은 만들고, 고치고, 표시하고, 동기화만 합니다. 아래 세 가지(M1~M3)는 시작 전이며 명세는 시작할 때 구체화합니다. 모바일 전용 KnowledgeOS 앱은 하지 않기로 한 범위 밖입니다(운용 원칙).

    원본: docs/CAPABILITIES.md · Follow-up: mobile

    Follow-up: mobile#

    These are reserved and specified when started. Processing always happens in the Mac KnowledgeOS. Mobile only creates, edits, marks and syncs.

    • M1 Templates and sync shortcuts. Apple Shortcuts create capture, idea and question notes from the Vault templates, with conforming frontmatter including id, and drive Working Copy pull, commit and push. Acceptance to be written: a Shortcut-created note passes STD-7.
    • M2 Vault-borne requests. A note marked kos_request: <capability[:mode]>, or a request note in 00_Inbox/Requests/, is admitted by the Director after the Mac pulls. Results are written as usual, and the request marker is cleared through the C2 write path. To decide: request identity across devices, duplicate marks, and how the result is announced (digest or alert).
    • M3 GitHub Actions. Candidates are deterministic checks on push (YAML validity, conflict markers, duplicate IDs) reported as a check status or issue. Constraints: no model calls, no KnowledgeOS credentials, and no commits unless Blueprint §5.7 is revised to admit a second Git writer.

    쉬운 말로 정리하면 이렇습니다.

    과제 무엇 아직 정해야 할 것 (원본)
    M1 템플릿·동기화 단축어Apple 단축어로 포착·아이디어·질문 노트를 Vault 템플릿에서 만들고 Working Copy의 pull·commit·push를 구동인수 기준을 써야 함: 단축어로 만든 노트가 STD-7을 통과해야 함
    M2 Vault를 통한 요청노트에 kos_request: <기능[:모드]>를 표시하거나 00_Inbox/Requests/에 요청 노트를 두면, Mac이 pull한 뒤 Director가 접수. 결과는 평소처럼 쓰이고 요청 표시는 규격화 쓰기 경로로 지움기기 간 요청 신원, 중복 표시, 결과를 요약으로 알릴지 즉시 알림으로 알릴지
    M3 GitHub Actionspush 때의 결정적 점검(YAML 유효성, 충돌 표시, 중복 ID)을 점검 상태나 이슈로 보고제약: 모델 호출 없음, KnowledgeOS 자격 증명 없음, Blueprint §5.7을 고쳐 두 번째 Git 작성자를 인정하기 전에는 commit 없음

    kos_request 속성과 00_Inbox/Requests/ 폴더는 이 용도로 예약되어 있어 비활성이며, 다른 용도로 쓰지 않습니다. 지금 모바일에서 하는 일(Obsidian으로 쓰고 Working Copy로 동기화하면 Mac이 예약 작업으로 규격화·정리)은 아래 원문의 "지금" 부분입니다.

    Delivery order#

    Build in thin slices and revise this document after each one. The console and CLI grow with each slice.

    1. Owner core, Director (static), StandardizationOfficer and static EvalOfficer: C2 manual path and CLI batch, the C3 service, C11 basics, and a rebuildable project development image that keeps make image-id and make state-check working.
    2. Scheduling and attention: C7 standardize and digest, C8, C5.
    3. Thinking Team: C4 with ThinkingManager, its teammates, the model EvalOfficer and TeamReview.
    4. Curation Team: C1 with C6 review, then the curate job.
    5. Fabric: C9 Experience and C10 Gateway.
    6. Mobile: follow-ups M1 to M3.

    PROJECT_STATE.md의 목표 KNOWLEDGEOS_CAPABILITY_IMPLEMENTATION은 완료로 기록되어 있어 1~5번 조각은 모든 인수 시나리오가 테스트로 구현된 상태입니다. 6번(모바일)만 시작 전입니다. 지금의 목표 KNOWLEDGEOS_REAL_ADOPTION은 이 구현을 실제 호스트에서 하나씩 확인하는 일입니다(현재 상태).

    일부러 하지 않기로 한 것#

    기록에 결정으로 남은, 빠진 것이 아니라 의도한 것입니다. 후속 과제로 오해하지 마세요.

    • 알림 기록에 전달 실패 이유를 남기지 않는다: D_NOTICE_NO_FAILURE_REASON.
    • TeamReview의 일반 개선 제안은 후보로 자동 승격하지 않는다. 로컬 관찰로 두고, 이후 실제 사용자 수정 같은 사건이 생기면 그 사건 자체의 근거로 새로 기록합니다: D_C9_PENDING_CLASSIFICATION, C9.
    • Temporal은 호스트 loopback에만 공개한다: D_TEMPORAL_LOOPBACK.
    • 하지 않는 일(브라우저·CLI에서 문서 작업, Discord로 명령 받기, 모바일 전용 KnowledgeOS, Git 명령 실행 등)은 운용 원칙에 있습니다.
