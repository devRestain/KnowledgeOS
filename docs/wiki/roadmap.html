    남은 확인과 아직 만들지 않은 기능

    현재 남은 일은 기능 자체의 설명과 분리해 이곳에 모읍니다. 구현되어 있지만 실제 사용을 더 봐야 하는 일과 아직 구현하지 않은 모바일 요청 기능은 다릅니다. 완료 근거는 현재 상태에서 확인할 수 있습니다.

    다음에 이어갈 일#

    현재 인계 기록은 다음과 같습니다.

    # 상태 다음 작업
    1incompleteOpen Home and the Tasks dashboard in Obsidian to confirm daily tasks render and forwarded items stay hidden then review the open organize proposal and tune related_min_score related_min_probability and min_confidence against real notes

    읽기 쉽게 풀면 세 가지입니다.

    1. Home·Tasks 화면 확인. 데일리의 기한 없는 할 일이 실제 Obsidian 보기에서 나타나고, 과거 노트의 [>] 이월 항목은 숨겨지는지 확인합니다. 파일 처리와 Discord 전달은 실행 기록이 있지만 최신 보기의 장치 관찰은 남아 있습니다(E_HOME_TASKS_DEVICE, C12).
    2. 열린 정리 제안의 사용자 검토. 제안을 적용할지 거절할지는 사용자가 결정합니다. 에이전트가 문서를 정비한다는 이유로 대신 결정하지 않습니다(C6).
    3. 관련 노트·선택 질문 문턱 조정. related_min_score, related_min_probability, min_confidence를 실제 노트 결과와 비교합니다. 각각 벡터 후보 문턱, 관련성 판단 확률 문턱, 선택형 답의 채택 문턱입니다(C3, C2).

    별도 실행 근거가 필요한 경로#

    먼저 공유 System One의 선택지 배열 전달을 바로잡을 필요가 있습니다. 내부 도구는 선택지 목록을 받지만 Hermes→Owner의 HTTP 검사는 현재 배열을 거절합니다. 문자열·객체·정수와 구별해 배열을 검사하고, 실제 도구 HTTP 경계를 지나는 검증을 추가하는 것이 다음 구현 범위입니다. 이번에는 소스 대조만 했고 동작은 바꾸지 않았습니다(현재 상태).

    공개 인터페이스 테스트가 있어도 다음 실환경 근거까지 생긴 것은 아닙니다.

    확인할 경로 지금 구별해야 할 한계
    공유 System One 도구를 쓰는 네 모델 팀원도구 설치·집중 테스트는 있으나 linker·connector·challenger·synthesizer의 새 실제 모델 호출은 미실행(E_SHARED_SYSTEM_ONE_MODELS)
    기본 다섯 작업의 자연 실행과 지속 사용임시 예약 슬롯·수동 실행·따라잡기 기록이 모든 기본 시각의 장기 관찰은 아님
    문서 관리의 상태·보관 제안실제 System One 상태 제안과 실제 Bases 사용 관찰은 별도
    제안 거절·낡은 제안·자동 변경 되돌리기실제 제안 적용 기록이 이 분기들까지 증명하지 않음
    Gateway의 다른 Operation과의 왕복구현·테스트와 실제 송신자/수신자 연동은 별개
    HermesTrace 수신기로컬 사건·Candidate 생성과 실제 수신 확인은 별개
    충돌·효과 결과 불명의 즉시 Discord 전달요약·데일리 메시지 전달이 즉시 경고 조건의 실행 근거는 아님
    실제 Owner의 관리 콘솔기존 브라우저 관찰은 일회용 합성 환경

    과거 Gemma 분류의 시간 초과나 사이드바 1.1.0의 팝업 미확인은 당시 구성의 이력입니다. 현재 분류기는 Terra high이고, 사이드바는 인라인 방식입니다. 과거 구성을 다시 검증하는 일을 현재 과제로 만들지 않습니다.

    실제 사용으로 정할 세 가지#

    Blueprint §9에 남아 있는 열린 질문입니다.

    • 검색 품질: 기본 관련성 점수와 이웃 수가 실제 노트에서 적절한가.
    • 예약 주기: 지금의 다섯 작업 시각·주기가 실제 사용에 맞는가.
    • 보기 도구: 문서 관리에 Obsidian 코어 Bases만으로 충분한가.

    이는 기능이 없다는 뜻이 아니라 기본값과 도구 선택의 적합성을 평가하는 일입니다. Blueprint의 열린 질문이 원본입니다.

    아직 구현하지 않은 모바일 요청 기능#

    현재 모바일에서는 Obsidian으로 노트를 쓰고 Working Copy 등으로 동기화합니다. Mac이 그 파일을 받은 뒤 기존 예약 작업이 처리하는 흐름은 사용할 수 있지만, 모바일에 요청 표시를 붙여 KnowledgeOS를 호출하는 아래 경로는 아직 비활성입니다.

    후속 기능 만들려는 것 시작 전에 정할 것
    M1 템플릿·동기화 단축어Apple 단축어로 표준 노트를 만들고 Working Copy 동기화를 실행생성 노트가 규격화 계약을 만족하는 인수 기준
    M2 Vault를 통한 요청kos_request 또는 00_Inbox/Requests/를 Mac이 읽어 접수기기 간 요청 신원, 중복 방지, 결과 알림
    M3 GitHub Actionspush된 노트의 YAML·충돌·중복 ID를 결정적으로 검사결과 전달 방식; Git 작성자를 늘릴 경우 계약 개정

    M2의 속성과 폴더는 예약만 되어 있습니다. 지금 노트에 표시를 적는다고 요청이 실행되지는 않습니다. 모바일 전용 KnowledgeOS 앱, 원격 관리 API 개방, Actions의 모델 호출이나 자격 증명 보관을 이 계획에 포함하지 않습니다.

    원본 범위는 기능 명세의 모바일 후속과 사용자 모바일 흐름에서 확인할 수 있습니다.
