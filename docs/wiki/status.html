    현재 상태: 무엇이 어떤 근거로 확인되었나

    이 페이지는 PROJECT_STATE.md(진행과 검증 증거의 유일한 기계 판독 원본)를 읽기 쉽게 보여 줍니다. 핵심 질문은 두 가지입니다. 무엇이 되어 있는가, 그리고 그것을 어떤 종류의 근거로 알 수 있는가. 아직 안 된 것과 다음에 할 일은 로드맵에 있습니다.

    한눈에 보기#

    단계로 보면 이렇습니다. 앞의 두 단계(명세 재정립, 이전 구현 퇴역)와 세 번째 단계(모든 인수 시나리오를 공개 인터페이스 테스트로 구현)는 완료로 기록되어 있고, 지금 진행 중인 목표는 실제 호스트 도입(KNOWLEDGEOS_REAL_ADOPTION)입니다. 즉 "명세대로 동작하는 코드와 테스트"는 갖춰졌고, 이제 실제 Temporal·Hermes 역할 profile·Vault·Obsidian 위에서 하나씩 확인해 가는 중입니다.

    참고

    아래 숫자와 표는 매번 PROJECT_STATE.md와 명세에서 다시 만들어집니다. 이 페이지의 문장은 사람이 쓴 해설이라 표보다 늦을 수 있으니, 어긋나 보이면 표가 맞습니다.

    근거의 종류 (evidence class)#

    증거 기록마다 class가 붙어 있습니다. 같은 "pass"라도 종류에 따라 증명하는 범위가 다릅니다.

    참고

    원본에는 종류의 정의가 한곳에 적혀 있지 않습니다(저장소 규칙은 "static, runtime, deployment, device 증거를 따로 기록하고 돌리지 않은 것은 정확히 표시하라"고만 합니다). 아래 정의는 기록들의 쓰임에서 읽어 낸 해석입니다.

    class 어떤 근거인가 기록 예
    static소스·문서·표를 읽고 대조한 결과. 시스템을 실제로 돌리지는 않습니다추적표가 인수 ID와 일치(E_CAPABILITY_TRACE), 퇴역 자산 삭제(E_RETIREMENT_DELETE)
    runtime코드를 실제로 실행하거나 실행 중인 서비스·프로세스를 관찰한 결과. 일회용 환경인지 실제 호스트인지는 각 기록의 source와 observed로 구분합니다테스트 전체 통과(E_TRACED_TESTS), 합성 데이터의 콘솔 관찰(E_CONSOLE_BROWSER), 실제 호스트의 예약 슬롯 관찰(E_REAL_SCHEDULER_SLOT)
    external_service실제 외부 서비스(모델, Discord, Ollama)를 호출해 얻은 결과실제 모델 역할 스모크(E_REAL_ROLE_SMOKE), Discord 전달(E_DISCORD_DELIVERED), 실제 임베딩(E_REAL_SEMANTIC)
    device사용자의 실제 장치·Vault·Obsidian에서 관찰한 결과Obsidian에서 Owner 시작·중지(E_OBSIDIAN_OWNER_LIFECYCLE), 사용자가 제안 적용(E_USER_PROPOSAL_APPLY)
    deployment설치·구성이 실제 호스트에 적용되었음사이드바 플러그인 설치(E_SIDEBAR_INSTALL), Hermes cron 제거(E_HERMES_CRON_REMOVED)
    artifact만들어진 산출물(이미지, 아카이브, 해시)의 확인개발 이미지 빌드(E_DEV_IMAGE_BUILD), 아카이브 기록(E_RETIREMENT_ARCHIVE)
    semantic명세 해석·결정을 정리한 의미적 해소TeamReview 제안의 분류 충돌 해소(E_C9_CATEGORY_CONFLICT)

    result는 pass, fail, blocked 중 하나입니다. fail과 blocked 기록은 나중에 해결되어도 지우지 않고 남깁니다(예: E_DISCORD_MISSING_ACCESS는 이후 E_DISCORD_DELIVERED가 생겼지만 그대로 있습니다).

    "pass"가 증명하는 것과 증명하지 않는 것#

    확인된 것 증명하는 것 증명하지 않는 것
    테스트 통과 (runtime)명세의 시나리오가 공개 인터페이스를 통해 기대대로 동작함. 실제 Temporal 개발 서버와 LangGraph 위에서 돌았음실제 모델의 응답 품질, 실제 Hermes profile 설치, 예약 작업의 실제 시각 실행, launchd 등록과 Owner 시작·중지, Discord 전송, 실제 HermesTrace 수신기, Obsidian GUI. 테스트에서 모델 역할은 스크립트 대역이고 Hermes와 launchctl은 가짜 실행 파일이며 시계는 가짜입니다
    추적표 일치 (static)모든 인수 ID에 구현 위치와 테스트가 연결되어 있음테스트가 통과했다는 것, 배포되었다는 것
    일회용 환경 관찰 (runtime)합성 데이터로 띄운 Owner가 콘솔에서 보이고 동작함실제 Owner·실제 Vault에서도 같다는 것
    실제 외부 서비스 한 번의 성공 (external_service)그 구성에서 조립이 된다는 것(모델 경로, 전달 경로, 임베딩 경로)품질이나 꾸준한 신뢰성. 예: 모델 역할 스모크는 라벨이 붙은 스모크 노트 세 개로 한 번씩 돌린 것입니다
    실제 장치에서의 관찰 (device)그 장치·그 시점·그 버전에서 그것이 보이고 동작함다른 버전이나 관찰하지 않은 부분. 예: 1.2.0의 인라인 GUI 관찰(E_SIDEBAR_INLINE_GUI)이 앞선 1.1.0 팝업 메뉴의 미확인 이력(E_SIDEBAR_NATIVE_MENUS)을 바꾸지는 않습니다
    브라우저 대역 렌더링사이드바 소스가 DOM 대역에서 그려지고 넘침이 없음(E_SIDEBAR_PREVIEW)실제 Obsidian 플러그인 설치와 GUI 관찰은 별개입니다(README)

    그래서 로드맵의 "아직 확인하지 못한 것"은 "실패했다"가 아니라 "이 종류의 증거가 아직 없다"는 뜻입니다.

    주의

    추적표 문서의 머리말에는 "네이티브 Hermes/모델 호출, 실제 Discord, 실제 Owner 서비스 배포, Obsidian/장치 검증은 돌리지 않았다"고 적혀 있습니다. 이 문장은 추적표가 가리키는 테스트 묶음의 범위를 말한 것이고, 그 뒤 실제 환경 스모크는 PROJECT_STATE.md에 따로 기록되어 있습니다(아래 증거 표). 둘을 섞어 읽지 마세요.

    PROJECT_STATE.md 맨 위의 /checkpoint 줄에는 기록 시점의 revision과 dirty 여부가 있습니다. revision이 UNKNOWN이거나 dirty=true이면 그 기록이 특정 커밋에 고정되지 않았다는 뜻입니다 [해석].

    검증 범위#

    테스트는 실제 Temporal 개발 서버와 LangGraph를 사용하지만, 모델 역할은 스크립트 대역이고 Hermes와 launchctl은 가짜 실행 파일이며 시계는 조작 가능한 가짜입니다. 실제 모델 호출, Hermes profile 설치, 예약 작업의 실제 시각 실행, launchd 등록과 Owner 시작·중지, Discord 전송, 실제 HermesTrace 수신기, Obsidian GUI는 별도로 확인해야 하며, 그 결과는 PROJECT_STATE.md에 따로 기록합니다.

    이전 구현의 퇴역#

    이전 KnowledgeOS 구현(소스, 내부 상태, Runtime, 역할 profile, 합성 Vault 노트)은 복구용 아카이브에 보관한 뒤 삭제했고, 호환이나 재생 의무는 없습니다. 이 위키가 설명하는 것은 퇴역 뒤 명세에 맞춰 새로 만든 구현입니다(E_RETIREMENT_ARCHIVE, E_RETIREMENT_DELETE).
