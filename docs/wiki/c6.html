    C6 검토: 적용·거절·되돌리기

    한눈에 보기#

    KnowledgeOS는 판단이 필요한 변경을 노트에 직접 쓰지 않고 제안(용어 참고)으로 만들어 둡니다. C6은 그 제안을 사용자가 적용하거나 거절하는 단계이고, 자동 규격화가 바꾼 것을 되돌리는 단계입니다. 결정은 항상 사람의 명시적 행동으로만 일어납니다.

    적용은 "제안을 만들 때 본 노트가 지금도 그대로일 때만" 일어납니다. 그사이 노트가 바뀌었으면 아무것도 쓰지 않고 다시 요청하라고 안내합니다. 이렇게 해서 사용자가 나중에 고친 내용을 KnowledgeOS가 덮어쓰는 일을 막습니다.

    항목 내용
    트리거사용자가 제안 노트에서 "적용" 또는 "거절"을 누르거나, 노트에서 "자동 변경 되돌리기"를 실행 (사람의 행동만 트리거)
    담당Owner의 효과(effect). 모델 역할은 없음 (기능 요약표의 Roles 칸은 "—")
    결과물대상 노트에 반영된 체크한 변경, 삭제된 제안 파일, 복원된 노트, 기록된 결정(HumanActionResponse)
    사용자 결정 여부예. 적용·거절·되돌리기 모두 사용자가 직접 결정

    왜 이 명세가 필요한가#

    USER_FEATURE_SPEC.md의 '지키는 약속' 가운데 세 가지를 지키기 위한 단계입니다.

    • "Vault는 사용자의 것입니다." 약속 1. 사용자가 어디서든 노트를 고칠 수 있으므로, 제안을 만든 뒤 노트가 바뀌었을 가능성을 항상 전제해야 합니다. 정확한 내용 확인(SHA-256 preimage) 없이 적용하면 사용자의 수정을 덮어쓰게 됩니다.
    • "자동으로 바꾸는 것은 작고 기계적인 것뿐입니다." 약속 4. 판단이 필요한 변경은 제안으로 만들고 적용은 사용자가 결정한다는 약속을 이 기능이 실제로 구현합니다. C6이 없으면 제안은 읽기만 하는 메모가 되거나, 반대로 사용자 모르게 적용되어 버립니다.
    • "Git이 백업이자 이력입니다." 약속 5. 거절·적용된 제안 파일은 지워지지만 기록은 Git에 남고, 되돌리기가 거절하는 경우에도 Git 이력으로 안내합니다.

    결정이 기록되지 않거나 응답이 유실될 때 같은 요청이 두 번 적용되면 노트가 이중으로 바뀔 수 있습니다. 그래서 모든 결정은 요청 ID로 기록되고, 유실된 응답은 재전송이 아니라 기록 조회로 풀립니다(용어 참고).

    어떻게 쓰는가#

    Obsidian에서 (Thin Client·Note Toolbar·사이드바)#

    1. 검토 대기 목록 보기. 검토용 Bases 화면이 제안과 보고서를 나열합니다.
    2. 제안 노트(type: proposal)를 엽니다. 변경 체크리스트와 diff가 보입니다.
    3. 원하지 않는 변경은 체크를 해제합니다. 체크리스트는 직접 고칠 수 있습니다.
    4. 적용을 누릅니다. Note Toolbar의 적용 버튼, 명령 팔레트의 "적용 · 거절", 사이드바의 적용 버튼 중 하나입니다. 사이드바에서는 제안 노트에서만 적용·거절이 나타납니다(C11).
    5. 결과 알림을 확인합니다. 적용되었으면 체크한 변경만 대상 노트에 들어가고 제안 파일은 사라집니다. 대상이 그사이 바뀌었으면 노트는 그대로이고 제안이 stale로 표시되며, 알림이 다시 요청하라고 안내합니다.
    6. 원치 않으면 거절을 누릅니다. 결정이 기록되고 제안 파일이 삭제되며 대상 노트는 바뀌지 않습니다.

    되돌리기. 자동 규격화(C2)나 수동 규격화가 바꾼 노트에서 "자동 변경 되돌리기"를 실행합니다. 사이드바에서는 더보기를 선택한 뒤 같은 영역의 되돌리기를 누릅니다. 직전 규격화 변경의 원래 내용으로 복원하되, 노트가 그 변경의 결과 그대로일 때만 합니다. 그 뒤 노트를 고쳤다면 아무것도 쓰지 않고 Git 이력으로 되돌리라고 안내합니다.

    콘솔·CLI#

    C6의 사용 경로는 Obsidian 쪽(Note Toolbar, 명령, 사이드바)입니다. USER_FEATURE_SPEC의 "하지 않는 일"은 브라우저 콘솔과 CLI에서 문서 작업을 하지 않는다고 못 박고 있으므로, 둘은 적용·거절을 하지 않는 관리용입니다. 결과를 알 수 없는 요청의 관리는 C11과 사용 가이드를 보세요.

    자동 경로#

    사용자의 결정을 대신하는 자동 적용은 없습니다. 자동으로 일어나는 것은 7일이 지난 stale 제안의 삭제뿐입니다.

    사용 예#

    00_Inbox/에 적은 포착 노트에 대해 C1의 "정리 요청"으로 제안이 만들어졌다고 합시다. (아래는 설명용 가상 예시입니다.)

    1. 제안에 세 항목이 체크되어 있습니다: 종류를 question으로, 제목 추가, 40_Knowledge/Questions/로 이동.
    2. 이동은 원하지 않아 체크를 해제하고 적용합니다.
    3. 종류와 제목만 노트에 반영되고 파일은 제자리에 있으며 제안 파일은 사라집니다. 이것이 REV-1과 ORG-4가 확인하는 동작입니다.
    4. 만약 적용 전에 그 노트를 직접 고쳤다면 3번 대신 노트는 그대로이고 제안이 stale이 되며 "다시 요청" 안내가 나옵니다 (REV-2).

    동작 흐름#

    흐름의 순서는 원본 명세가 정합니다. 적용은 결정을 먼저 기록하고, 그 다음 대상의 현재 SHA-256이 기록된 preimage와 같을 때만 체크한 변경을 적용하며, 마지막에 제안 파일을 삭제합니다. 결과를 관찰할 수 없으면 unknown으로 남고 자동 재전송은 없습니다(Blueprint §6의 효과 규칙 5).

    참고

    응답이 유실되면 클라이언트는 같은 요청을 다시 보내지 않고 요청 ID의 기록된 결과를 읽습니다. Owner가 "기록된 적이 없다"고 확정해 알려 줄 때만 동일한 요청을 다시 보낼 수 있고, 기록된 unknown은 재실행 허가가 아닙니다 (REV-4, SUR-1).

    C6 Review#

    The user decides on KnowledgeOS output inside Obsidian.

    • Queue: the review Bases view lists proposals and reports. A proposal note shows its checklist and diff, and Note Toolbar offers the "적용" and "거절" commands on notes with type: proposal.
    • Apply is one explicit action. The Owner records the decision first. It then applies the checked changes only if the target's current SHA-256 equals the recorded preimage, and deletes the proposal file. On a preimage mismatch, the decision stays recorded as accepted-not-applied, the proposal is marked stale, and the notice offers to request it again.
    • Reject records the decision and deletes the proposal file.
    • Undo ("자동 변경 되돌리기" on the current note) restores the recorded preimage of the last autofix or manual standardization, but only if the note still equals that change's result. Otherwise it refuses and points to Git history.
    • Expiry: stale proposals are deleted after 7 days.
    • Preservation: an open or stale proposal reserves its target until the user decides or stale expiry occurs. Regeneration is the sole create-only exception: it requires the exact bytes still recorded as Owner-written and preserves user edits, including checklist edits. A State-unrecorded proposal is never overwritten or duplicated. An explicit new user request may refresh an unchanged stale proposal under the same checks.
    • Recorded outcomes: every decision is a HumanActionResponse. Outcomes distinguish received, applied, not applied and unknown. A lost response is resolved by reading the request ID's recorded outcome, never by resending.

    Acceptance:

    • REV-1 Given a proposal and an unchanged target, when the user applies it, then exactly the checked changes appear in the target and the proposal file is gone.
    • REV-2 Given the target was edited after the proposal was created, when the user applies it, then the target is unchanged, the proposal is stale and the decision is recorded.
    • REV-3 Given an autofix followed by a user edit to that note, when undo is requested, then nothing is written and the notice points to Git history.
    • REV-4 Given the client times out after apply, when it reconnects, then it shows the recorded outcome for that request ID and nothing is applied twice.

    현재 상태와 남은 일#

    PROJECT_STATE.md와 Blueprint §9가 말하는 사실만 적습니다.

    • 계약 테스트: C6 인수 시나리오 REV-1~REV-4는 추적표에 구현 심볼과 테스트 노드가 연결되어 있습니다. 전체 테스트 통과는 E_TRACED_TESTS가 기록합니다(248개 통과, 건너뜀·xfail 없음).
    • 실환경 근거:
      • 사용자가 실제 Vault에서 스모크 제안을 적용했습니다. 체크한 변경 7개로 포착을 40_Knowledge/Questions로 옮기고 제안을 삭제했습니다(E_USER_PROPOSAL_APPLY, 장치 확인 통과).
      • Note Toolbar는 제안 전용으로 정리되어 적용·거절 버튼이 있습니다(E_VAULT_CONFIG_CLEANUP).
      • 실제 모델 역할 스모크가 열린 제안 1개를 만들었습니다(E_REAL_ROLE_SMOKE).
    • 기록되지 않은 것: 실환경에서 stale 제안(REV-2), 되돌리기 거절(REV-3), 요청 시간 초과 후 재접속(REV-4)을 관찰했다는 기록은 PROJECT_STATE.md에 없습니다. 이 위키에서 확인할 수 있는 근거는 계약 테스트이며, 기록 부재가 실행하지 않았다는 증거는 아닙니다.
    • GUI 근거의 범위: 현재 인라인형 사이드바 1.2.0의 실제 설치·화면 관찰은 E_SIDEBAR_INLINE_INSTALL·E_SIDEBAR_INLINE_GUI에 기록되어 있습니다. 다만 제안 노트에서 적용·거절 버튼이 나타나는 양성 사례는 이 GUI 기록으로 입증되지 않으므로 테스트 근거와 구분해야 합니다. 이전 1.1.0 관찰에서는 일반 노트에서 결정 영역이 숨겨진 것을 확인했지만 제안 노트가 없어 양성 사례를 확인하지 못했습니다. 당시 네이티브 팝업 내용을 확인하지 못한 E_SIDEBAR_NATIVE_MENUS의 blocked는 과거 이력이며, 더보기 등을 팝업 없이 표시하는 현재 인라인 UI의 미확인을 뜻하지 않습니다.
    • C6만의 미결 항목: Blueprint §9의 열린 질문 중 C6에 해당하는 것은 없습니다. 열린 handoff는 첫 정시 규격화·임베딩 실행 관찰과 related_min_score 조정으로, C6과 무관합니다.

    전체 계획은 로드맵, 검증 근거 전체는 현재 상태에서 볼 수 있습니다.

    관련 기능#

    • C1: 정리가 만든 제안이 C6의 주된 검토 대상입니다. 체크 해제 후 적용은 ORG-4가 다룹니다.
    • C2: 자동·수동 규격화의 변경이 "자동 변경 되돌리기"의 대상입니다.
    • C5: 문서 관리가 만든 보관 제안도 같은 방식으로 검토합니다. 예: 완료된 프로젝트의 보관 제안은 사용자가 결정할 때까지 하나만 유지됩니다 (DOC-4).
    • C9: 제안의 적용·체크 해제·거절, 되돌리기는 해당 역할의 피드백이 됩니다. 예: 거절된 정리 제안은 다음 classifier의 feedback에 들어갑니다 (LRN-1).
    • C11: 적용·거절·되돌리기를 호출하는 명령, 사이드바, 요청 ID 기반 복구 규칙이 여기 있습니다 (SUR-8).
    • C8: 알림은 알림만 합니다. Discord 메시지나 반응으로는 아무것도 승인되지 않으므로 적용·거절은 항상 Obsidian에서 합니다.
