    C2 규격화 (Standardize)

    1. 한눈에 보기#

    규격화는 노트가 Vault 계약(id·type·created·status·ai_policy 같은 frontmatter)에 맞도록 작고 최소한으로 고쳐 주는 기능입니다. 담당인 StandardizationOfficer는 Owner 코드이고, 규칙 1~8은 같은 입력이면 늘 같은 결과를 내는 결정적 규칙입니다. 규칙 9만은 System One(용어)에게 선택지가 고정된 값을 묻습니다. 폴더로 정할 수 없는 type, 올바르지 않은 status·confidence, 빠졌거나 잘못된 capture_kind가 그 대상이며, System One은 선택지 안에서 고르기만 하고 쓰는 것은 Owner입니다. 제목·태그·링크·폴더나 이미 유효한 type을 다시 분류하는 일, 그리고 ai_policy·sensitivity는 묻지 않으며 C1 정리(또는 사용자)의 몫입니다.

    항목 내용
    트리거작성할 때(QuickAdd·Templater 템플릿), 수동(Thin Client "규격화 미리보기", CLI standardize), 자동(standardize 예약 작업, 매시간 :00)
    담당StandardizationOfficer(Officer, static; 규칙 9는 System One에게 질문)와 정적 EvalOfficer. Team·Manager·Hermes 모델 역할 없음
    결과물노트 자체의 작은 frontmatter 변경: 자동 경로는 Autofix, 수동 경로는 확인을 거친 변경
    사용자 결정 여부자동 경로는 불필요(확신도가 기준 이상인 값만 적용). 수동 경로는 System One이 고른 값과 확신도가 diff 위에 나오고, 확인 또는 취소. 판단이 필요한 나머지 필드는 다루지 않음

    (출처: CAPABILITIES 요약표와 C2. 아래 "원본 명세"에 전문이 있습니다. Autofix, Officer, Work 같은 용어는 용어를 참고하세요.)

    2. 왜 이 명세가 필요한가#

    KnowledgeOS의 다른 기능은 모두 노트가 id와 type을 갖고 있다고 기대합니다. 그런데 사용자는 frontmatter 없이도 자유롭게 쓸 수 있어야 합니다. 이 간극을 메우는 것이 규격화이고, 그래서 사용자 기능 명세의 다음 약속을 직접 지킵니다.

    • 자동으로 바꾸는 것은 작고 기계적인 것뿐입니다. "빠진 frontmatter를 채우는 결정적 규격화만 자동"이라는 약속(USER_FEATURE_SPEC '지키는 약속' 4)이 C2의 모든 규칙을 제한합니다. 값이 없거나 모양이 잘못된 곳에만 적용하고, 본문·기존 속성·파일 위치는 바꾸지 않습니다.
    • Vault는 사용자의 것입니다. frontmatter·폴더 없이 쓴 Markdown도 그대로 유효하므로, 규격화는 일반 Markdown을 폴더만으로 제외하지 않으면서도(Vault 맨 위에 쓴 노트 포함) 사용자의 기존 줄은 그대로 둡니다.
    • Git이 백업이자 이력입니다. diff가 작고 읽기 쉬워야 하므로 최소 diff만 씁니다(운용 원칙).

    규격화가 없다면 결과는 둘 중 하나입니다. 사람이 id·type을 일일이 채우거나, 규격이 없는 노트가 검색·정리·문서 관리에서 빠집니다. 반대로 규격화가 모델의 추측을 아무 제한 없이 받아쓴다면 "자동 변경은 기계적인 것뿐"이라는 약속이 깨집니다. 그래서 선택지가 고정된 값(enum)만 System One에게 묻고, 확신도가 기준(기본 0.7) 미만이거나 none_of_these, 거절이면 그 필드는 바꾸지 않고 이유와 함께 "정하지 못함"으로 남깁니다. 사용자가 직접 쓴 daily 같은 기존 종류와 ai_policy·sensitivity 같은 개인정보 필드는 아예 묻지 않습니다.

    3. 어떻게 쓰는가#

    3.1 작성할 때 (플러그인)#

    QuickAdd 선택지와 Templater 템플릿(99_System/Templates/)으로 노트를 만들면 처음부터 규격에 맞는 frontmatter가 들어갑니다. KnowledgeOS 호출은 없고 플러그인이 쓰는 경로입니다(Blueprint §3.1). 템플릿으로 만든 노트에는 규격화가 변경을 제안하지 않아야 하며(STD-7), 모바일의 Apple 단축어 후속 과제 M1도 같은 기준을 목표로 합니다.

    3.2 수동: Obsidian Thin Client#

    1. 노트를 열고 사이드바에서 규격화를 선택한 뒤 아래 기능 창의 미리보기를 누릅니다. 기능 선택만으로는 요청하지 않습니다. 명령 팔레트나 파일·편집기 메뉴의 규격화 미리보기로도 실행할 수 있으며, 선택한 여러 파일·폴더는 해당 명령에서 대상으로 고릅니다.
    2. 클라이언트는 노트 경로와 마지막으로 본 내용의 SHA-256만 보내고 본문은 보내지 않습니다(SUR-1).
    3. 사이드바에서는 같은 기능 창에 diff와 적용 / 취소가 표시됩니다. 명령 팔레트·문맥 메뉴에서는 기존 미리보기 창에서 확인합니다. 명시적으로 적용하거나 취소할 때까지 기다립니다.
    4. 적용하면 바뀌지 않은 대상만 각각 반영됩니다. 그사이 바뀐 대상은 쓰지 않고 "달성 못함"으로 보고합니다(STD-3). 취소하면 아무것도 쓰지 않고 변경 기록도 남지 않습니다(STD-8).
    5. 방금 편집한 노트도 수동 경로에서는 규격화할 수 있습니다(STD-4).
    6. System One이 고른 값: type이나 status가 비었거나 잘못된 노트의 미리보기에는 System One이 고른 값과 확신도(예: status: draft → seed, 93%)가 diff 위에 나옵니다. 확인하기 전에는 아무것도 쓰지 않습니다(STD-9). 사이드바에서는 Thin Client 1.3.0이 diff 위에 "System One: 항목 → 값 (NN%)" 줄을 그립니다. 1.3.0은 활성 Obsidian 플러그인 폴더에 설치되었고, 실제 사이드바에서 "System One: status → seed (93%)"와 적용/취소가 모달·메뉴 없이 보이는 것을 확인했습니다(E_SYSTEM_ONE_CLIENT_INSTALL, E_SYSTEM_ONE_CLIENT_GUI).

    자유 요청에서도 모델 Director는 규격화 미리보기만 매핑할 수 있고, 작업·검토·예약 관리 명령은 매핑하지 못합니다(C11). 자유 요청이 KnowledgeOS와 무관해 보이면 Director에 가기 전에 System One이 먼저 걸러 낼 수도 있습니다(C11, SUR-10).

    3.3 수동: CLI 일괄 처리#

    knowledgeos standardize PATH --dry-run   # 계획된 변경만 출력, 아무것도 쓰지 않음
knowledgeos standardize PATH --apply     # 같은 Owner 접수와 효과 규칙으로 적용

    폴더 전체에 --dry-run을 먼저 돌려 계획을 보는 것이 권장 순서입니다. --dry-run은 아무것도 쓰지 않습니다(SUR-5). 명령 형태는 README의 "사용" 절에서 가져왔습니다.

    3.4 자동: standardize 예약 작업#

    Owner가 켜져 있는 동안 매시간 :00에 C7의 standardize 작업이 마지막 실행 이후 내용 해시가 바뀐 노트에 규칙을 적용합니다(Git 이력이나 실행 이력으로 판단하지 않습니다). 최근 10분(기본 조용한 시간) 안에 편집한 노트는 건너뛰고 다음 실행에서 다시 검토합니다. Owner가 꺼져 있으면 실행되지 않으며, 켜진 뒤 시작 지연이 지나면 놓친 슬롯을 한 번만 실행합니다(JOB-4). 수동으로 지금 실행하려면 knowledgeos job run standardize를 씁니다.

    3.4.1 규칙 9: System One이 값을 고르는 방식#

    노트 하나에 대해 요청 하나를 보내고, 필드마다 선택 질문 하나(계약의 값 + none_of_these)를 담습니다. 노트 본문은 설정한 길이(기본 8,000자)까지만 보냅니다.

    묻는 필드 묻는 조건
    type없고 폴더로도 정해지지 않을 때
    status그 type의 유효한 값(또는 archived)이 아니고 대소문자만의 차이도 아닐 때. 방금 type을 정했다면 규칙 5의 초기 status를 쓰거나, 기존 status가 틀렸을 때는 두 번째 요청으로 묻습니다
    confidenceknowledge 노트에 있지만 값이 잘못됐을 때
    capture_kindcapture 노트에서 없거나 잘못됐을 때
    • 수동·일괄 경로는 remote_ok와 ask 노트를 보낼 수 있고, 자동 경로(standardize 예약 작업)는 remote_ok 노트만 보냅니다. local_only·confidential·deny는 어느 경로에서도 보내지 않습니다. 정책은 보내기 직전의 현재 값으로 다시 확인합니다.
    • 선택지 안의 값이고 none_of_these가 아니며 확신도가 기준 이상일 때만 일반 변경(규칙 system_one)이 됩니다. 확신도와 함께 변경 기록에 남아 되돌리기(C6)가 가능합니다.
    • 정하지 못한 필드는 바뀌지 않고 이유가 붙습니다: unconfigured, unavailable, deferred(활동 시간 창이 끝나 갈 때 미룸), policy, refused, none_of_these, low_confidence.
    • unavailable·deferred로 끝난 노트는 "정해지지 않은" 것이라 다음 실행에서 다시 묻습니다. 다른 이유로 끝난 노트는 내용이 바뀔 때까지 다시 묻지 않습니다(STD-10, STD-11).
    • System One이 꺼져 있거나 실패해도 규칙 1~8은 그대로 적용되고, 한 요청 안에서 다시 시도하지도 않습니다. 이 호출의 기록(system_one State)에는 질문 이름·입력 해시·토큰 수만 남고 노트 내용은 남지 않습니다.

    참고

    독립 평가자는 정적 기준 decisions_grounded로 모든 system_one 변경이 (1) 규칙 9 필드의 허용된 값이고 (2) 기록된 기준 이상의 답과 같으며 (3) 그 요청의 출처에 대해 원격 모델 사용이 허용된 노트의 것인지 확인합니다.

    3.5 되돌리기#

    Thin Client의 자동 변경 되돌리기는 마지막 Autofix나 수동 규격화의 기록된 preimage를 복원합니다(C6). 노트가 그 변경의 결과와 같을 때만 동작하며, 그 뒤 사용자가 고쳤다면 거절하고 Git 이력을 안내합니다(REV-3).

    3.6 작은 예#

    40_Knowledge/Ideas/에 frontmatter 없이 본문만 있는 노트를 하나 만들었다고 합시다.

    식물 키우기 앱은 물 주기 알림보다 "시든 정도"를 먼저 보여 줘야 할지도 모른다.

    매시간 작업이나 수동 확인이 끝나면 다음 값이 채워집니다. 실제 값은 실행 시점의 값입니다.

    ---
id: <새로 만든 UUIDv4>
type: idea
created: <KnowledgeOS가 이 파일을 처음 관찰한 시각, ISO-8601 + 오프셋>
status: seed
ai_policy: ask
---

    본문 바이트는 그대로입니다(STD-1). 이미 규격에 맞는 노트에 다시 실행하면 어느 경로에서도 아무것도 쓰지 않습니다(STD-5).

    본문 끝에 tags: [a, b] 줄이 잘못 들어가 있고 frontmatter에는 tags: [b]가 있었다면, frontmatter는 [b, a]가 되고 그 줄만 본문에서 사라집니다. 다른 부분은 바뀌지 않습니다(STD-2).

    도움말

    처음 쓰는 폴더에는 CLI --dry-run으로 어떤 변경이 계획되는지 먼저 확인하세요. 노트 하나는 Thin Client 미리보기가 같은 일을 합니다.

    4. 동작 흐름#

    C2에는 맞는 이름의 도식이 없습니다. 도식의 Work 흐름은 Team·Manager 경로를 그리지만, 규격화는 Officer 하나가 혼자 만들고 EvalOfficer가 평가하는 가장 짧은 경로입니다. 단계는 다음과 같습니다(Blueprint §4.3, §6).

    1. 요청: Thin Client, CLI, 또는 schedule/standardize 예약 실행이 요청 ID와 함께 들어옵니다.
    2. Director 접수: 정형 요청이므로 모델 없이 정적 코드가 WorkSpec으로 접수합니다. 접수 시점에 대상 노트의 정확한 바이트를 State에 스냅샷합니다.
    3. StandardizationOfficer: 규칙 1~8을 적용하고, 규칙 9에 해당하는 필드가 있으면 System One에게 한 번 묻습니다(노트마다 요청 하나, 필요하면 status용 두 번째). 답이 기준을 넘으면 계획(변경 목록)에 system_one 규칙으로 넣습니다.
    4. 정적 EvalOfficer: 계획을 독립적으로 평가합니다. Officer는 1 segment 예산입니다.
    5. 확인(수동만): 미리보기가 사람의 확인 또는 취소를 기록할 때까지 기다립니다. 자동 경로는 이 단계가 없습니다.
    6. Owner 쓰기: 쓰기 직전 현재 SHA-256이 예상 preimage와 같은지 확인하고 원자적으로 교체합니다. 다르면 쓰지 않고, 병합·재시도도 없습니다. 쓰기 전에 의도를 기록하고, 쓴 뒤 preimage·결과 digest와 정확한 delta를 변경 기록에 남겨 되돌리기(C6)를 가능하게 합니다.

    참고

    건너뛰는 경우: 자동 경로는 조용한 시간(10분) 안에 수정된 노트를 건너뜁니다. 모든 경로는 충돌 표시, 파싱할 수 없는 YAML, 중복 ID가 있는 노트를 건너뛰며, 이들은 주의 항목(C5)이 됩니다.

    5. 원본 명세#

    원본: docs/CAPABILITIES.md · C2 Standardize

    C2 Standardize#

    The StandardizationOfficer makes notes conform to the Vault contract with minimal edits. Rules 1-8 are deterministic. Rule 9 lets System One map closed-set (enum) values that need judgment; every other judgment, such as title, tags, links, folder or reclassifying a valid type, belongs to capability C1.

    Three paths:

    Path Who How Writes
    AuthoringThe user, through pluginsQuickAdd choices and Templater templates in 99_System/Templates/ create notes with conforming frontmatterThe new note (by the plugins)
    ManualThe user, through KnowledgeOSThin Client "규격화 미리보기" on a note, selection or folder shows the exact diff and applies after confirmation. The CLI batch does the same for maintenance with --dry-run and --applyConfirmed changes
    AutomaticThe standardize job (C7)Applies the rules to notes changed since the last run, honoring the quiet periodAutofix

    Rules. Each rule applies only where the value is missing or malformed.

    1. Create a frontmatter block if absent.
    2. Add id: a new UUIDv4 when missing or malformed. UUID validity is deterministic, not a classification judgment.
    3. Add type derived from folder:
      • 00_Inbox/ → capture
      • 40_Knowledge/Ideas/ → idea
      • 40_Knowledge/Notes/ → knowledge
      • 40_Knowledge/Questions/ → question
      • 40_Knowledge/Sources/ → source
      • 20_Projects/<name>/<name>.md → project
      • Anywhere else, rule 9.
    4. Add created: the first time KnowledgeOS observed the file.
    5. Add the type's initial status.
    6. Add ai_policy: the Owner's default.
    7. Normalize shapes:
      • tags and aliases become lists.
      • A leading # is dropped from tags.
      • Dates become ISO-8601 with an offset.
      • Enum values use their canonical case.
    8. Move trailing body lines that are frontmatter keys of known list properties (such as tags: or related:) into frontmatter. Merge them with existing values without duplicates, and remove only those lines.

    9. Ask System One for closed-set values that need judgment, one request per note with one choice question per field over the contract's values (Blueprint §5.2, §5.3) plus none_of_these:

      • type when it is missing and rule 3 derives none;
      • status when it is neither a valid value of the note's type (or archived) nor one up to case;
      • confidence of a knowledge note when present but invalid;
      • capture_kind of a capture when missing or invalid.

      A type decided this way gets the initial status by rule 5, or a second request when its existing status is invalid for that type. An accepted answer (System One section) becomes an ordinary planned change with rule system_one, recorded with its confidence; anything else leaves the field unchanged and is listed as undecided with its reason (unconfigured, unavailable, deferred near the Activity window's end, policy, refused, none_of_these or low_confidence). Manual and batch Work may send remote_ok and ask notes; the automatic path only remote_ok. An existing unknown type (for example a user's own daily), a missing confidence, ai_policy, sensitivity and every non-enum field are never judged.

    Outside the explicit system, review, reserved and ignored-path exclusions below, a folder alone never excludes ordinary Markdown, including a note at the Vault root; only navigation notes identified as home or system are excluded as navigation.

    Never:

    • Change other body text.
    • Delete, rename or reorder properties.
    • Rename or move files.
    • Touch deny notes, 99_System/, 01_AI_Review/, the reserved 00_Inbox/Requests/, navigation notes, attachments or ignored paths.

    Skips:

    • The automatic path skips notes modified within the quiet period (default 10 minutes).
    • All paths skip notes with conflict markers, unparseable YAML or a duplicate ID. These become attention items.
    • The automatic path detects changes by content hash, not by Git history or the mere occurrence of a prior run. A note whose rule-9 question was unavailable or deferred is not settled, so the next run asks again; other outcomes settle it until its content changes.

    Write: an exact-preimage check, an atomic replace and a minimal diff (Blueprint §5.7, §6). A manual preview waits for a recorded human confirmation or cancellation and shows each System One value with its confidence above the diff. Confirmation applies unchanged targets independently; a changed target is not written and is reported unmet. Each write records its preimage and result digests and the exact delta, including System One decisions, in the change log, which supports undo (C6).

    Static criteria (EvalOfficer): skips respected, result valid, properties preserved, minimal diff, and decisions grounded: every system_one change is an offered value of a rule-9 field, equals an accepted answer at or above the recorded threshold, and belongs to a note whose admitted policy allows remote model use for the Work origin.

    Acceptance:

    • STD-1 Given a frontmatter-less note in 40_Knowledge/Ideas/, when standardize runs, then it gains id, type: idea, created, status: seed and ai_policy: ask, and its body bytes are unchanged.
    • STD-2 Given a note whose body ends with tags: [a, b] and whose frontmatter has tags: [b], then the frontmatter becomes [b, a], the trailing line is removed and nothing else changes.
    • STD-3 Given the note changes between preview or read and write, then nothing is written. The manual path reports the change; the automatic path reconsiders the note on its next run.
    • STD-4 Given a note edited 2 minutes ago, then the automatic path skips it, while a manual preview and confirmation still standardizes it.
    • STD-5 Given an already conforming note, then every path writes nothing.
    • STD-6 Given frontmatter with custom keys and quoted values, then only missing keys are appended, and existing lines stay byte-identical.
    • STD-7 Given a note created from each type template, then standardization proposes zero changes.
    • STD-8 Given a manual preview that the user cancels, then nothing is written and no change-log entry exists.
    • STD-9 Given a note at the Vault root with status: 초안 and no type, when a manual preview runs with System One answering knowledge (0.92) and then developing (0.81), then two requests are sent (type, then status), the preview shows both values with their confidence, nothing is written until confirmation, sensitivity and ai_policy are never asked, and the system_one State records carry the Work ID but no note text.
    • STD-10 Given remote_ok notes with invalid statuses or a missing capture_kind, an ask note and a low-confidence answer, when the automatic path runs, then only confident answers are written as autofix, the ask note's text is never sent, the low-confidence field is left unchanged, and a second run sends nothing for the settled notes.
    • STD-11 Given System One is down, when the automatic path runs, then rules 1-8 still apply, the rule-9 field stays unchanged with reason unavailable, and the next run after recovery asks again and applies the answer.

    7. 현재 상태와 남은 일#

    • 명세·구현·추적: C2의 STD-1~STD-11은 모두 추적표에 구현 심볼과 테스트 노드가 있습니다. System One 추가 후 추적표는 68개 인수 예시와 68행·195개 pytest 노드의 연결을 확인했고(E_SYSTEM_ONE_TRACE), 전체 테스트 277개가 통과했습니다(E_SYSTEM_ONE_TESTS). 이전 기록은 최초 59개(E_CAPABILITY_TRACE), 사이드바 추가 후 60개(E_SIDEBAR_TRACE), 인라인형 추가 후 61개(E_SIDEBAR_INLINE_TRACE)이며, 248개 시점의 E_TRACED_TESTS와 인라인형 집중 검사 5개(E_SIDEBAR_INLINE_TESTS)도 별도 기록으로 남아 있습니다. 추적표 일치와 테스트 실행 근거는 구분합니다.
    • 실환경 근거: 실제 Owner를 system_one을 설정해 다시 시작하자 health가 system_one: ready를 보고했고, 실제 노트 40_Knowledge/Notes/KOS 점검 - 생성 효과.md의 수동 미리보기가 status: draft를 seed(확신도 0.93)로 매핑했습니다. 미리보기는 적용하지 않고 취소했으며 Vault Markdown 22개의 해시는 그대로였습니다(E_SYSTEM_ONE_LIVE, E_SYSTEM_ONE_PRESERVATION, 목표 KNOWLEDGEOS_REAL_ADOPTION.SYSTEM_ONE). 이 한 번의 관찰은 수동 미리보기 경로이며, 자동 standardize가 System One 값을 쓰는 실제 실행은 기록이 없습니다. 그 밖에 PROJECT_STATE에는 C2 적용 실행을 따로 식별한 근거가 없습니다. E_REAL_ROLE_SMOKE는 정리·강화·자유 요청을 기록하지만 자유 요청의 최종 매핑 명령을 명시하지 않으므로, 이 기록만으로 C2 포함 여부를 판정할 수 없습니다. E_VAULT_CONFIG_CLEANUP은 실제 Vault의 T10_Daily 정비와 vault-check 근거이며 C2 실행 증거와는 구분합니다. 테스트 통과와 실환경 관찰도 서로 다른 근거입니다.
    • 남은 일: 현재 인계(handoff)는 "열린 정리 제안을 검토하고, 첫 자연 시각의 매시간 standardize 실행을 System One과 함께 관찰하며, related_min_score·related_min_probability·min_confidence를 실제 노트에 맞춰 조정"하는 것입니다(incomplete). 실제 시각에 도는 예약 슬롯 자체는 임시 index.embed 작업으로만 관찰했습니다(E_REAL_SCHEDULER_SLOT). standardize 슬롯은 아직 자연 실행을 확인하지 않았습니다. 확신도 기준 0.7은 시작값입니다. 사이드바 GUI 관찰은 macOS 화면이 잠겨 있어 사이드바 영역의 CDP 렌더만 확인한 것입니다. 이 미리보기는 "Preview cancelled; nothing written"으로 취소했습니다.
    • 열린 질문: Blueprint §9에서 C2에 직접 걸린 항목은 기본 ai_policy(지금은 ask)가 예약 정리를 쓰기 시작한 뒤에도 맞는지, 그리고 예약 작업 기본 주기가 실제 사용과 맞는지입니다. 규격화 규칙 자체에 대해 열린 질문은 기록되어 있지 않습니다.
    • 후속 과제: 모바일 M1(템플릿 노트가 STD-7을 통과해야 함)과 M2(kos_request 표시를 C2 쓰기 경로로 지우는 것)가 이 기능에 기대지만 아직 시작 전입니다. 자세한 것은 로드맵와 현재 상태를 보세요.

    8. 관련 기능#

    • C1 정리: 규격화가 건드리지 않는 판단 필드(이미 유효한 type의 재분류, 제목, 태그, 링크, 폴더 등)를 제안으로 맡습니다. 같은 System One이 정리의 scout 단계에 참고용 힌트를 주기도 합니다(ORG-7).
    • C5 문서 관리: 충돌 표시·YAML 오류·중복 ID로 규격화가 건너뛴 노트를 주의 항목으로 보여 줍니다.
    • C6 검토: "자동 변경 되돌리기"가 마지막 Autofix나 수동 규격화를 되돌립니다.
    • C7 예약 작업: 매시간 standardize 작업이 자동 경로를 실행합니다.
    • C10 Gateway: 다른 Operation이 보낸 포착 노트에도 C2와 C1이 일반 노트처럼 적용됩니다.
    • C11 호출·관리 화면: Thin Client "규격화 미리보기", 사이드바 버튼, CLI standardize가 C2를 호출합니다.
    • 사용 가이드: Obsidian·콘솔·CLI 사용 안내 전체.
