    C2 규격화 (Standardize)

    규격화는 frontmatter 없이 자유롭게 쓴 노트에 id·type·created·status·ai_policy 같은 계약 속성을 최소한으로 채우고 모양을 다듬는 기능입니다. 생각을 새로 쓰거나 파일을 옮기지는 않습니다. 본문 끝에 잘못 놓인 속성 줄을 머리말로 옮기는 경우를 제외하면 본문을 보존하고, 사용자 정의 속성과 이미 규격에 맞는 노트는 그대로 둡니다(STD-5). 제목·태그·링크·폴더의 새 판단은 C1 정리가 맡습니다.

    항목 내용
    호출 경로작성 시점 템플릿(호출 없음), 수동 미리보기·적용·취소, CLI 일괄 실행, 매시 정각 예약 standardize
    실행 담당정적 StandardizationOfficer와 정적 EvalOfficer (규칙 9만 System One 직접 호출)
    Hermes Profile없음 (단, 자유 요청 번역 시에만 kos-director 사용)
    Graph / TemporalOfficer 1단계 직렬 LangGraph + WorkWorkflow; 수동 확정·취소만 ActionWorkflow; 되돌리기는 즉시 처리
    쓰는 결과노트 frontmatter 최소 변경, State의 changes 변경 이력(되돌리기용)

    1. 네 가지 시작 경로와 입력#

    사용자가 노트를 만들거나 고친 뒤 규격화가 개입하는 경로는 네 가지입니다.

    1. 작성 시점(Obsidian 플러그인): QuickAdd와 Templater 템플릿(99_System/Templates/)으로 노트를 만들면 처음부터 규격에 맞는 frontmatter가 들어갑니다. KnowledgeOS 프로세스를 부르지 않으며, 템플릿으로 생성한 노트는 규격화가 변경을 제안하지 않도록 맞춥니다(STD-7).
    2. 수동 미리보기(Obsidian Thin Client): 사이드바에서 규격화 → 미리보기를 누르거나 명령 팔레트·파일 메뉴에서 규격화 미리보기를 실행합니다. 클라이언트는 노트 본문을 보내지 않고 경로 목록과 마지막으로 본 내용의 SHA-256 해시만 standardize.preview 요청에 담아 보냅니다(SUR-1). 바꿀 내용이 1건 이상이면 계산된 결과 바이트를 State에 저장한 채 Work가 awaiting_confirmation 상태로 대기하고, 사이드바(Thin Client 1.3.0)에서는 diff 위에 System One: 항목 → 값 (NN%) 줄을 표시한 뒤 같은 영역의 적용(standardize.confirm) 또는 취소(standardize.cancel)를 기다립니다. 확정하지 않은 채 사이드바 탭이나 대상 노트를 바꾸면 즉시 취소 요청을 보내고, 늦게 도착한 미리보기 응답도 자동 적용하지 않습니다(SUR-9). 바꿀 내용이 0건이면 대기 없이 바로 완료됩니다.
    3. CLI 일괄 실행: 터미널에서 knowledgeos standardize PATH --dry-run 또는 --apply를 실행하면 standardize.batch 요청이 접수됩니다. --dry-run은 계획된 변경과 diff, 건너뛴 목록만 출력하고 Vault와 변경 이력(changes)에 아무것도 쓰지 않습니다(SUR-5).
    4. 자동 예약 실행(standardize 작업): Owner가 켜져 있는 동안 C7 스케줄러가 매시 정각(0 * * * *, 서울 시각)에 schedule/standardize 행위자로 standardize.auto를 실행합니다. 수동으로 즉시 돌릴 때는 knowledgeos job run standardize를 씁니다. 자동 경로는 Git 이력이 아니라 State의 자동 커서(standardize_seen.jsonl)에 기록된 마지막 정산 내용 해시와 현재 파일의 해시를 비교해 내용이 달라진 approve 노트만 후보로 올립니다(JOB-1). 이때 수정 시각이 조용한 시간(기본 10분, quiet_period_minutes) 이내인 노트는 quiet_period 사유로 건너뛰어 다음 정각에 다시 확인합니다(STD-4).

    사용자가 더보기 → 자유 요청에 문장을 적어 보낸 경우에는 System One 사전 거름(free_text_command)을 거쳐 kos-director(openai-codex/gpt-6.1-sol, reasoning_effort: high)가 standardize.preview 명령 초안으로 번역할 수 있습니다(C11). 그 밖의 모든 규격화 요청은 정형 접수 코드가 바로 처리합니다.

    2. 실행 구조: Hermes Profile · Graph · Temporal 접점#

    규격화는 정적 Officer 경로입니다. 공통 실행 단계(begin, compose, open, evaluate_*, commit, settle)의 세부 동작은 구조를 따르며, C2의 실제 접점은 다음과 같습니다.

    • Hermes Profile 없음: StandardizationOfficer는 Owner 프로세스 내부의 정적 Python 코드로 동작하며, EvalOfficer 역시 정적 검사 다섯 항목(제외 규칙 준수, 결과 계약 유효성, 비관리 속성 보존, 최소 diff, System One 판단 근거)만 실행합니다. 의미 기준이 없으므로 kos-eval을 포함한 어떤 Hermes Profile도 호출하지 않습니다.
    • Graph 형태: standardize.preview, standardize.batch, standardize.auto는 모두 StandardizationOfficer → evaluation으로 이어지는 1개 생산자 직렬 LangGraph에 매핑되어 1개 세그먼트(생산자 호출 1회 예산)로 실행됩니다.
    • Temporal과 직접 실행의 구분: 위 세 명령은 WorkWorkflow(knowledgeos.work.v1)로 실행됩니다. 수동 미리보기가 awaiting_confirmation으로 멈춘 뒤 사용자가 누르는 적용(standardize.confirm)과 취소(standardize.cancel)는 대기 중 Work를 재개하는 경로(engine.resume)를 타므로 별도의 ActionWorkflow(knowledgeos.action.v1)로 실행됩니다. 반면 뒤에서 설명할 자동 변경 되돌리기(review.undo)는 Work나 Action Workflow를 열지 않고 접수 worker 안에서 즉시 동기 처리됩니다(C6).

    3. 건너뛰는 대상과 규칙 1~9의 실제 순서#

    접수 단계와 StandardizationOfficer는 먼저 손대지 않을 노트를 걸러 냅니다.

    1. 경로 제외: .으로 시작하는 숨김 경로, 80_Assets/ 첨부 폴더, .md가 아닌 파일, .gitignore에 걸린 경로, 시스템 폴더(99_System/), 검토 산출물(01_AI_Review/), 모바일 요청 예약 경로(00_Inbox/Requests/)는 제외합니다. 폴더나 . 전체를 지정하면 이 경로들을 조용히 빼고, 특정 파일을 직접 지정했을 때만 결과의 건너뜀 목록(skipped)에 사유를 남깁니다. Vault 루트에 둔 일반 Markdown 문서는 폴더만으로 제외하지 않으며, frontmatter의 type이 home 또는 system일 때만 내비게이션 노트로 건너뜁니다(STD-1).
    2. 내용·정책 제외: ai_policy가 deny이거나 퇴역·알 수 없는 정책값인 노트(빠지거나 빈 값만 approve), Git 병합 충돌 표시(<<<<<<<, =======, >>>>>>>)가 있는 노트, UTF-8로 읽을 수 없는 파일, YAML 파싱이 깨진 노트, Vault 안에서 id가 다른 노트와 겹치는 노트는 모두 건너뜁니다(DOC-3). 이 가운데 충돌·깨진 YAML·중복 ID는 C5 주의 항목으로 노출되며, 자동 경로에서는 내용이 바뀔 때까지 다시 시도하지 않도록 커서에 정산합니다.

    제외되지 않은 노트에 대해서는 줄바꿈(\n 또는 \r\n), UTF-8 BOM, 기존 속성 순서, 따옴표, 사용자 정의 속성, 본문 바이트를 그대로 유지하는 편집기가 아래 규칙을 순서대로 적용합니다. 값이 비어 있거나 계약 모양에 어긋난 항목만 고치며, 새로 넣는 속성은 frontmatter 맨 끝에 붙입니다(STD-6).

    1. 규칙 1 — frontmatter 블록 생성: 맨 위 --- 블록이 없으면 빈 frontmatter를 새로 만듭니다.
    2. 규칙 2 — id 채우기: id가 문자열이 아니거나 소문자 UUIDv4 형식이 아니면 고칩니다. 앞뒤 공백이나 대문자만 다른 유효 UUIDv4는 소문자 정규화(shape)로 다듬고, 없거나 잘못된 값에는 새 UUIDv4를 발급합니다.
    3. 규칙 3 — type 추론: type이 비어 있으면 폴더 관례에서 결정합니다(00_Inbox/ → capture, 40_Knowledge/Ideas/ → idea, 40_Knowledge/Notes/ → knowledge, 40_Knowledge/Questions/ → question, 40_Knowledge/Sources/ → source, 20_Projects/<이름>/<이름>.md → project). 폴더로 정할 수 없으면 규칙 9 질문으로 넘깁니다. 이미 값이 있을 때는 알려진 8개 종류(capture, idea, knowledge, question, project, source, report, proposal)와 대소문자·공백만 다를 때만 소문자로 정규화하며, 사용자가 직접 쓴 알 수 없는 type은 건드리지 않습니다.
    4. 규칙 4 — created 채우기: 비어 있으면 Owner가 그 경로를 처음 관찰한 시각(State first_seen.jsonl에 기록한 서울 시각 기준 오프셋 포함 ISO-8601)을 넣습니다. 이미 문자열이 있으면 2026-11-21이나 2026/11/21 9:30처럼 오프셋이 빠졌거나 구분자가 다른 날짜를 +09:00 기본 오프셋이 붙은 ISO-8601 형식으로 고칩니다.
    5. 규칙 5 — status 채우기: type이 상태를 갖는 여섯 종류(capture, idea, knowledge, question, project, source)에 속할 때만 적용합니다(daily, report, proposal, 알 수 없는 종류는 제외). 값이 비어 있으면 종류별 초기 상태(capture=unprocessed, idea=seed, knowledge=seed, question=open, project=planned, source=unread)를 넣고, 허용 상태(종류별 상태 + archived)와 대소문자·공백만 다르면 정규화합니다. 허용 목록에 없는 값이면 규칙 9 질문으로 넘깁니다.
    6. 규칙 6 — ai_policy 기본값: 비어 있거나 없으면 approve를 채웁니다. 이미 적힌 정책은 덮어쓰지 않습니다.
    7. 규칙 7 — 열거형·목록 모양 정리: ai_policy, sensitivity(public·personal·confidential), confidence(low·medium·high), capture_kind(text·link·voice·image)가 대소문자·공백만 다르면 소문자로 맞춥니다. tags·aliases가 있으면 문자열 목록으로 정규화하되 여러 줄 블록 목록(- item) 형식은 유지하고, tags는 앞의 #을 떼며 쉼표·공백으로 이어 쓴 문자열도 목록으로 나눕니다. 다만 중첩 목록이나 객체처럼 해석이 모호한 값은 건드리지 않습니다.
    8. 규칙 8 — 본문 끝 목록 줄 옮기기: 본문 맨 끝에 tags:, aliases:, related:, projects:, sources:, supports:, contradicts:, derived_from:으로 시작하는 줄(한 줄 형태 또는 - item 블록)이 잘못 남아 있으면 이를 읽어 frontmatter의 기존 목록 뒤에 중복 없이 합치고 본문에서 그 줄들만 제거합니다(STD-2). 기존 frontmatter 값이 정규화할 수 없는 구조면 안전을 위해 본문과 frontmatter 모두 그대로 둡니다.
    9. 규칙 9 — System One 폐쇄형 선택 질문: 규칙 1~8로 정하지 못한 고정 선택지 항목만 OpenAI Decisions API(POST /v1/decisions, 기본 모델 gpt-6-luna)에 직접 묻습니다.

    4. 규칙 9의 System One 질문·확신도·fallback#

    규칙 9는 Hermes Profile이 아니라 Owner가 OpenAI Decisions API에 직접 보내는 선택형 호출입니다. 노트 1개마다 한 번의 요청으로 아래 해당하는 질문을 묶어 보냅니다.

    묻는 항목 묻는 조건 선택지(공통으로 none_of_these 포함)
    typetype이 없고 규칙 3 폴더 관례로도 정해지지 않을 때capture, idea, knowledge, question, project, source
    status상태를 갖는 여섯 종류인데 현재 값이 유효 상태·archived와 대소문자 무시로도 맞지 않을 때해당 종류의 유효 상태 + archived
    confidenceknowledge 노트에서 이미 값이 있는데 low·medium·high가 아닐 때 (비어 있으면 묻지 않음)low, medium, high
    capture_kindcapture 노트에서 비어 있거나 유효값이 아닐 때text, link, voice, image

    type이 규칙 9에서 새로 정해진 노트는 같은 단계 안의 재계획 루프에서 규칙 5를 다시 탑니다. 이때 status가 비어 있었다면 규칙 5가 초기 상태를 채우지만, status: 초안처럼 이미 잘못된 status가 적혀 있었다면 StandardizationOfficer가 두 번째 API 요청을 보내 그 종류에 맞는 status를 이어서 묻습니다(STD-9). 반대로 ai_policy, sensitivity, 이미 유효한 type의 재분류, 알 수 없는 기존 type, 빠진 confidence, 제목·태그·링크는 절대 묻지 않습니다.

    보내는 입력은 노트의 경로·제목·frontmatter·본문 앞 최대 max_input_chars(기본 8,000자)입니다. 경로와 수동·일괄·자동 출처에 관계없이 보내기 직전 디스크의 현재 파일을 다시 읽어 ai_policy가 approve인 경우에만 전송합니다. State의 system_one.jsonl에는 요청 목적(standardize), work_id, 모델, 질문 키 이름, 입력 해시, 토큰 수와 성패만 기록하고 노트 텍스트는 남기지 않습니다.

    답변이 선택지 중 하나(none_of_these 제외)이고 confidence >= min_confidence(기본 0.7)일 때만 system_one 규칙 변경으로 채택합니다. 아래 fallback 조건에서는 해당 필드만 바꾸지 않고 결과의 미결정 목록(undecided)에 사유를 남기며, 규칙 1~8의 결정적 정리는 중단 없이 그대로 진행합니다(STD-11).

    • unconfigured: settings.system_one.api_key_file이 설정되지 않음.
    • unavailable: API 키 파일이 0600 개인 파일이 아니거나 통신·응답 오류가 남. 한 번의 Officer 단계 안에서 첫 실패가 나면 같은 작업의 남은 노트에서는 재시도하지 않고 바로 unavailable로 처리합니다.
    • deferred: Activity 실행 제한 시간(activity_timeout_seconds, 기본 120초) 종료까지 timeout_seconds + 10초 미만만 남아 다음 노트를 미룸.
    • policy: 접수 뒤 보내기 직전 사이에 노트가 deny로 바뀌거나 삭제됨.
    • refused / none_of_these / low_confidence: API가 거절하거나 none_of_these를 고르거나 확신도가 기준(0.7) 미만임.

    자동 경로(standardize.auto)에서는 규칙 1~8 적용 결과, 미변경, 영구 건너뛰기(충돌·UTF-8 불가·YAML 오류·중복 ID·내비게이션)와 low_confidence·none_of_these·refused·policy 결과를 State standardize_seen.jsonl 커서에 정산해 내용 해시가 바뀔 때까지 다시 묻지 않습니다(STD-10). 반면 unavailable이나 deferred가 남은 노트는 커서에 정산하지 않으므로 다음 매시 정각 실행에서 자동으로 다시 묻습니다(STD-11).

    5. 반영, 변경 이력, 자동 변경 되돌리기#

    수동 standardize.confirm, CLI --apply, 자동 standardize.auto는 모두 반영 처리에서 같은 안전 검사를 거칩니다. State의 effects.jsonl에 쓰기 의도를 먼저 기록한 뒤, 쓰기 직전 디스크의 현재 SHA-256을 미리보기/접수 시점의 preimage와 비교합니다. 한 바이트라도 달라졌으면 쓰지 않고 not_applied로 보고하며, 수동 확인에서 하나라도 실패하면 요청 상태가 unmet으로 끝납니다(STD-3).

    성공적으로 교체한 노트마다 State changes/<change_id>.json에 이력을 남깁니다. 여기에는 변경 종류(manual·batch·autofix), work_id, preimage_sha와 원본 blob 해시, result_sha와 결과 blob 해시, 정확한 변경 목록과 diff, System One 판단과 확신도가 저장됩니다.

    Obsidian 더보기 → 되돌리기 또는 자동 변경 되돌리기 명령(review.undo)은 WorkWorkflow나 ActionWorkflow를 띄우지 않고 접수 worker 안에서 바로 실행됩니다. 대상 노트의 경로 또는 note_id와 일치하는 가장 최근 manual·batch·autofix 기록을 찾아 다음 세 조건이 모두 맞을 때만 원본 바이트를 복원합니다(C6).

    1. 아직 되돌린 적이 없고(undone_at 없음),
    2. 현재 파일의 SHA-256이 기록된 result_sha와 정확히 일치하며,
    3. State에 preimage_blob이 남아 있어야 합니다.

    그사이 사용자가 노트를 고쳤거나 State 기록이 없으면 아무것도 쓰지 않고 거절하며 Git 이력을 안내합니다(REV-3). 복원에 성공하면 해당 변경 기록에 undone_at을 남기고 standardize_seen.jsonl 커서도 preimage_sha로 돌려놓습니다. 따라서 방금 되돌린 노트를 다음 매시 정각의 자동 규격화가 곧바로 다시 고치지 않으며, 이후 사용자가 내용을 수정한 뒤에만 다시 규격화 대상이 됩니다.

    6. 실제 입력과 결과 예시#

    예시 1: 폴더에 frontmatter 없이 쓴 메모 (규칙 1~8)#

    40_Knowledge/Ideas/Thought.md에 frontmatter 없이 아래처럼 본문과 잘못 놓인 tags: 줄을 썼다고 합시다.

    # 도구와 생각

도구가 생각의 모양을 바꾼다.

tags: [a, b]

    미리보기 후 적용하거나 자동 규격화가 조용한 시간(10분) 뒤 실행하면, 폴더에서 idea를 정하고 초기 상태 seed와 나머지 필수 속성을 채웁니다. 끝의 tags: 줄은 frontmatter로 옮기고, “도구가 생각의 모양을 바꾼다”라는 본문은 그대로 둡니다(STD-1, STD-2).

    ---
id: <새 UUIDv4>
type: idea
created: <Owner 최초 관찰 시각, +09:00 ISO-8601>
status: seed
ai_policy: approve
tags: [a, b]
---

    예시 2: 루트에 status: 초안만 적은 노트 (규칙 9)#

    Vault 루트 생각 메모.md에 아래처럼 적어 둔 노트에 사이드바 규격화 → 미리보기를 누릅니다.

    ---
status: 초안
sensitivity: secret-ish
---
도구가 생각의 모양을 바꾼다는 주장.

    폴더에서 type을 정할 수 없으므로 StandardizationOfficer가 먼저 System One에 type을 묻고(knowledge, 확신도 0.92), 이어서 knowledge 기준에 맞지 않는 status: 초안에 대해 두 번째 요청으로 status를 묻습니다(developing, 확신도 0.81). 미리보기 diff 위에는 두 선택과 확신도가 표시되고(sensitivity와 ai_policy는 묻지 않음), 사용자가 적용을 누르기 전에는 파일이 바뀌지 않으며, 적용 전 노트를 고쳤다면 not_applied로 남고 아무것도 쓰지 않습니다(STD-9, STD-3).

    7. 실환경 확인 범위와 구현 근거#

    현재 호스트의 규격화 미리보기·자동 쓰기·사이드바 표시 확인 범위는 현재 상태에 모았습니다. 기본 확신도 문턱 0.7이 실제 노트에 적절한지는 로드맵의 조정 과제로 남아 있습니다.

    • 명세: C2 Standardize, Vault 계약
    • 구현·설정: 규격화 규칙, C2 Officer·커서·확인, System One 클라이언트, 되돌리기 처리, C2 설정
    • 클라이언트·관련 기능: Thin Client 미리보기 UI, C1, C5, C6, C7
